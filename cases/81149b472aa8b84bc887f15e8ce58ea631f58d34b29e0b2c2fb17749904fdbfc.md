Scope: a task-authorized read-only investigation on a single remote host over SSH (host/account/address redacted). The question under investigation: whether a dedicated small acceptance container can be safely started for physical NPU 8 without disturbing existing work. No containers or processes were created, started, stopped, or reconfigured; no NPU compute was run. No judgment is recorded in this increment.

Recorded actions and observations (sample times 2026-09-25 18:00–18:01 +0800):

1. Endpoint probe succeeded (remote Python 3.13.13; cwd not a git repository).

2. `npu-smi -h` and `npu-smi info -h`: documented command surface. `npu-smi info` supports `watch`, `proc`, `-m` (mapping), `-l` (topology), `-t <type>` (board, memory, usages, health, topo, hccs, proc-mem, phyid-remap, etc.), with selectors `-i` Card ID, `-c` Chip ID, `-p` Chip Physical ID. The task notes that physical ID must not be assumed equal to the PyTorch logical ID; mapping was checked via tool output rather than computation.

3. `npu-smi info` (version 25.5.3): 8 NPU cards, 16 chips, all `Ascend910`, all Health `OK`. AICore utilization 0% on all chips. HBM-Usage per chip approximately 60695–60976 MB used of 65536 MB (i.e., nearly full on every chip). For NPU ID 4, chip 0 (Phy-ID 8, Bus-Id 0000:8D:00.0): HBM 60960/65536 MB. The process table listed one `VLLMWorker_TP` process per chip (16 total), each with process memory 57858–57862 MB, including a process on the chip with Phy-ID 8.

4. `npu-smi info -m`: mapping table shows Chip Logic ID equal to Chip Phy-ID on this host (0→0 through 15→15); specifically NPU ID 4 / Chip ID 0 maps to Logic ID 8 and Phy-ID 8 (`Ascend910`).

5. `npu-smi info -t topo -i 4`: Phy-ID 8 shows `SIO` affinity with its sibling Phy-ID 9 and `HCCS_SW` (HCCS through a switch) links to the other 14 chips.

6. `npu-smi info -t health -i 4`: NPU ID 4 Chip Count 2; Health `OK` for both Chip ID 0 and Chip ID 1.

7. A read-only attribution command was then issued for one of the observed PIDs on Phy-ID 8: read `/proc/<pid>/cgroup`, `ps -o pid,ppid,stat,etime,comm -p <pid>`, and `docker ps --format '{{.ID}} {{.Names}} {{.Status}}'`, to distinguish a container's device declaration from actual current use of the device by a process. The output of this command is not present in this increment (coverage continues), so no container attribution or start-safety judgment is recorded here.
