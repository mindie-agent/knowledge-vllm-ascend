### assistant:final_answer
结论：当前 pinned vLLM 没有合适的公开 pre-render request hook，无法在不 monkeypatch 的前提下让自定义 renderer 获得完整 `ChatCompletionRequest` / `ResponsesRequest`。

源码依据：

- `BaseRenderer.render_messages(_async)` 只接收 messages 和 `ChatParams`；`ChatParams` 不包含 `tool_choice`、`response_format` 或请求类型。
- Chat/Responses 的 `build_chat_params()` 只传递 reasoning、模板和媒体参数；tools 由 `OnlineRenderer.preprocess_chat()` 单独合并。
- `Parser.adjust_request()` 能获得完整请求，但当前调用顺序是先 render，后 adjust，无法影响 prompt。
- 原 `OnlineRenderer.render_chat` wrapper 还遗漏 Responses 与 batch 路径，并因复制 request 导致 prompt、output parser、sampling 使用不同请求状态。
- `ParserManager` 独立选择 reasoning/tool parser 后动态组合，没有 renderer/parser 或 parser-pair 校验 hook。

建议：

- 不恢复 renderer adapter 或任何全局 monkeypatch。
- 本 PR 若聚焦模型、组网和特性注册，最好将整个 serving 能力拆到后续 PR；仅保留 parsers 会成为“有输出解析、无原生 prompt renderer”的半功能。
- 如果暂时保留 parsers，只能定义为“配合外部已验证 K3 模板的 Chat Completions 输出解析”，并明确要求 reasoning/tool 两个 K3 parser 同时启用。当前 Responses 的 `VLLMValidationError` 显式拒绝是合理边界，但只在 K3 parser 启用时生效，而且发生在 tokenization 后、engine scheduling 前。
- K3 checkpoint 没有 Jinja；删除 renderer 后，普通 Chat Completions 没有仓库内完整 prompt source。本地 GPQA Jinja 仅覆盖简单文本，忽略 tools 和 response format，不能作为通用 serving 实现。
- parser-only 也不能正确映射标准 `reasoning_effort`：上游传 `reasoning_effort`/`enable_thinking`，K3 parser 却读取私有 `thinking` 参数。
- 默认 thinking 时 reasoning parser 输出仍含 response XTML envelope，需要 K3 tool parser 清理；任意漏配或混配都会泄漏控制标记或解析失败，而当前 API 无法提前验证。

完整解决方案应先上游 vLLM：

1. 将 `Parser.adjust_request()` 移到 `build_chat_params()` 和 render 之前，并让后续 parser/sampling 使用同一原 request；或
2. 增加类型化的 pre-render request adapter hook；同时
3. 增加 unified parser/renderer compatibility 校验。

这样才能通过公开 registry 恢复 K3 renderer，并一致覆盖 Chat、Responses 和 batch。
