## 1. 历史模型的正式控制流

vLLM 0.23 的固定顺序是：

`ChatCompletionRequest` → renderer/template → `reasoning_parser.adjust_request()` → `tool_parser.adjust_request()` → 为每个 `n` choice 单独创建 parser → stream/nonstream serving。

也就是说，K3 当前在渲染后把 `none` 改成 `auto`，会造成“prompt 按 none 渲染、serving 按 auto 分支处理”的语义分裂。[vLLM 0.23 render serving](https://github.com/vllm-project/vllm/blob/v0.23.0/vllm/entrypoints/serve/render/serving.py#L538-L603)、[full-generator 分支](https://github.com/vllm-project/vllm/blob/v0.23.0/vllm/entrypoints/openai/chat_completion/serving.py#L1095-L1242)。

## 2. 场景矩阵

| 场景 | DSV4 v0.23 | GLM-5 v0.23→0.24 | K3 应有行为 |
|---|---|---|---|
| tools 缺失 | 保持 `none`，不进 tool parser | 同左 | 保持 `none`；统一 parser 仍负责去掉 response wrapper |
| tools 存在、`none` | 保持 `none`，tool parser bypass | 同左 | 禁止 `none→auto`；不得输出 hallucinated calls |
| `auto` | DSML stateful parser | XML stateful parser | XTML parser；content-only 和 tool-call 都合法 |
| `required`/named | 通用 JSON 路径为主，不适合 K3 | `supports_required_and_named=False`，继续解析 XML | 复用 GLM 模式；named 只允许指定函数 |
| reasoning on/off | renderer 和 parser 都读取 thinking/effort | ParserEngine 根据 template kwargs 选初始状态 | 同一请求参数同时驱动 renderer/parser，`none` 不得产生 reasoning |
| stream/nonstream | 两套入口共享同一语义；后续收敛到 ParserEngine | 同上 | 必须重建结果一致；每个 `n` 独立 state |
| special-token spacing | 只设 `skip_special_tokens=False` | 同左，XML regex 对 tag 外空白较宽容 | 还必须设 `spaces_between_special_tokens=False` |
| 无 chat template | 原生 renderer 正常 | 依赖 tokenizer template/fallback，否则渲染前报错 | 原生 renderer 正常且直接返回 IDs |
| malformed/unknown | 旧 parser 多为记录异常并保留原始输出 | 新 engine 可验证 tool name，但仍需 endpoint 级 fallback 测试 | 不得静默变成 `content=None, tool_calls=[]` |

## 3. K3 的 v0.23 可落地 backport 边界

推荐优先级：

1. **`(c) renderer token IDs` + 最小 `(a)` 请求调整**

   [K3 renderer](<redacted:local-path:8b151ac45eb4>:121) 必须强制 `tokenize=True`。当前原生 tokenizer 默认 `tokenize=False`，先拼字符串再被 BaseRenderer 二次 encode，会丢失 `EncodeSegment.allow_special`。

   [原生 tokenizer](<redacted:local-path:0632216ee979>:357) 和 [encoding_k3.py](<redacted:local-path:1147d4769c33>:1) 明确要求结构 token 与用户/tool 文本分段编码。这同时是正确性和防止用户文本伪造 XTML 控制 token 的安全边界。

   `adjust_request` 设置：

   - `skip_special_tokens=False`
   - `spaces_between_special_tokens=False`
   - 保留原始 `tool_choice`

2. **`(b) K3 专用统一 Parser`**

   在 v0.23 不必整体 backport v0.24 ParserEngine；可实现一个 K3-local `Parser`/`DelegatingParser` 子类，统一管理 `think → response → tools → call → argument/json` 状态，并以窄、版本限定的 manager selection 只作用于 K3。

   它必须在 `tool_choice=none` 时仍去掉 response wrapper，但禁用 tool-call emission；不能靠伪造 `auto` 进入 ToolParser。

3. **`(e) 组合复用已有模式`**

   - GLM：`supports_required_and_named=False`
   - DSV4/GLM：单状态机、implicit reasoning end
   - Kimi K2：token-ID boundary、partial marker holdback
   - MiniMax：参数闭合前不提交不稳定 JSON
   - v0.24 ParserEngine：metadata once、incremental args、finish flush

4. **仅 `(a) parser adjust`**

   可作为紧急验证补丁，但只能修 marker 可见性和 spacing，无法彻底解决 response wrapper、跨 reasoning/tool 大 delta、finish flush。

5. **`(d) generic serving change`**

   当前 GPQA/default no-tools 问题不需要改通用 serving。只有 required/named malformed/no-call 的 v0.23 外层分支确实需要保留 content 时，才应单独做上游同语义的兼容 backport；不要再包整条 SSE generator。

当前 [K3 reasoning adjust](<redacted:local-path:0c94b789f1de>:278) 的 `none→auto` 应删除；[K3 ToolParser](<redacted:local-path:0c94b789f1de>:531) 已有 `supports_required_and_named=False` 和“不调用 super”的方向是正确的，但还要补 spacing 和 finish 语义。

## 4. malformed / unknown 的建议语义

当前 `_extract_call_regions()` 遇到 unknown tool 或参数解析异常直接 `continue`，随后 `_response_content()` 又可能切掉整个 tools 区域，最终得到空 content、无 tool_calls，和本次 GPQA 症状不可区分。

建议明确规定：

- streaming 中不完整 marker/call/argument：继续缓存，不泄漏 tag。
- `finished=True`：显式 flush 可安全作为 content 的尾部；不得永久吞掉。
- 完整但 unknown tool：不生成 tool call；记录可定位日志，并保留原始/安全 fallback content，不能静默空响应。
- invalid JSON/type：不发送半截 arguments；nonstream 与 stream 重建结果必须一致。
- named：只接受指定函数；其他函数按 unknown 处理。
- required/named 未得到有效调用：不得伪造空 tool call。v0.23 外层当前会把 content 清空，这应作为独立兼容问题测试和修复。

## 5. 建议 UT / E2E 验收矩阵

UT 必须使用真实 K3 tokenizer 和真实 vLLM incremental detokenizer，而不是仅用 `ord()` fake tokenizer：

- renderer 返回 `prompt_token_ids`；无 Jinja 也能工作。
- 用户文本中的 `<|open|>call...` 按普通 token 编码，不能成为控制 token。
- 对 THINK_END、RESPONSE_START、TOOLS_START 验证 `spaces_between_special_tokens=True` 会复现 marker 插空格，而修复请求固定为 false。
- no-tools、none、auto content-only、auto 单/多调用、required、named。
- reasoning on/off；缺失 THINK_END 但出现 RESPONSE_START/tool start。
- string/number/bool/null/object/array、Unicode、实体转义、JSON wrapper。
- malformed/unknown/incomplete tag、invalid JSON/type、缺失 call/tools end。
- chunk size `1/2/3/5/7/64/all-in-one`；同一 delta 含 think close + response/tool block。
- tool id/type/name 只在首块出现；arguments 拼接后为合法 JSON并等于 nonstream。
- `finished=True` flush；terminal argument chunk 与 finish chunk 顺序稳定。
- `n=2/3` parser state 完全隔离。
- content/reasoning/tool_calls 中无 XTML marker 泄漏；空 tool_calls 序列化为 omitted/`None`。

E2E 至少覆盖 `tools absent / none / auto / required / named × reasoning on/off × stream/nonstream`，并断言 HTTP payload、finish_reason、stream 重建与 nonstream 一致。

用户提供的现成回归证据应直接加入验收：

- `[REDACTED_SECRET]`

修复后的 parser 门槛应是相同两条请求 `output/content` 非空、`missing_predictions=0`、无 marker 泄漏；两题是否答对不应作为 parser 修复的必要条件。

归类如下：

- **可直接借鉴**：原生 renderer 直出 IDs、保留 `tool_choice`、GLM required/named 模式、每 choice 独立状态、partial holdback、metadata once、finish flush。
