- VA `upstream/main`：[`8a4ea1478`](https://github.com/vllm-project/vllm-ascend/commit/8a4ea1478b2eefcc516ce687674c7bef3db1f0eb)

为什么 VA KDA 需要单独处理：

1. FULL graph 为固定 shape，会把 `query_start_loc` 尾部填成同一个累计 token 数，并把 state slot 填为无效值。比如捕获 8 行、实际 5 token：

   ```text
   query_start_loc = [0,1,2,3,4,5,5,5,5]
   ```

   后三段 `seqLen=0`。[VA metadata padding](https://github.com/vllm-project/vllm-ascend/blob/8a4ea1478b2eefcc516ce687674c7bef3db1f0eb/vllm_ascend/ops/gdn_attn_builder.py#L330-L360)

2. VA 的 Torch adapter 用 `at::empty_like(value)` 创建 KDA 输出；AscendC kernel 遇到 `seqLen==0` 直接 `continue`，不会写对应输出行。因此 padding 尾部是未初始化数据，ACLGraph replay 下还可能是上一轮残留。[adapter](https://github.com/vllm-project/vllm-ascend/blob/8a4ea1478b2eefcc516ce687674c7bef3db1f0eb/csrc/attention/recurrent_kda/recurrent_kda_torch_adpt.h#L117-L153) / [kernel](https://github.com/vllm-project/vllm-ascend/blob/8a4ea1478b2eefcc516ce687674c7bef3db1f0eb/csrc/attention/recurrent_kda/op_kernel/recurrent_kda.h#L227-L264)

3. 所以 KDA wrapper 用 device-side 的 `query_start_loc[-1]` 得到 live token 数，把未覆盖尾部清零。不能简单做动态切片，因为 replay 时 live 数会变，且不应 `.item()` 引入同步。[KDA padding helper](https://github.com/vllm-project/vllm-ascend/blob/8a4ea1478b2eefcc516ce687674c7bef3db1f0eb/vllm_ascend/ops/kimi_kda.py#L37-L56)

4. 它在 norm-gate 后又 mask 一次也不是重复：padding 的 `g2` 可能是无效/NaN，`0 * sigmoid(NaN)` 仍然是 NaN。因此第一次清 KDA 输出，第二次保证最终 norm-gate 输出定义良好。[合并与二次 mask](https://github.com/vllm-project/vllm-ascend/blob/8a4ea1478b2eefcc516ce687674c7bef3db1f0eb/vllm_ascend/ops/kimi_kda.py#L500-L543)

为什么 GDN 看起来没有：

| 路径 | padding 输出策略 |
|---|---|
| VA KDA | 外层和 recurrent 输出都来自 `empty`，所以显式 mask |
| VA GDN | 外层 `core_attn_out` 直接 `torch.zeros`，设计意图是 kernel 只覆盖 live rows，padding 保持 0 |
| vLLM KDA 普通 decode | packed decode kernel 遍历所有 graph rows，遇到无效 `state_idx` 会主动写 0 |

VA GDN 使用 `torch.zeros` 是刻意保留的，代码还直接引用了社区关于 GDN padding 行不能使用 `torch.empty` 的讨论。[VA GDN allocation](https://github.com/vllm-project/vllm-ascend/blob/8a4ea1478b2eefcc516ce687674c7bef3db1f0eb/vllm_ascend/ops/gdn.py#L224-L252) / [vLLM PR #28182](https://github.com/vllm-project/vllm/pull/28182)

不过这里有一个值得继续审计的点：当前 VA GDN 内部 recurrent op 同样返回 `at::empty`，kernel 对零长度行也不写，之后又把整个 `num_actual_tokens` 范围复制回外层 zero buffer。从纯源码 contract 看，外层 `torch.zeros` 不一定足够，GDN 可能也存在未定义 padding tail；只是这些行通常被后续丢弃，尚不能据此宣称线上 bug。[GDN merge](https://github.com/vllm-project/vllm-ascend/blob/8a4ea1478b2eefcc516ce687674c7bef3db1f0eb/vllm_ascend/ops/gdn.py#L559-L592)

你说“上游社区没有”也对，但它不是完全等价路径：

- 最新 vLLM KDA 仍然从 `torch.empty` 创建输出，没有通用 `_zero_padded_output`。[upstream KDA](https://github.com/vllm-project/vllm/blob/73029d42441321b631779db3475031f5ec26dd6c/vllm/models/kimi_k3/nvidia/kda.py#L619-L630)
- 普通 decode 使用专门的 packed kernel，无效 state slot 会显式写零。[packed decode](https://github.com/vllm-project/vllm/blob/73029d42441321b631779db3475031f5ec26dd6c/vllm/models/kimi_k3/nvidia/ops/third_party/kda/fused_recurrent.py#L499-L503)
- 但 speculative recurrent kernel 对 `sequence_length==0` 同样直接返回。因此上游在这部分更像是依赖 padding 行不被消费，不是更强的“输出完整定义”保证。[upstream recurrent](https://github.com/vllm-project/vllm/blob/73029d42441321b631779db3475031f5ec26dd6c/vllm/models/kimi_k3/nvidia/ops/third_party/kda/fused_recurrent.py#L174-L195)

所以我的判断是：**VA KDA 这段逻辑当前有明确必要性；GDN 没有同款 helper 是实现策略不一致，甚至可能是待审计缺口；上游没有不能作为删除依据。** 如果要优化掉 mask，应该先让 AscendC kernel 或 adapter 保证所有 graph rows 都写确定的 0，并同时处理 norm-gate 后的 NaN 风险。

补充：如果你指的是 `in_proj_padding`，那是另一回事——用于把 TP-local fused projection 宽度补到 16 对齐的 BF16 GEMM 路径，而且最新 vLLM 上游本身就有。[upstream `in_proj_padding`](https://github.com/vllm-project/vllm/blob/73029d42441321b631779db3475031f5ec26dd6c/vllm/models/kimi_k3/nvidia/kda.py#L407-L430)

### assistant:final_answer
你说得对。按 graph 数据流重新审计后，我修正前面的判断：当前 KDA 的两次 padding mask 没有充分理由，至少第一次属于冗余防御。

核心证据：

- KDA adapter 用 `empty_like` 分配输出，`seqLen == 0` 时 kernel 直接 `continue`。
- GDN adapter 同样用 `empty`，`seqLen <= 0` 时也直接 `continue`。

所以这不是 KDA kernel 独有的语义需求，两边都会留下未写 padding。[KDA adapter/kernel](https://github.com/vllm-project/vllm-ascend/blob/8a4ea1478b2eefcc516ce687674c7bef3db1f0eb/csrc/attention/recurrent_kda/recurrent_kda_torch_adpt.h#L117-L153)、[GDN adapter/kernel](https://github.com/vllm-project/vllm-ascend/blob/8a4ea1478b2eefcc516ce687674c7bef3db1f0eb/csrc/attention/recurrent_gated_delta_rule/recurrent_gated_delta_rule_torch_adpt.h#L21-L52)。

当前 KDA 实际叠了三层处理：

1. recurrent 返回后用 `arange + compare + where` 清 `core_spec/core_non_spec`。
2. merge 前把 caller buffer `zero_()`。
3. `o_norm` 后再做一次相同的 `where`，处理 padding gate 可能为 NaN 的情况。[当前完整数据流](https://github.com/vllm-project/vllm-ascend/blob/8a4ea1478b2eefcc516ce687674c7bef3db1f0eb/vllm_ascend/ops/kimi_kda.py#L500-L543)

但 `o_norm` 是逐 token、只在最后一维归一化；前后没有跨 token 归约。只要保留最后一次 mask：

- padding 行的 NaN 不会污染 live 行；
- 最终 padding 仍会被置零；
- 第一次 recurrent-output mask 不会改变任何 live 输出或 state；
- pure spec/non-spec 分支里，merge 前的 `zero_()`还会马上被整段赋值覆盖。

因此从静态语义看，合理的最小实现是：先只保留 norm 后的一次 mask，删除 recurrent 后的 mask 和 merge 前的预清零。你看到它明显比 GDN 的一次 `torch.zeros` 更长，和实现完全一致：现在是多次整张量读写，还额外生成 `arange` 和布尔 mask。

GDN 没有这套逻辑，并不是因为它的 kernel 会清 padding，而是它依赖“外层 zero buffer + 只写有效区域”的 output-buffer 契约；上游也是这样设计的。[上游 GDN output buffer](https://github.com/vllm-project/vllm/blob/73029d42441321b631779db3475031f5ec26dd6c/vllm/model_executor/layers/mamba/gdn/qwen_gdn_linear_attn.py#L943-L965)。不过 VA 的 GDN generic/spec 路径也存在 `empty` 临时输出再拷贝的情况，所以严格说它的 padding 保证同样不够强；这更像实现不对称，而不是 KDA 必须特殊处理的证据。

历史上这几层逻辑在 K3 初次合入时一起加入，没有对应的上游实现、独立故障归因或“分别删除其中一次”的 A/B；现有 UT 只验证 helper 能清 NaN，并没有证明两次都不可缺少。

所以目前最准确的结论是：

- “至少需要定义一次最终 padding”有合理性；
- “KDA 必须做两次 mask，而 GDN 不需要”没有源码依据；
- 当前实现很可能是过度防御，第一层 mask 应优先删除；
- 是否进一步改成 GDN 式单次 zero buffer，需要在 graph size > live tokens、spec/non-spec、idle DP 三类 replay 上做一次删除式 A/B 才能定论。

### assistant:final_answer
不完全对。只有同时修改“kernel 写入契约”时，才能用外层 `zeros` 替掉两个 mask；单纯把 `torch.empty` 改成 `torch.zeros` 不够。

当前 pure spec/non-spec 路径会发生：

```python
core_attn_out = torch.zeros(...)   # 外层先清零
core_spec = recurrent_kda(...)     # 内部仍然 empty_like，padding 未写
core_attn_out[...] = core_spec     # 整段 copy，重新把垃圾覆盖回来
core_attn_out = o_norm(..., g2)    # padding gate 若为 NaN，0 * NaN 仍是 NaN
```

整段赋值发生在 [kimi_kda.py L523-L543](https://github.com/vllm-project/vllm-ascend/blob/8a4ea1478b2eefcc516ce687674c7bef3db1f0eb/vllm_ascend/ops/kimi_kda.py#L523-L543)。因此：

- 去掉第一个 mask 后，recurrent 的未写 padding 会覆盖外层零。
- 去掉最后一个 mask 后，即使 attention output 是零，`g2` padding 为 NaN 时 norm-gate 仍能重新产生 NaN。

GPU 为什么不用外层 zero？因为它采用的是更弱的契约：只保证 live-token 输出，padding 是 don’t-care，并不保证 padding 为零。

具体来说：

- metadata builder 会从 active spec/non-spec 索引中排除零长度 graph padding。[GPU metadata](https://github.com/vllm-project/vllm/blob/73029d42441321b631779db3475031f5ec26dd6c/vllm/models/kimi_k3/nvidia/kda_metadata.py#L446-L510)
- fused decode 直接写 `core_attn_out[:, :num_actual_tokens]`。[GPU KDA](https://github.com/vllm-project/vllm/blob/73029d42441321b631779db3475031f5ec26dd6c/vllm/models/kimi_k3/nvidia/kda.py#L718-L743)
- 普通 packed decode 遇到非法 state index 会显式写零。[GPU recurrent kernel](https://github.com/vllm-project/vllm/blob/73029d42441321b631779db3475031f5ec26dd6c/vllm/models/kimi_k3/nvidia/ops/third_party/kda/fused_recurrent.py#L180-L205)
- 但 spec 的零长度序列仍然直接 return，尾部其实也没有“保证为零”。所以 GPU 不是用别的办法清了 padding，而是假设这些值不可观察。

因此分两种修法：

- 最小、语义安全：保留最后一次 post-norm mask，删掉 recurrent 后的 mask 和 merge 前 `zero_()`。
- 真正无额外 mask kernel：外层改 `zeros`，同时让 recurrent KDA 接受 caller-owned `out`、只写 live 行，禁止整段 copy；另外还要证明 `g2` padding 永远 finite，或者把 valid-row 判断融合进 RMSNormGated kernel。

所以“外层改 zero + 直接删两个 mask”现在不是安全的最简单修复；“只留最后一个 mask”才是当前数据流下最小的安全改动。至于是否可以完全采用 GPU 的 padding-don’t-care 契约，需要用 graph padding、spec replay、idle DP 做删除式 A/B；源码里没有证据说明 Ascend必须比 GPU 多这一层保证。
