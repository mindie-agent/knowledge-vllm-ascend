### assistant:final_answer
结论：不是权重问题，而是 exact image 内 SGLang 与 DeepEP wheel 的 Python API 没对齐。

- 当前镜像 tag 解析为 manifest digest `sha256:352bc889…`，构建参数是 `SGLANG_TAG=0721_zkk`、`SGLANG_KERNEL_NPU_TAG=2026.7.4`。发布命令只设置了旧环境变量，没有 dispatcher dtype 参数。[issue #32519](https://github.com/sgl-project/sglang/issues/32519)
- DeepEP 2026.7.4 的 default normal dispatch 已要求显式 `quant_mode`；`None` 会走 BF16，不读取 `DEEP_NORMAL_MODE_USE_INT8_QUANT`。
- `02a924b` 的 normal dispatcher 没把 `self.deepep_output_dtype` 传给 `buffer.dispatch()`。即使加 `--deepep-dispatcher-output-dtype int8`，也只更新 `use_fp8`；NPU `_update_int8_quant_env()` 仍是 `pass`。
- 所以 normal/prefill 返回单 Tensor，SGLang 解包得到 `hidden_states_scale=None`，最终形成 `per_token_scale=[None]`。
- A3 算子本身支持 normal INT8，且 A3 EP64 仍走 intranode 分支，因此无需改或重编译 `.so`。

最小正确修复是 Python-only，在 `_DeepEPDispatcherImplNormal._dispatch_core()` 的 `buffer.dispatch(...)` 增加：

```python
**(
    {"quant_mode": self.deepep_output_dtype.value}
    if _is_npu
    else {}
),
```

修复后保持：

```text
--deepep-mode auto
--deepep-dispatcher-output-dtype auto
```

target W4A8 会得到 `int8`，unquant draft 保持 `bf16`。不要全局指定 dispatcher `int8`，否则会同时污染 unquant draft。

如果坚持零源码修改，只能做有限正确性旁路：

```text
--deepep-mode low_latency
--chunked-prefill-size 512
--max-running-requests 16
```

DP4 后每个 scheduler 的 prefill 上限是 128；gamma 7 的验证宽度为 8，`16×8=128`。该方案仅适合短请求/精度门禁，不等价于原来的 `auto + 8192` 正常拓扑。`DEEP_USE_MODE=alltoall` 也不可用，2026.7.4 存在 `quant_mode` 关键字签名不匹配。
