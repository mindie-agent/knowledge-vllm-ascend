## 1. K3 的 KV layer 构成

K3 target 一共 93 个需要 KV/state 的层：

| 类型 | 数量 | 内容 |
|---|---:|---|
| Target MLA | 24 | 完整序列 MLA KV |
| Target Mamba/KDA | 69 | recurrent/conv state |
| DSpark draft attention | 5 | GQA 或 MLA draft |

因此：

- GQA DSpark：`24 MLA + 69 Mamba + 5 GQA`
- MLA DSpark：`24 target MLA + 69 Mamba + 5 draft MLA`

进入 grouping 之前，Ascend 已经把这些层对齐到相同 scheduler block/page：

- TP16：scheduler block 384，page 488,448 B
- TP8：scheduler block 768，page 976,896 B

这里的 384/768 是 scheduler ownership 粒度，attention kernel 仍可使用更小的 kernel block，例如 TP16 下的 128。

## 2. 原生 0.27 的通用 grouping 算法

上游 [`_get_kv_cache_groups_uniform_page_size()`](<redacted:local-path:1020163726d8>:1140) 大致执行：

1. 按可合并的 KV spec 将 layer 放入不同 bucket。
2. 找到最小 bucket 的 layer 数量，作为统一 `group_size`。
3. 每种 bucket 都按照这个 `group_size` 拆成若干组。
4. 每个 KV group 持有一张独立 block table。
5. runner 遍历所有 KV group/attention group，逐一调用 metadata builder。

其核心公式是：

```text
group_size = min(各 spec bucket 的 layer 数量)
group_count = Σ ceil(bucket_layer_count / group_size)
```

仅当最大 bucket 小于最小 bucket 的 1.5 倍时，才会改用最大 bucket 避免过多 padding。K3 的 69 和 5 相差很大，不会进入这个特殊分支。

## 3. GQA DSpark 的 20 个 group 怎么产生

GQA 下三个 spec bucket 无法合并：

```text
Target MLA:    24
Draft GQA:      5
Mamba/KDA:     69
```

最小 bucket 是 5，所以：

```text
group_size = min(24, 5, 69) = 5
```

然后分别切分：

### Target MLA

```text
ceil(24 / 5) = 5 groups
实际大小：[5, 5, 5, 5, 4]
```

### Draft GQA

```text
ceil(5 / 5) = 1 group
实际大小：[5]
```

### Mamba/KDA

```text
ceil(69 / 5) = 14 groups
实际大小：[5 × 13, 4 × 1]
```

合计：

```text
5 MLA groups
+ 1 GQA group
+ 14 Mamba groups
= 20 KV groups
```

原始结构可以表示为：

```text
KV group 0~4     Target MLA
KV group 5       Draft GQA
KV group 6~19    Mamba/KDA
```

### 为什么是 20 次 build

MRV1 在 [`model_runner_v1.py`](<redacted:local-path:8ee7f05d0387>:3062) 中执行：

```text
for each KV group:
    for each AttentionGroup in that KV group:
        builder.build(...)
```

MRV2 在 [`attn_utils.py`](<redacted:local-path:3d6ccc29f766>:218) 也是相同的双层循环。

原始 GQA 的每个 KV group 都是同一种 backend/spec，所以每组只有一个 AttentionGroup：

```text
20 KV groups × 1 builder = 20 次 build
```

这里说的是每次 target forward/input preparation 的 metadata build，不包括 DSpark 后续七步 drafting loop 自己的 build。

## 4. 原生 MLA DSpark 为什么不是 20 个 group

MLA draft 与 target 都是 `MLAAttentionSpec`：

```text
Target MLA: 24
Draft MLA:   5
Mamba:      69
```

原生 0.27 的 `MLAAttentionSpec.merge()` 允许 target/draft MLA 合并，并用：

```python
non_causal_multi_token_decode = any(...)
```

产生一个 merged spec。

因此 attention bucket 直接成为：

```text
24 target MLA + 5 draft MLA = 29 MLA
```

然后：

```text
group_size = min(29, 69) = 29
```

分组结果：

```text
MLA attention: ceil(29 / 29) = 1 group，大小 29
Mamba:         ceil(69 / 29) = 3 groups，大小 [23, 23, 23]

合计 4 groups
```

所以 MLA DSpark 原始布局就是：

```text
group 0: target MLA 24 + draft MLA 5 = 29
group 1: Mamba 23
group 2: Mamba 23
group 3: Mamba 23
```

它没有 GQA 的 20-group 性能问题。

但是原始 MLA 合并有一个语义缺陷：target MLA 的 `non_causal_multi_token_decode=False` 和 draft MLA 的 `True` 被压成了一个 merged spec，最终整个 group 都表现成 `True`，没有保留逐层差异。

## 5. 当前 PR 怎么解决 GQA 的 20-group 问题

当前 PR 在 [`patch_kv_cache_utils.py`](<redacted:local-path:3c6b3a22fc07>:114) 增加 K3 专用 grouping。

它识别完整的 K3 DSpark 拓扑：

- target attention
- draft attention
- aligned speculative Mamba
- 所有 layer 都被完整匹配
- block size 一致
- page size 一致
- Mamba spec 一致

不满足完整签名时仍回到 0.27 通用 grouping。

### 第一步：合并 scheduler ownership

它不再按照 MLA/GQA backend 类型分别建立 scheduler group，而是把所有完整序列 attention 放入一个 `UniformTypeKVCacheSpecs`：

```text
24 target MLA + 5 draft GQA/MLA = 29 attention layers
```

关键语义是：

> target 和 draft 共用一张 scheduler block table，但每个 layer 仍拥有独立的物理 KV tensor 和独立的原始 KV spec。

因此这不是把 MLA KV 和 GQA KV 写进同一份内容，而只是让它们使用相同的 block ID ownership。

代码中特意先插入 target MLA，使 scheduler 将这个 group 解包成 target 的 causal full-attention representative，从而继续使用 `FullAttentionManager`。

### 第二步：按 attention group 大小切 Mamba

代码计算：

```python
mamba_group_count = ceil(mamba_layer_count / attention_layer_count)
```

对 K3：

```text
ceil(69 / 29) = 3
```

再均衡切分：

```text
Mamba group sizes = [23, 23, 23]
```

最终：

```text
group 0: target MLA 24 + draft attention 5 = 29
group 1: Mamba 23
group 2: Mamba 23
group 3: Mamba 23
```

所以 GQA 和 MLA 都变成 4 个 scheduler KV group。

这个算法没有硬编码 TP16 的 384/488448，也没有硬编码 24/5/69，因此 TP8 以及 layer 数量变化后的同类结构也能按实际比例计算。

## 6. 为什么 4 个 KV group 仍然是 5 次 build

worker 的 AttentionGroup 去重键不是只有 `kv_cache_group_id`，而是：

MRV1：

```text
(attention backend, exact KV spec)
```

MRV2 还会加上：

```text
num_heads_q
```
