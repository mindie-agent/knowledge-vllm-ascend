### 现在仍然存在的多余 D2H

GQA builder 中，并行 draft 时先选择设备 `seq_lens`，随后又执行 `.tolist()`：

- 设备长度选择：[attention_v1.py:524](<redacted:local-path:f08a16241754>:524)
- 直接触发同步 D2H：[attention_v1.py:535](<redacted:local-path:f08a16241754>:535)
- FIA sink 实际又使用设备 Tensor：[attention_v1.py:590](<redacted:local-path:f08a16241754>:590)

所以 GQA sink fast path 的 `.tolist()` 是确定可以删除的；只需要给传统 FIA、C8、encoder-decoder 等 fallback 保留 host list。

MLA 的绕路更加明显：

1. 已保存设备 `seq_lens_device`：[mla_v1.py:704](<redacted:local-path:9af0dc6c2b04>:704)
2. 仍优先使用精确 CPU mirror：[mla_v1.py:714](<redacted:local-path:9af0dc6c2b04>:714)
3. 转成 Python list：[mla_v1.py:895](<redacted:local-path:9af0dc6c2b04>:895)
4. 再重新构造 NPU Tensor：[mla_v1.py:955](<redacted:local-path:9af0dc6c2b04>:955)

A5 FlashMLA 也是 CPU list 再 H2D，见 [mla_v1.py:633](<redacted:local-path:9af0dc6c2b04>:633)。

所以目前 #15336 做到了“算子内部 tiling 下沉”，但 MLA metadata 输入还没有真正设备化。

### Model runner 中可以删除的部分

当前 `_needs_seq_lens_cpu_sync` 只根据 backend 类型判断，GQA/MLA 全部要求精确 CPU 长度：

[model_runner_v1.py:458](<redacted:local-path:94dff6371c93>:458)

随后 `_correct_optimistic_seq_lens_cpu()` 等待上一步 accepted-count D2H：

[model_runner_v1.py:1454](<redacted:local-path:94dff6371c93>:1454)  
[model_runner_v1.py:1654](<redacted:local-path:94dff6371c93>:1654)

在完成 builder 去 host 化后，K3 的这些路径不再需要这个同步：

- A2/A3 GQA FIA v2 sink
- A2/A3 MLA FIA v2 sink
- A5 GQA FlashAttention sink
- A5 MLA FlashAttention/FlashMLA sink
- DSpark target/draft attention

但不能简单按 `AscendAttentionBackend`/`AscendMLABackend` 整体关闭。应该让 metadata builder 声明类似 `requires_exact_host_seq_lens` 的能力，再由 model runner 汇总，因为这些路径仍需要精确 host 长度：

- DCP/PCP 中现存的 host metadata 构造
- DSV4 compress
- MLA chunked prefill
- C8、NZ、sinks、encoder-decoder 等未进入 sink 的 fallback
- 通用非 padded speculative proposer

`optimistic_seq_lens_cpu` 本身不用删除。它完全由 scheduler CPU 数据生成，不是 D2H，可继续作为图档位和粗粒度 upper bound；只是不再为了 attention 把它修正成设备侧精确值。

### `num_accepted_tokens` 为什么还不能全删

K3 含 Mamba/GDN，因此 `need_accepted_tokens` 恒为真：

[model_runner_v1.py:3968](<redacted:local-path:94dff6371c93>:3968)

GDN 已经直接消费设备 Tensor，不需要 D2H：

[gdn_attn_builder.py:418](<redacted:local-path:883aae355e54>:418)

剩下的阻碍是 Mamba align：

1. postprocess 在 NPU 上计算 accepted count。
2. 异步拷回 CPU。
3. 下一轮在 [model_runner_v1.py:1340](<redacted:local-path:94dff6371c93>:1340) 等待。
4. CPU `preprocess_mamba()` 用它计算 state block 和 `accept_token_bias`：[patch_mamba_utils.py:317](<redacted:local-path:d5fd79f130ba>:317)
5. 随后又把结果 H2D 给 GDN/Mamba kernel：[model_runner_v1.py:2248](<redacted:local-path:94dff6371c93>:2248)

这是一条真正的 `NPU → CPU planning → NPU` 回路。要删除它，需要把以下内容一起设备化：

- request reorder 后的 accepted-count 重排
- `prev_state_idx/curr_state_idx`
- `accept_token_bias`
- Mamba state-copy metadata 生成
- state block 搬运判定

仅删除 event wait 或 CPU buffer 会重现之前的状态错位/脏值问题。

### 建议拆分

第一步可以安全落地：

- 清理 GQA/MLA sink builder 的 `.tolist()` 和 CPU-list-to-NPU 绕路。
- sink metadata 全部直接消费 `common_attn_metadata.seq_lens`、`query_start_loc`。
- 把 `_needs_seq_lens_cpu_sync` 改成 builder capability。
- K3 sink-only 路径停止执行 `_correct_optimistic_seq_lens_cpu()`。

第二步单独处理 Mamba：

- 将 Mamba align preprocess/state-copy planning 下沉到设备。
- 复用 GPU accepted count，删除 `num_accepted_tokens` D2H、下一轮 event wait 和重新 H2D。
- sampled token IDs 给 host scheduler 的 D2H仍需保留；这是调度输出契约，不属于 attention tiling。

因此最终判断是：K3 attention seqlen 相关 D2H 可以清零；K3 model runner 内所有 `num_accepted_tokens` D2H 暂时不能清零，Mamba 状态迁移设备化后才可以。当前没有修改代码。
