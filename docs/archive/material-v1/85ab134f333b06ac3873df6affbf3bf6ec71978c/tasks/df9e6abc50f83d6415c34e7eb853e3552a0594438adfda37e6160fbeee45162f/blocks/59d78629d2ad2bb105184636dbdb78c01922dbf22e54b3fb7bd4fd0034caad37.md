### 核心差异

| 层次 | cann-recipes-infer | 当前 VA | 影响 |
|---|---|---|---|
| Torch schema | `Tensor(a!) state -> Tensor` | 新 `recurrent_kda` 也是同样形式 | 两边 binding 语义基本正确 |
| State 存储 | K3 `recurrent_state` 直接申请 `float32 Tensor` | Mamba/KDA cache 从一整块 `int8` buffer 做跨 dtype `view` | VA 更容易被 reinplace 的 alias 检查拒绝 |
| KDA 执行 | CANNBot DSL，`initial_state`、`final_state` 指向同一 Tensor | ACLNN + 自定义 `EXEC_NPU_CMD` | recipes 的 KDA 实际没有经过它的 `EXEC_NPU_CMD_V1` |
| ACLNN 提交 | 其他算子用 `RunOpApiV2` | VA 是较老的 `OpCommand + SetCustomHandler + Run` | 值得升级，但发生在 FX 优化之后 |

外部 KDA 的 schema 和同址 state 实现在 [fused_recurrent_kda.py](https://gitcode.com/cann/cann-recipes-infer/blob/master/ops/cannbot_dsl/fused_recurrent_kda.py)，它的 recurrent state 是独立 `float32` 分配：[attention_data.py](https://gitcode.com/cann/cann-recipes-infer/blob/master/models/kimi_k3/models/modules/attention_data.py)。

VA 新路径其实已经做对了两件事：

- [`recurrent_kda` schema](<redacted:local-path:ec13566b382a>:2301) 把 `initial_state` 声明成 `Tensor(a!)`，而且不返回被修改的 state。
- CANN 层把同一个 `stateRef` 同时作为输入、输出，[OP_INPUT/OP_OUTPUT](<redacted:local-path:1fb0464c4762>:57)。

最大嫌疑是 cache 创建方式：

- V1：[model_runner_v1.py](<redacted:local-path:86d6937a1949>:4481)
- V2：[attn_utils.py](<redacted:local-path:56242e117f3e>:687)

两处都是：

```python
raw_int8_buffer[slice].view(state_dtype).view(state_shape)
```

npugraph_ex 会把 mutable op 包成 `auto_functionalized_v2`。如果 `_all_bases` 是图输入的 `view/detach`，而不是直接的 `placeholder/get_attr`，当前 `can_inplace()` 会保守拒绝，随后 `decompose_auto_functionalized` 物化为：

```text
clone(state_view)
mutable_op(cloned_state)
copy_(state_view, updated_clone)
```

最终 `clone/copy_` 都可能在 Profiling 中显示成 TensorMove。TorchAir 文档也明确说明 `input_inplace_pass` 就是用来逆转这类 “out-of-place + copy_” 的；但它仍受 alias/view 安全检查约束。[TorchAir inplace pass 文档](https://gitcode.com/Ascend/torchair/blob/26.0.0/docs/zh/npugraph_ex/basic/inplace_pass.md)

另外，如果实际 FX 图里还是：

```text
npu_recurrent_gated_delta_rule_functional
getitem(new_state)
copy_(state, new_state)
```

那是另一条 legacy functionalization 路径。此时即使 state 是直接 Tensor，也可能因为 functional/inplace pair 没注册到 npugraph_ex 而留下写回。当前新 `recurrent_kda` 路径应优先替代它。

### 建议的优化顺序

1. **先确认 TensorMove 来源**

   在最终 FX dump 搜：

   ```text
   recurrent_kda
   npu_recurrent_gated_delta_rule_functional
   auto_functionalized_v2
   _all_bases
   clone
   copy_
   ```

   并检查 `debug.log` 中：

   ```text
   can_inplace return False
   missed reinplacing opportunities
   cannot find an inplace op
   ```

2. **优先修 cache mutable base**

   对 K3 decode，把 `recurrent_state` 改成直接申请的 `float32/bfloat16 Tensor`，不要让 mutable op 接收统一 `int8` backing storage 的 dtype view。因为 conv state 和 recurrent state dtype 不同，长期方向应是分开物理分配，同时补齐 cache 大小核算、KV transfer 和 sleep/wake 生命周期。

   如果必须保留统一 byte buffer，只改 Torch binding 或强行放宽 npugraph_ex 的 view reinplace 检查不够安全；还需要证明所有同 storage sibling view 在该 op 前后没有冲突读取。

3. **确保使用现代 functionalization**

   保留当前形式：

   ```text
   recurrent_kda(... Tensor(a!) state ...) -> Tensor
   ```

   不返回被修改的 state，并提供正确 Meta。当前 [`recurrent_kda_meta`](<redacted:local-path:c9e99aa83b14>:626) 已符合这个方向。

   若必须兼容旧 GDR，可临时注册：

   ```text
   functional_op = npu_recurrent_gated_delta_rule_functional
   inplace_op    = npu_recurrent_gated_delta_rule
   mutated_arg   = [3]
   ```

   但这是版本耦合的过渡方案，长期仍应走 `auto_functionalized_v2`。

4. **显式保证 `input_inplace_pass=True`**

   VA 当前只显式设置了 `inplace_pass=False`，[compiler_interface.py](<redacted:local-path:180064bf2cf4>:110)。在 TorchAir 26.0 中，`inplace_pass` 和 `input_inplace_pass` 是两个独立开关，因此这不是当前首要根因；不过建议根据 TorchAir 版本显式设置后者，避免旧版本配置映射差异。

5. **EXEC_NPU_CMD 单独升级**

   VA 当前宏仍是旧的 [`OpCommand::Run()` 路径](<redacted:local-path:cf75b26a7c70>:687)。建议按官方 op-plugin 的实现对齐：

   - `RunOpApiV2`
   - task queue V1/V2 分流
   - stream resource 注册
   - `unsafe_empty_workspace`
   - deterministic、executor cache 和正确的 workspace 生命周期

   [官方 op-plugin 实现](https://gitee.com/ascend/op-plugin/blob/master/op_plugin/utils/op_api_common.h)和[官方 C++ extension 示例](https://gitcode.com/Ascend/op-plugin/blob/master/examples/cpp_extension/README.md)都使用 `RunOpApiV2`。

   不建议直接复制 recipes 的 `ops_common.h`：当前代码里外层 `workspace_tensor` 又被 `auto workspace_tensor` shadow，存在可疑的 workspace 生命周期问题。

### 验收标准

- `auto_functionalized_v2._all_bases` 直接指向 state placeholder，不是 `view/detach`。
- `after_reinplace_input_mutated_ops`、`after_decompose_auto_functionalized` 中没有对应 KDA state 的 `clone + copy_`。

- 多步 decode、MTP accepted-token、不同 state slot 的状态更新保持正确。
- 将“cache/reinplace 修复”和“EXEC_NPU_CMD 升级”分别 A/B，避免误归因。

### assistant:final_answer
对，单独把 `output[...] = self.wo_b(...)` 改成 `output = self.wo_b(...)` 肯定会精度炸，而且本质不是数值误差，是数据流断了：

- 外层先分配一块 `torch.empty` 作为 `output`：[dsa.py](<redacted:local-path:16539b7c8a93>:160)
- `dsa_forward` 的 ABI 是 `mutates_args=["output"]`、返回 `None`：[dsa.py](<redacted:local-path:16539b7c8a93>:171)
- `_forward_o_proj()` 的返回值又被直接忽略：[dsa_v1.py](<redacted:local-path:140757172e15>:1236)
- 最终返回的仍是最开始那块 `output_padded`：[dsa_v1.py](<redacted:local-path:140757172e15>:1240)

所以：

```python
output[...] = self.wo_b(x)  # 写进调用者那块 buffer，正确
```

换成：

```python
output = self.wo_b(x)       # 只重绑定局部 Python 变量
```

调用者最后读到的是未写入的 `torch.empty`。这条路当然寄。

但这也进一步证明了 TensorMove 的来源：当前 mutation ABI 强制要求把 `wo_b` 新生成的 MatMul 输出复制进预分配 `output`，因此 profiler 才是：

```text
MatMul → TensorMove(copy_) → HcPost
```

真正可行的方向只剩两个：

1. **完整改造 functional-return ABI**  
   从 `_forward_o_proj → impl.forward → dsa_forward → AscendDeepseekSparseAttention.forward` 全链返回 MatMul Tensor，而不是只改一行。若此前已经这样完整改过仍有精度问题，才说明 ACLGraph replay 对返回 Tensor 的地址/生命周期有约束。

2. **更稳妥：保留 mutation ABI，让 MatMul 直接写 `output`**  
   即给 `wo_b` 增加 out-variant。非量化 MatMul 本身有 `matmul.out`，可以做一个 DSV4 专用的 `unquantized_gemm_out(..., output)`；但量化路径的公开 `npu_quant_matmul` 只有 functional 返回值，可能需要 C++ torch binding 直接把预分配 `output` 传给 ACLNN。

所以现在最关键的是先锁定当时 profiler 对应的 `wo_b.quant_method`。如果确实是普通 MatMul，做一个非常窄的 `wo_b out` 路径，既保留现有精度语义，又能真正消掉这个 TensorMove，风险比重构整个 DSA custom-op ABI小得多。
