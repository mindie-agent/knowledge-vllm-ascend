## 6. 把框架问题与实验问题强制分流

这是你当前最需要的规则：

```text
出现故障时先分类：

A. 实验配置错误：
最小修正后继续。

B. 当前环境漂移：
恢复已知正确环境后继续，不做通用兼容。

C. 独立框架缺陷：
保存首个 traceback 和最小复现，记录为后续任务；
除非它阻塞全部实验，否则不要在当前任务修复。
```

不要让同一个 Agent 任务同时无限承担：

> 服务 bring-up + 框架维修 + 通用兼容 + 性能实验 + PR 清理

这些目标天然会互相吞时间。

## 相比之前，我现在有三个新判断

### 1. 不要只限制时间，要限制“无决策价值的动作”

之前说“preflight 最多 15 分钟”“最多一个 patch”，有用但比较机械。

更好的标准是：

> **每一次检查、修改和实验，都必须关闭一个明确的决策问题。**

例如：

```text
问题：0.26 和 0.27 的 acceptance 差异是否来自 QuaRot 加载路径？

正向结果：加载 tensor/hash/path 不同 → 继续查加载实现。
负向结果：完全相同 → 停止研究加载，转向运行时 metadata。
```

如果正反两种结果都不会改变下一步，那么这个检查基本没有价值。

所以进度指标应该从：

- 完成了多少检查；
- 修了多少 runtime 问题；
- 服务走到哪个初始化阶段；

改成：

- **计划关闭几个问题；**
- **实际关闭了几个；**
- **完成了几组有效请求；**
- **还有哪个分叉没有证据。**

### 2. 门禁不是越少越好，而是只能有两类

允许：

- **安全门禁**：防止破坏他人服务、错误清理进程、占错机器。
- **实验有效性门禁**：防止版本、权重、拓扑或参数错误导致结果不可比较。

默认不允许：

- 为了“以后更稳”的兼容门禁；
- 尚未发生错误的 import/operator/config 全量检查；
- 自动 fallback、自动修复、自动重试；
- 为单次实验建设通用 runner；
- 用源码静态检查冒充 NPU/runtime 结果。

每个新增门禁都要求 Agent 回答：

```text
1. 它防止哪个具体的错误结论或破坏性动作？
2. 哪条已经观察到的证据触发了它？
3. 它是否会改变被测运行路径？
4. 如果去掉它，当前实验是否仍然可以安全执行？
```

答不上第 1、2 条，通常就不该做。

而且现在还要增加一个新要求：**检查门禁的失败顺序。**

近期经验显示，前面的 topology assertion 可能先失败，导致后面的 capability gate 根本没有执行。此时继续增加检查只会让错误更早、更绕，并不更接近真因。

### 3. 实验和框架修复必须成为两条独立泳道

这是最重要的新版本：

#### 实验泳道

- 冻结 commit、容器、权重、参数和启动脚本；
- 先跑已知 baseline；
- 再做单变量 A/B；
- 不修改产品代码；
- 目标是得到请求级结果和区分信号。

#### 修复泳道

只有 baseline 被真实 traceback 阻塞后才能进入：

- 保存第一个真实错误；
- 证明它确实阻塞目标实验；
- 做一个最小修复；
- 立即重跑完全相同的实验行；
- 不顺手补通用兼容和未来 fallback。

如果修复需要改多个模块、增加版本分支或设计启动框架，就应该升级成独立任务，而不是吞掉实验任务。

## 最后的新总结

之前的原则是：

> 少写防御代码，尽快开始实验。

现在更准确的是：

> **让 Agent 围绕“关闭决策问题”工作；安全和有效性检查是成本，框架修复是独立泳道，只有完成真实请求并产生区分信号才算进度。**

“少做检查”仍然可能让 Agent 草率；“每个动作必须有决策价值”才是真正稳定的约束。
