## 1. 历史 `all!` 根因：旧三平面 compact GQA stride 碰撞

旧布局下 raw tensor 是：

```text
P0 conv | P1 recurrent / MLA-NoPE | P2 MLA-RoPE
```

GQA 仍从 raw tensor 尾部取两个 compact plane。以当时 `num_blocks=5689` 为例：

```text
old GQA-K base = (488448 - 2 * 49152) * 5689
old GQA block 1969
  == P1 base + target MLA block 5224 * 393216
```

即 draft GQA group 5/block 1969 与 target MLA group 0/block 5224 同地址；target 的 128-token kernel page 是 `5224 * 3 = 15672`。历史 full-chain dump 已把 corruption 定位到 target attention cache、sampler 之前；后续 R11 只读重放也看到 group 0 的 page 5225–5227 出现大面积 nonfinite。

现有四平面：

```text
P0 conv
P1 recurrent / MLA-NoPE
P2 MLA-RoPE / GQA-K
P3 GQA-V
```

让 GQA K/V 都按同一个 scheduler physical block ID 和相同 plane stride 索引，旧 compact-stride 公式不再成立。相关实现 seam：

- `vllm_ascend/core/kv_cache_interface.py:25-134`
- `vllm_ascend/patch/platform/patch_kv_cache_utils.py:27-58`
- `vllm_ascend/worker/model_runner_v1.py:4027-4031`
- `vllm_ascend/worker/model_runner_v1.py:4229-4261`

历史反证也排除了“单纯 block-table H2D async”是旧根因：`3a2cae19b` 把 block-table copy 改为 blocking 后，clean c1 仍是 `" He"`，经过 c1/c2 压力后同一路径仍变成 `"!"、"!"`。

当前四平面生产验收必须先复现同一历史压力序列，不应先叠其他修复：

1. clean c1 一 token；
2. c1/c2 128K×1024；
3. 相同 129792-token prefix 连续三次一 token；
4. c2 再跑两到三轮 128K×1024。

每轮同时要求 first-token/hash、输出质量和 acceptance；不能只看 acceptance，因为 draft 和 target 同时损坏时，`!` 也可能显示 acceptance 1.0。

建议补一条 allocator 合同单测：同一 shared raw tensor 中，共享 P1/P2 的不同 KV groups，其同时存活 physical block ID 不得相交；覆盖 prefix hit、finished row replacement、block reuse。现有 pointer-offset UT 只证明 view 几何正确，还没证明生命周期内 block ownership。

## 2. Active candidate A：`e32ece64a` metadata lifetime

当前代码在 input-prep 中只收集 pinned CPU pointer tables：

- `patch_mamba_utils.py:241-279`

实际 H2D 与 pointer kernel 延迟到 KV load 后：

- `model_runner_v1.py:2060-2062`
- core `mamba_utils.py:963-971`

`prepare_inputs_event` 在 input-prep 结束时已经 record；后置的三次 H2D 不在 event 保护范围内。async scheduling 下一轮可在前一次 H2D 尚未读完时覆写 `src_ptrs/dst_ptrs/sizes`。

严格激活条件：

```text
prefix cache enabled
mamba_cache_mode == align
async scheduling
copy_bufs.offset > 0
下一轮 CPU prep 快于前一轮 metadata H2D 完成
```

`copy_bufs.offset > 0` 只在：

```python
prev_state_idx != -1 and prev_state_idx != curr_state_idx
```

所以：

- fresh、总长不超过 384：不可达；
- 896 hit：cached=384，`prev=0 -> curr=2`，可达；
- 8576 hit：cached=8064，`prev=20 -> curr=22`，可达；
- 129792 hit：cached=129408，`prev=336 -> curr=337`，可达；
- prefix-on miss：首 chunk 不触发，后续跨 384 边界触发；
- prefix-off 通常把 Mamba block 拉到 max length，基本不可达。

历史证据不支持它是旧 `all!` / 二轮下降的充分根因：

- 等价修复 `2a827f021`：c2 r1 acceptance `0.5802469`，r2 降至 `0.3459524`，并出现 `literal_none`；
- late blocking H2D `90a097d4f`：首轮 `0.4576122`；
- raw state-copy sync `656c58db8`：首轮 `0.4560327`；
- blocking H2D `da3079b7a`：首轮 `0.6026899`；
- pure-head baseline：r1 `0.4576122`，r2/r3 都稳定降到完全相同的 `0.2907861` 和相同输出 hash；
- `2a827f021` 的 896 hit 一 token连续三轮输出/hash 稳定。

因此 `e32ece64a` 是真实 latent correctness fix，值得保留，但不能叫作历史精度根因修复。

最小生产 seam 就是移植 `e32ece64a`：

1. 在 `preprocess_mamba` 的现有 input-prep event scope 内只 stage 三张 metadata 表；
2. KV load 后的 `do_mamba_copy_block` 只读已经 stage 好的 GPU tables；
3. state copy 位置、async scheduling、task queue 都不变。

已有 UT 已覆盖：

- offset>0 时 preprocess stage 三张表；
- state copy 不重复 H2D；
- preprocess 只 stage、不提前 state copy。

建议再补两轮复用 UT：第一次 H2D 尚未完成时覆写 pinned CPU view，断言第二次覆写必须等 input-prep event，而 pointer kernel 仍消费第一次 GPU snapshot。

最小远端 A/B：当前四平面 baseline vs 仅加 `e32ece64a`，固定 prompt/hash/DP route/history；896、8576、128K 的 hit 与 prefix-on unique miss 都至少三轮，记录 `copy_bufs.offset` 次数和 metadata hash，不先做大 tensor dump。

## 3. Active candidate B：Mamba `global_stream` event 等得太晚

这是当前源码里更明确的 request-lifecycle race。

上一轮：

- sampling event：`model_runner_v1.py:2187-2192`
- global stream 等 sampling event 后执行 Mamba postprocess：`2310-2317`
- fused postprocess 读取生命周期内持久的 GPU block tables，并把 accepted counts async D2H：
  - core `mamba_utils.py:719-733`
  - core `mamba_utils.py:1103-1156`
  - core `gpu_model_runner.py:1545-1590`

下一轮当前顺序却是：

1. `_update_states()`：`model_runner_v1.py:1778-1801`
2. 这里会 remove/add/condense request rows；
3. `block_table.commit_block_table()`：`852-854`
4. 直到 `_prepare_inputs` 后段才 `num_accepted_tokens_event.synchronize()`：`1049-1072`

于是存在两条 race：

- 上轮 accepted-count D2H 正写 `input_batch.num_accepted_tokens_cpu_tensor`，下一轮 `_update_states/condense/add` 已在 swap 或复用同一 CPU 行；
- 上轮 global fused kernel 正读 persistent GPU block table，下一轮 main stream 已 commit 新表内容。

严格激活条件：

```text
hybrid + speculative decode
上一轮执行过 _update_states_after_model_execute
下一轮在 global postprocess 完成前进入 input prep
且至少发生以下之一：
  - finished/remove/condense/add/request row reuse
  - preempt/resume
  - 上轮 postprocess 会读取的 row/column 对应 block-table cell 被改写
```

仅追加一个未来不被上轮读取的 block-table column通常无害；同一 request、同一 row、旧 cells 完全不变也通常无害。最强场景正是 c2/c4 长输出结束后的第二波请求替换，以及 prefix pressure 后 physical blocks 重用。

这不是旧 `all!` 的已证根因，但四平面消掉 backing collision 后，它仍足以造成二轮 acceptance 波动或 Mamba state 错位。历史 blocking block-table A/B 没排除它，因为 blocking H2D 不是对 prior `global_stream` event 的依赖。

### 最小正确 A/B seam

不能只把 `event.synchronize()` 前移一行。

原因：若先 wait，accepted counts 已按旧 row 完成 D2H；随后 `_update_states/condense()` 会把 `num_accepted_tokens_cpu` 随 request row 一起 swap。现有 `prev_positions` 分支又假定 D2H 在 condense 后按旧 row 覆盖，并再次按旧索引 gather；单纯前移会二次重排。

最小正确语义 patch：

1. 增加 `accepted_tokens_pending` 状态；
2. 在下一轮 `execute_model`、`_update_states` 之前 synchronize pending event；
3. 之后让 `_update_states/condense/add` 自然把已完成的 accepted counts 随 request 行移动；
4. `_prepare_inputs` 上传 accepted counts 时直接使用 current-row CPU values，跳过 `prev_positions` 的旧-row gather；
5. 上轮 global postprocess enqueue/record event 后置 pending；
6. event 必须在 `_update_states` 和 `block_table.commit_block_table` 两者之前完成。

性能优化版以后可以改成独立 immutable previous-row accepted-count snapshot，再保留 `prev_positions` gather；但 block-table commit 前仍必须有 event dependency，除非 fused postprocess 也改读 per-step block-table snapshot。

必要 UT：

- mock event，断言 synchronize 先于 `_update_states` 和 `commit_block_table`；
- old rows `[A,B]`，accepted `[2,6]`，下一轮 remove A、condense B、add C，断言 current rows 是 `B=6,C=1`；
- 断言早 wait 路径不再执行 `prev_positions` 二次 gather；
- stable `[A,B]` 无 row 变化；
- event 无 pending 的首轮不得误等；
- 模拟 global postprocess pending 时，commit 不可先发生。
