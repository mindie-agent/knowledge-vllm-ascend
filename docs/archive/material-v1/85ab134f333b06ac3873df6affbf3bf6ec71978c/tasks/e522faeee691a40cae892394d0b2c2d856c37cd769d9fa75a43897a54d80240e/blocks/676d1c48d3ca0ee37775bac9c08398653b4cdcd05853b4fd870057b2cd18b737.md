### 3. zero / Prefix replay / CoW 的实际可达性

**Zeroer 当前完全不在 DSpark 路径。**

`vllm_ascend/worker/worker.py:892-923` 只有同时满足：

- `needs_kv_cache_zeroing`
- speculative method 为 `eagle3`
- speculative tokens 大于 1

才创建 `AscendKVBlockZeroer`。现有 launcher 明确为 `method=dspark`；仓内没有另一条 A3 DSpark 构造路径。scheduler 虽会下发 `new_block_ids_to_zero`，但 core `_zero_block_ids()` 因没有 `_kv_block_zeroer` 属性而直接 no-op。因此 zero kernel 不是当前第二 step 卡死前的前序 NPU 操作。

若未来放开 gate，现 zeroer 会在 MLA P1=`393216` 和 P2=`49152` 页宽之间触发 `Non-uniform page sizes` 断言；这是潜在兼容缺口，不是当前故障。

**当前 Prefix Cache hit 只复用 block ID，不执行 worker CoW copy。**

CoW 只在 `num_local_computed_tokens % manager.block_size != 0` 的 partial hit 发生。当前：

- 20 个 group 全部是 384；
- launcher 未设置 `--prefix-match-unit`；
- 默认 hash unit 为 GCD，即 384；
- 因而 partial-hit 条件永远为假。

DSpark 被 `use_eagle()` 视为 Eagle，attention 命中会再 drop 一个 384 page，所以这些用例的实际 replay 长度为：

- 384 / 385 token 边界：0
- 896 用例，共享 768：384
- 8576 用例，共享 8448：8064
- 128K 用例，共享 129792：129408

全部仍为 384 对齐，`kv_cache_block_copies` 为空。Prefix hit/replay 通过已有 block IDs 重新填 block table，各消费者自然落到对应 plane，没有 plane-major 重排。

**但 CoW helper 是确定的潜在 plane-major bug。**

Core `vllm/v1/worker/utils.py:541-577`：

- 按整个 storage pointer 去重；
- 把完整 backing storage `view(num_blocks,-1)`；
- 明确假设 backing 为 block-major。

当前实际 backing 是 `[P0 all blocks][P1 all blocks][P2 all blocks][P3 all blocks]` 的 plane-major SoA。若配置 `prefix_match_unit<384`，src→dst 会跨 plane/跨 block 错拷。

最小修复 seam 是该 core helper：以 `(storage_ptr, storage_offset_bytes, contiguous_numel_bytes)` 去重逻辑 lane，对每个精确 view/range 单独 reshape 成 `(num_blocks,-1)` 后拷贝。这样 P1、P2 的别名只各拷一次，最终每个 raw storage 正好处理 P0/P1/P2/P3 四段。

Simple CPU offload 也按整个 storage pointer 去重，只会注册遇到的首个 plane；当前 launcher 未启用 offload，所以同样 dormant。MRV1 没有可达的 backend `swap_blocks` 调用。

### 4. 能堵住下一 step 首个 KDA all-gather 的具体违约点

当前树中唯一明确、可产生“前一步 NPU 流异常，下一步在首个 collective 暴露”的活跃契约违约，是缺失的 Mamba copy metadata 生命周期修复：

- `patch_mamba_utils.py:241-281` 在 `synchronize_input_prep` 保护区内填写复用的 pinned `src_ptrs/dst_ptrs/sizes`，但不做 H2D。
- 保护区退出时 prep event 已在流上 record。
- `model_runner_v1.py:2061` 在保护区外才调用 `do_mamba_copy_block`。
- core `mamba_utils.py:963-971` 此时才对三张复用 pinned 表执行 nonblocking H2D，再启动 raw pointer batch memcpy。
- 下一 step 只等待较早记录的 prep event，可能在上一轮 H2D 尚未读完时覆写 pinned 表，形成错误指针、越界状态拷贝或 stream fault。
- KDA 的 `maybe_all_gather_and_maybe_unpad` 是模型 forward 的第一个 NPU 操作，因此很容易成为下一步首个可见阻塞点。

历史提交 `e32ece64a` 正好是最小修复：在 prep event 范围内仅 stage 三张 metadata 表，KV transfer 后仍只执行实际 state copy。

但这个候选有严格激活条件：`copy_bufs.offset>0`。

- Prefix replay、384 边界迁移、chunked long prompt、8576/128K 都会触发。
- 短 prompt、只在同一 384 block 内进行的 c64 第二 step 通常 `prev_state_idx==curr_state_idx`、`offset=0`，可直接排除此因。
- 对这种 offset=0 的短 c64，静态审计没有发现首个 KDA all-gather 前可达的四平面 zero/CoW/raw-copy 操作；应继续定位上一 step 的 forward、sampling、DP collective 或异步输出流，而不能把阻塞归因于四平面 copy。

可证伪实验：

1. 每 rank、每 step 只记录 `prev_state_idx/curr_state_idx/copy_bufs.offset` 和 prep-event generation；失败 step 若 offset=0，立即否定 metadata-copy 假设。
2. 对 offset>0 的同一 prompt、同一 block-ID 序列做当前树与 `e32ece64a` 精确 A/B；再用 `--no-async-scheduling` 作反向验证。
3. 同步仅用于定位：分别在 metadata H2D 后、state-copy 后插入一次 rank-scoped sync。最终修复应采用 event-protected staging，不保留全局同步。

### 5. 最小测试缺口

当前新增测试只证明 page 数学、group 数、data_ptr 和 contiguity，仍缺：

- 精确 shape、stride、storage_offset、storage pointer 断言。
- 四 lane sentinel：src block→dst block 后四 lane 正确、所有非 dst block 原样；现 core helper应失败。
- 默认 384/Eagle 的 385、896、8576、128K scheduler replay，并断言 `kv_cache_block_copies is None`。
- `prefix_match_unit=128` 的 partial-hit CoW 正例。
- DSpark 不初始化 zeroer、eagle3 初始化 zeroer的 gate 测试。
- Mamba metadata H2D 必须发生在 prep-event 范围内的时序测试。
- Prefix miss、full hit、partial hit 的输出/logit hash一致性。
- Offload/swap 支持若声明启用，则需单独覆盖四平面；否则应明确禁止该组合。

总体判断：当前四平面 forward 与默认 384-aligned Prefix Cache replay 静态闭合；短 c64 没有活跃的 plane-major auxiliary-copy 违约。需要优先用 `copy_bufs.offset` 判定是否纳入 `e32ece64a`；CoW helper 则是确定但当前默认验收矩阵不触发的通用性缺口。
