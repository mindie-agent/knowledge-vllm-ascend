只读 review 结论：`aebfbe7f5` 原提交不应直接部署，有两个会导致假阴性的高优先级问题。

1. P0：仅 global rank 0 不足以排除故障

KDA 的 96 heads 在 TP16 上分片；只 dump TP0 看不到其余 15 个 shard。并且只有 TP0 在 target forward 与 drafter collective 之间执行 synchronize、D2H 和哈希，会引入 TP 内非对称停顿。

建议：

- gate 改为 external-DP-aware 的 `data_parallel_index == 0`，覆盖 DP0 的 TP0–TP15。
- 文件名加入 `global_rank`。
- verifier 要求 global rank 0–15 各一份，并按 `(global_rank, layer_name, state/cache_kind)` 比较 warm/hit，不能要求不同 TP rank 的 KDA hash 相同。

每 rank 缓存 clone 约 72 MiB；加 512-token materialized aux 后估计峰值约 0.1–0.15 GiB/NPU。当前 launcher `--gpu-memory-utilization 0.80`，安全余量充足。主机一次总 D2H 约 1–2 GiB，也可控。

2. P0：只捕获了第一个 GDN group 的 metadata

原代码在 `capture_cached_source_attention_metadata()` 中用 `next(...)` 取第一个 GDN metadata。实际 `_build_attention_metadata()` 会针对 g6–g19 共 14 个 Mamba group，使用各自 block table 构造不同 metadata；这些 group 的物理 block IDs 本来就不同。

因此当前 manifest 即使 `gdn_metadata > 0`，也只能代表第一组，无法排除另外 13 组、其余 KDA 层的 state index、has-initial 或 query-start 错误。

最小修正：

- 遍历所有 metadata entry，按对象 ID 去重，但保留对应的 group ID 和 layer names。
- 每个 Mamba group 分别记录六个字段。
- 完整性要求覆盖 14 个 Mamba group、69 个 KDA layer，而不是简单判断 count > 0。
- 若有 ubatch，额外记录 ubatch ID。

其他重要问题：

- `contiguous().clone()` 会抹掉原 view 的 stride、storage offset 和基址，不能据此排除四平面 view 错误。应记录原 tensor 的 shape、stride、storage offset、storage base、selected data pointer 和 relative byte offset。
- MLA 越界 slice 会静默生成短/空 tensor，但原来的 record count 仍可能标记 complete，空 tensor 还会 `all_finite=true`。必须校验 block ID、page 范围、dim0 和预期 nbytes；Mamba 也应校验 column 数、非负 block ID 及容量。
- session 没有跨 iteration 的生命周期标识。若 aux 路径没在同一次执行到达，会长期保留约 72 MiB，并可能把后续 iteration 的 logits/aux 拼到旧 cache snapshot 上。建议绑定 execute-step ID，下一步到来时将未完成 session 判为失败并清理。
- `required_complete` 还应校验唯一 layer/stage/kind 集合，不能只看记录总数。
- `target_logits_indices` 不应归入 `gdn_metadata` category，否则会污染严格的 GDN 完整性计数。
- all-rank 模式下 `_rank_metadata()` 不应静默退化为 `global_rank=None`，否则多个 rank 会写同一个 `unknown` 文件并导致 worker 崩溃；启用 DFX 时应 fail closed。

首次 prefill 的 logits/aux 时点在当前受控实验下是正确的：

- no-spec prefill 时，`logits_indices=query_start_loc[1:]-1`，logits 每个 active request 一行且顺序与 `req_ids` 一致，因此 `logits[batch_index]` 正确。
- aux 在同一 no-spec 分支、真正 `_propose` 前，按 flat scheduled-token offset 截取，覆盖首次 prefill。
- 建议 manifest 继续记录 logits indices、request count、slice start/end，并断言总 offset 等于 materialized aux 行数。

默认关闭时没有 clone、同步、D2H 或文件 I/O，语义上无影响；只有每步几个 Python no-op hook 的微小开销。
