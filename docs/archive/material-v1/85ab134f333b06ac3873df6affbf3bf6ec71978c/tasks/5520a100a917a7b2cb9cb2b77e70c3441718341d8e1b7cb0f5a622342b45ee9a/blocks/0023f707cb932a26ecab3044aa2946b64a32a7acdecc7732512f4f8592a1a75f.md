### 为什么 zeroer 是首嫌

R8 卡死批次中，四个 DP 的 target collective ordinal、caller、返回向量和 padding 完全一致，最终都是 `[64,48,48,16] → pad 64`。真正明显的不对称发生在 forward 前：

- DP3 是 16 个全新请求，要一次清零 16 个新 block。
- DP0/1/2 主要是历史请求，DP0 只清零 1 个新 block。
- 随后四个 DP 都打印到 `before_forward`，但首次需要读取设备动态结果的 MoE `repeat_interleave(...).item()` 不再返回。

当前 [zero_block_ids](<<redacted:local-path:b8dd889167fe>/vllm-ascend-v0.26.0rc-dspark-mla-linear-ci/vllm_ascend/worker/utils.py:167>) 每次创建函数局部 pinned CPU tensor，再 nonblocking H2D 到局部 device tensor，发出 Triton zero kernel 后立即返回。它没有：

- 持久 pinned/device buffer owner；
- 与并发 batch 数对应的 ring；
- completion event；
- block-id 边界检查。

而精确 vLLM 实现明确使用 [`max_concurrency` 个环形 buffer](<<redacted:local-path:b8dd889167fe>/vllm-core-v0.26.0/vllm/v1/worker/utils.py:194>)，注释直接说明：nonblocking H2D 的 pinned source 在 batch 完成前不能被复用；上游 caller 还会传入 [`max_concurrent_batches`](<<redacted:local-path:b8dd889167fe>/vllm-core-v0.26.0/vllm/v1/worker/gpu_model_runner.py:1131>)。Ascend 当前 caller [没有传这个并发参数](<<redacted:local-path:b8dd889167fe>/vllm-ascend-v0.26.0rc-dspark-mla-linear-ci/vllm_ascend/worker/model_runner_v1.py:5358>)。

这还不能直接宣布是 UAF——NPU allocator 可能会正确延长局部 tensor 的流生命周期。但它确实违反了上游明确的异步 ownership 契约，而且与“只有历史后 c64、DP3 清零工作明显更多、host 已进入 forward、设备同步点才暴露卡死”的现场最吻合。

最符合现象的假设链是：

```text
DP3 zero H2D/kernel enqueue
→ host 提前走到 target forward
→ MoE repeat_interleave 首次强制同步设备结果
→ 观察到前序 stream 未闭合
→ 其他 EP rank 一起等待
→ sample_tokens RPC 超时
```

GQA packed 地址和 page stride 的静态算术目前是自洽的，没有找到确定 OOB；风险更集中在 zeroer 的异步执行契约，而不是 packing 公式本身。

### GPU-only Mamba align 为什么排第二

新增门控位于 [_use_gpu_mamba_align](<<redacted:local-path:b8dd889167fe>/vllm-ascend-v0.26.0rc-dspark-mla-linear-ci/vllm_ascend/worker/model_runner_v1.py:577>)，替换 legacy CPU/event 路径的入口位于 [execute_model 的 align preprocess](<<redacted:local-path:b8dd889167fe>/vllm-ascend-v0.26.0rc-dspark-mla-linear-ci/vllm_ascend/worker/model_runner_v1.py:2283>)，包含：

- GPU batch-row remap；
- GPU precopy；
- accepted-token metadata H2D；
- fused Triton postprocess；
- 绕过原来的 `sampling_done_event/global_stream.wait_event`。

相关日志中的 `after_mamba_preprocess`、`after_align_copy` 只能证明 host 已完成 enqueue，不能证明 NPU kernel 已完成。

但 R8 的实际批次削弱了它：

- DP3 全是 fresh request，`src_col=-1`，precopy 应该 fast-exit。
- DP0/1/2 的 cached row 仍在约 token 1，没有跨越 384-token Mamba block 边界，实际 state copy 同样应很少或不发生。
- 所以它仍是高风险异步路径，但比“DP3 确实清零 16 个 block”的 zeroer 证据弱。

另外，R2 已经会卡；R3 后来把 postprocess 调回 default stream，不可能是首次引入点。当前环境使用默认 SD conv layout，没有设置 `VLLM_SSM_CONV_STATE_LAYOUT=DS`，因此不能拿上游的 DS-layout 禁用断言作为这次的直接证据。
