### FIA 的 CPU seq_lens 同步

关键结论：SGLang NPU 当前没有真正消除这个同步，而是把它集中到了每轮 forward 入口，避免每层 FIA/builder 各做一次 D2H。

链路是：

```text
target verify 得到 new_seq_lens（NPU）
    ↓ FutureMap.publish
下一轮 resolve_seq_lens_cpu
    ↓ batch.seq_lens.cpu()，阻塞式 D2H
ScheduleBatch.seq_lens_cpu
    ↓ draft: + gamma；target verify: + verify width
Ascend metadata
    ↓ CPU tensor.tolist()
FIA actual_seq_lengths_kv
```

具体表现：

- `AscendAttnBackend` 默认 `needs_cpu_seq_lens=True`。
- DSpark 同时注册 target/draft backend，只要一个 backend 需要 CPU lens，FutureMap 就保留 CPU mirror。
- 在 NPU 上，CUDA 专用的 pinned buffer/private D2H stream 分支不会启用，因此 [resolve_seq_lens_cpu]([REDACTED_SECRET].[REDACTED_SECRET].py:405) 实际走同步的 `batch.seq_lens.cpu()`。
- draft metadata 直接在 CPU 上执行 `batch.seq_lens_cpu + gamma`，见 [dspark_draft.py]([REDACTED_SECRET].[REDACTED_SECRET].py:387)。
- 后续 FIA 中的 `.cpu().tolist()` 源 tensor 已经在 CPU，所以不会再次触发 NPU 同步。

所以它是“每轮集中同步一次”，不是“完全无同步”。

### 搬运建议

我的判断是：

- SGLang 的 KV 架构值得搬：共享逻辑 allocator/slot，draft 使用独立物理 KV pool。
- SGLang 的 NPU seq_lens 同步方案不值得原样搬，它比我们当前的 side-stream accepted-count 重建更粗。
- metadata 控制结构可以借鉴：按 `ForwardMode` 明确区分 draft、target verify、decode，统一生成一次 forward plan。
- 不建议继续让 proposer 原地修改 `CommonAttentionMetadata`。应定义一份明确的 `DSparkForwardPlan`，同时携带：
  - device exact seq_lens；
  - CPU exact seq_lens；
  - host-ready event/generation；
  - target/draft cache locations；
  - query width、verify width 和 accepted count。

然后要求 block-table 截取和 FIA `actual_seq_lengths_kv` 必须消费同一份 CPU snapshot，并在 DSpark 路径禁止 builder 的 `seq_lens.to("cpu")` fallback。

因此最终结论仍然是：整套 SGLang 源码不能直接搬——它是 GQA draft，我们当前是 MLA draft，而且 scheduler、graph、allocator API 不同；但“独立 draft 物理 KV pool + 共享逻辑 slot”可以搬。FIA seq_lens 部分应保留我们现在的窄 side-copy 思路，再把 metadata builder 收敛成一个显式 plan。
