结论：没有确认的 P0；在合法 K3 输入契约下，没有 correctness P1 blocker。当前主要问题是 3 个 P1 性能/流水设计问题。

- P1-PERF：核间负载严重不均衡。[dequant_situ_quant.h:99](<redacted:local-path:f23912cff6c8>:99) 每个 expert 都重新从 block 0 切分。真实 EP64 下本地 14 个 expert，若 decode 时各有 1 row，会变成 core0 处理 14 行、其余核空闲。
  - 最小修复：先按全局 `[0, rowLen)` 给每个 core 划连续区间，再和各 expert 的 `[groupOffset, groupEnd)` 求交；不要逐 expert 重置 block 分工。

- P1-PERF：当前不是真正的 MTE2/V/MTE3 流水。[dequant_situ_quant.h:65](<redacted:local-path:f23912cff6c8>:65) 的队列都是 depth=1，[dequant_situ_quant.h:116](<redacted:local-path:f23912cff6c8>:116) 每行严格 `CopyIn → Compute → CopyOut`。对照成熟实现，[dequant_swiglu_quant_dynamic_performance.hpp:233](<redacted:local-path:944b8c5cc212>:233) 有明确 ping-pong 和事件流水。
  - 最小修复：增加按 UB 容量选择的双缓冲标志；routed 6144 和 shared TP≥2 可做行级 look-ahead，TP1 保持单缓冲。TP1 当前约占 153,632B，再加一份 x+out 会到约 208,960B，不能直接全规格统一 depth=2。
  - 建议先修核间分工并 profile，再决定是否引入该分支，避免为未量化的收益再次大改 kernel。

- P1-PERF：热循环直接访问 GM 标量。[dequant_situ_quant.h:87](<redacted:local-path:f23912cff6c8>:87) 逐 expert `GetValue`，[dequant_situ_quant.h:159](<redacted:local-path:f23912cff6c8>:159) 逐 row 读取 activation scale。
  - 最小修复：group counts 一次 DMA 到小 UB；activation scale 和对应 x row 一起搬入 `xQueue` 尾部。避免每核重复 GM scalar load。

- P2-ROBUSTNESS：`group_index.sum()` 不等于 `rowLen` 时会静默产生坏输出。[dequant_situ_quant.h:85](<redacted:local-path:f23912cff6c8>:85) 会截断超额 count，但 count 总和不足时尾部行完全没有写入。
  - 这不是当前 K3 整网合法路径的 blocker：proto 已明确要求 counts 覆盖所有行，调用侧 `cumsum_group_list(..., dst_list_type=1)` 生成 count form。
  - 不建议在 adapter 用 `.sum().item()`，会引入 NPU→CPU 同步。最小处理是把它保持为受信输入前置条件，并补 producer invariant 测试；如果算子必须作为任意公开输入使用，才需要额外 device-side error/status 机制。
