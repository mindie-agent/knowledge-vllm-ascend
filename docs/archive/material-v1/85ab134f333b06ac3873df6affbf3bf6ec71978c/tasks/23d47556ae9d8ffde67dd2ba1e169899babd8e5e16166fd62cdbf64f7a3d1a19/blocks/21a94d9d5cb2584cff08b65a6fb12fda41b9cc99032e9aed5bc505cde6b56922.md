最新基线：knowledge `929bdcb`、Codex `4f7df13`、content `55ac470`。新代码已修 updater 退出码和候选 handoff interpreter，但 `auto_update.py:588` 仍使用运行中 updater 导入的 `build_probe_script`；内容格式、validator pin、adapter runtime pin 仍分散。以下只解决 P1#1，不桥接旧 updater，不迁移旧 schema。

**建议冻结的最小方案**

1. **一个产品组合，以候选 adapter commit 为身份。**

   在 Codex 仓用 `product-contract.json` 替换当前全为 `1` 的 `update-contract.json`：

   ```json
   {
     "schema": "mindie-product/1",
     "runtime": {
       "knowledge": "<exact commit>",
       "remote-dev": "<exact commit>"
     },
     "publication": {
       "repository": "mindie-agent/knowledge-vllm-ascend",
       "ref": "main",
       "verified_commit": "<exact content commit>",
       "contract_sha256": "<publication-contract.json hash>"
     }
   }
   ```

   adapter SHA 取下载并核验的 Git commit，不写入自己造成循环引用。knowledge commit 已固定其 diagnostics、ReMe、LangMem 依赖；候选验证读安装元数据，核对这些实际来源。`runtime-requirements.txt` 从 manifest 生成或强校验一致，CI checkout pin 也从同一 manifest 取得，避免三处手工同步。这里固定产品组件，不声称所有间接 PyPI 依赖已完成可复现构建。

2. **候选拥有验证逻辑；运行中 updater 只负责稳定外壳。**

   新增/改造候选内的 `candidate_validate.py`，以**候选 venv + 候选脚本**执行。`setup.py` 与 updater 调相同入口。当前 updater 不再导入 `runtime_probe.build_probe_script`，不再了解 `SummaryLedger`、`MaintenanceBudget` 等内部实现。

   外壳仅负责：来源 SHA、manifest envelope、路径属于候选目录、进程与输出上界、JSON 回执身份。候选内部负责实际 runtime API、已安装组件 SHA、catalog、Hook、summary policy、publication schema 等检查。

   回执建议：

   ```json
   {
     "schema": "mindie-candidate-check/1",
     "status": "validated",
     "candidate_revision": "<adapter SHA>",
     "manifest_sha256": "<hash>",
     "runtime": {"knowledge": "<actual SHA>", "remote-dev": "<actual SHA>"},
     "publication_contract_sha256": "<hash>"
   }
   ```

   非零退出、额外非 JSON 输出、超时、身份不符一律失败；不能出现 stdout 成功但进程失败仍通过。候选准备结果与其完整 manifest/hash 一起进入 `prepared.json`、安装事务和最终状态，避免复用仅凭目录存在的旧准备回执。

3. **内容仓声明同一个数据与审阅契约。**

   新增 `publication-contract.json`，声明：

   - domain；
   - package/task/block/entry/feedback 的精确 schema；
   - knowledge validator 的固定 SHA；
   - reviewer contract ID 与可信检查名 `publication-head`。

   不建立新服务、兼容范围或可配置路径 DSL。只支持新版 `tasks/<id>/index.md + blocks/*.md`；旧布局直接明确拒绝。

   三个使用点必须读取**精确 Git commit 的同一文件**：

   - **Feed**：先读合同，再解析任务文件；合同不符不安装、不把旧布局当空库。
   - **Publisher**：取得 upstream `base_tip` 后，首次远端写入之前验证合同；不匹配保留 frozen payload，返回明确 `contract_mismatch`，不消耗“已经尝试外部写入”的回执。
   - **Content CI**：只从可信 base 的合同选择 validator；PR head 仅作为数据读取，不能通过修改合同选择执行代码。当前 `pull_request_target` 的“不 checkout PR、不执行候选代码、check 绑定 exact head”继续保留。

   CI 另输出 `content_only`：普通内容 PR 只能修改 task/feedback 数据。修改合同、AGENTS、workflow 等是开发变更，不能获得普通内容自动合并资格。`publication_check.py` 当前对这些非内容路径直接跳过，需补 exact base→head 的路径分类。

4. **跨仓切换不伪造原子提交。**

   发布顺序：

   1. 发布并校验新版 knowledge/remote-dev 精确 commit。
   2. 内容仓发布新版合同、固定 validator 和新版数据布局；运行 exact-head CI。
   3. 现有 Grok Bot 改为遵循新版合同：只处理允许的数据路径、复用 exact-head 审阅、等待同 head 可信 `publication-head` 成功；实际配置与事件验收单独记录。
   4. 最后发布包含这些 SHA/hash 的 adapter 产品 commit；安装/更新在切换前核验组合。

   正常知识更新仍跟踪 `main`，只接收合同 hash 相同的后续内容提交，不要求每次知识贡献重发插件。合同变化必须随下一产品组合发布。`verified_commit` 是发行时已验证的数据基线，不冻结今后的正常内容同步。

   GitHub 多仓无法同时原子切换；中间状态应**可见拒绝且不覆盖有效状态**。无需给旧客户端增加兼容代码。新客户端安装失败仍报告失败；已有有效新版组合升级失败保留原组合，但不能称为更新成功。

**关键失败语义**

| 情况 | 应有结果 |
|---|---|
| 组件 / schema / validator 不匹配 | `failed` + `stage` + `code=contract_mismatch`；未切换、无远端写入 |
| 下载或读取合同失败 | `unavailable`；保留已有状态，不能当成首次使用或空库 |
| native install 结果不明 | 事务标为不确定，先读回原生选择，禁止盲重装 |
| 已切换而启动 / 记账失败 | 分别返回已切换版本与失败阶段，不让后错覆盖已发生效果 |
| 发布远端写入不明 | 延用既有 unknown receipt / read-only reconciliation，不重写 |
| Bot 合同文件已更新但未部署或未见事件 | 只能报告配置产物完成，不能报告自动发布闭环完成 |

**拟改文件**

- Codex：`product-contract.json`、`runtime-requirements.txt`、`scripts/auto_update.py`、`runtime_probe.py`/新候选 CLI、`setup.py`、`tests/preflight.py`、CI。
- knowledge：小型 `publication_contract.py` 公共接口、`loop/feed.py`、`community/publish.py`、`publication_check.py`；不让 updater 依赖内部 class 名称。
- content：`publication-contract.json`、可信 `.github/workflows/check.yml`、AGENTS/README/Bot 合同说明。
- 外部 Bot：沿用现有软件和 routines，不新建审核服务；部署回读与真实事件证据须独立完成。

**必要验证**

- 新版 updater 用候选自己的 validator；故意把运行中 probe 换成会失败的实现，仍不应被调用。
- 安装元数据与 manifest 任一 SHA 不同必须拒绝。
- 同一合成 task package 经过 producer→publication validator→feed→query/read；三者报告同一合同。
- 篡改 schema、hash、validator pin、内容 PR 中修改工作流，分别被正确拒绝。
- 各仓处于不同发布步骤时不产生伪成功、空库或错误外部写入。
- 新版组合之间的安装、切换、失败回读与恢复；**不测、不实现旧版升级桥接**。
- 外部 Bot 的真实 exact-head CI/审阅/合并/独立消费列为独立验收，文档和本地替身不能代替。
