### assistant:final_answer
静态审计结论：最高优先级不是 conv1d 注册，而是上一轮 Mamba/KDA align postprocess 与下一轮 batch 重排、block-table 更新之间的跨 stream 竞态。

关键时序：

1. 上一轮在 `global_stream` 异步执行 state copy，并异步写回 `num_accepted_tokens_cpu`。
2. 下一轮先进入 `_update_states()`，执行 remove/condense/reorder。
3. `_prepare_inputs()` 很早就 `commit_block_table()`，覆盖 fused postprocess 仍在读取的持久 GPU block table。
4. 直到更晚才 `num_accepted_tokens_event.synchronize()`。

这会同时导致：

- recurrent/conv state 被复制到错误 block；
- accepted count 按旧 request row 写回到新 batch 顺序；
- 第一张 FULL 图的 qsl、padding 都合法，但输入 state 已损坏并在中层变 NaN。

它也解释了为何 32 并发时每 rank 尾部一个请求偶现，而直接 2+2 通过：高并发前期 token 数超过 16，走 eager；请求陆续结束后缩到 1–2 个请求，首次切入 FULL size16 时恰好发生 finished/remove/condense 和 block-table 重写。DP3 即使两个真实请求、没有 padding，也会中招。

最小修复建议：

- 临时 DSpark 版本：由于 DSpark 当前明确禁用 async scheduling，只在非 async 模式下于 `_update_states()` 入口提前等待 `num_accepted_tokens_event`。后续 non-async direct copy 无需调整。
- 若做通用修复：所有模式都提前 wait，同时移除 async 路径后续基于 `prev_positions` 的 accepted gather，改为直接使用 parent 已经随 condense/swap 搬到当前顺序的 CPU buffer；否则会 double-remap。

具体 double-remap 示例：

- 旧顺序 `[A,B,C]`，accepted `[2,5,7]`
- B 结束、新增 D、重排后为 `[C,A,D]`
- early wait 后 parent 已将 buffer 搬成 `[7,2,1]`
- 现有 `prev_positions=[2,0,-1]` 再 gather 会错误得到 `[1,7,1]`
- 正确做法是直接复制 `[7,2,1]`

- GDN qsl 尾部每轮均覆盖；
- FULL spec 的 `state_indices/query_start_loc/accepted/actual_seq_lengths` 固定 buffer 在真实 spec replay 中完整刷新；
- `spec_token_indx` 的旧尾部在捕获的 pure-spec 分支不会被消费；
- dummy padding accepted 由 1 改 0 不是该偶现问题的根因；
