[PR #15443](https://github.com/vllm-project/vllm-ascend/pull/15443) 本质上是一个 **DeepSeek V4 推理性能优化**：把若干 NPU 元数据计算从模型主 stream 搬到独立 stream，尝试与模型计算并行。

### 它具体做了什么

原来每次 forward 前，模型主 stream 会串行构造：

- Compressor metadata
- QLI（Quant Lightning Indexer）metadata
- SAS（Sparse Attention Selector）metadata
- DSpark sliding-window metadata
- DSA-CP 的本地 token metadata

这些算子会占住主 stream，部分路径还有 device-to-host 同步，影响 enqueue ahead 和 TPOT。

PR 新增了 `DeviceMetadataExecutor`：

```text
模型主 stream:  更新输入 ───────── 模型计算 ─ 等待首个消费者 ─ 继续执行
                         ╲
metadata stream:          compressor → QLI/indexer → SAS/attention
```

同步不是一次等全部完成，而是拆成三个阶段：

1. `COMPRESSOR`
2. `INDEXER`
3. `ATTENTION`

每个消费者只在第一次真正使用对应 metadata 时等待；同一批次后续 layer 不再重复等待。

### 实现上的关键点

- 每个 eligible worker 创建一个独立 NPU metadata stream。
- 用 `inputs_ready` 保证输入写完后才能构造 metadata。
- 使用固定地址的持久化输出 buffer，方便 ACLGraph 使用。
- 用 `buffer_reusable` fence 防止下一批提前覆盖上一批仍在读取的 buffer。
- Full Graph 通过 `ExternalEvent` 把 graph 内消费者和 graph 外 metadata producer 接起来。
- 异步任务一旦部分提交后失败，会直接报错，不再退回同步路径重算，避免使用已被部分修改的 buffer。
- 没有新增环境变量或用户配置，满足条件时自动启用。

### 影响范围

范围比较克制：

- 只针对 **DeepSeek V4**
- 只接入 **Model Runner V1**
- 其他模型和 Model Runner V2 不创建 metadata stream
- Python 控制流、普通 slot mapping、CP/PCP 通信仍保持原路径
- DSpark 异步路径要求没有 DCP、没有 PCP，并保留 prefill 等不适用场景的同步 fallback
- 纯 `FULL` graph 下 compressor metadata 暂时保留原路径，因为有效输出长度不够 capture-stable

代码量是 17 个文件、`+2390/-120`；生产代码约 `+721/-114`，其余大部分是 UT 和一个 compressor metadata NPU nightly 测试。

### 当前结论

这项改动的目标是降低 TPOT，但**现在还不能说性能已经提升**：

- 作者报告了 105 个聚焦 UT、格式检查和若干 A3 NPU stream/operator smoke。
- 还没完成 RFC 要求的 DeepSeek V4 W8A8C8、DP4/TP4/EP16、DSA-CP + DSpark 的完整正确性和性能矩阵。
- RFC 的合入门槛是平均 TPOT 至少提升 2%，同时检查 p99、吞吐和 speculative acceptance。
- 当前 PR 仍是 Draft，head 为 `895a0b1`，存在 merge conflict。
- CI gate 红灯是因为选出的 NPU 测试没有加 `ready-precise/ready-all` 标签而被跳过，不是已经跑出的测试失败。
- 目前也没有人工 approve。

一句话概括：**它搭了一套 worker 级异步 metadata 执行框架，并首先把 DeepSeek V4 的 DSA/DSA-CP/DSpark 元数据计算接进去；设计和测试框架已经比较完整，但端到端收益及完整正确性尚待验证。**

### CPU 入参情况

结论是：**没有发现这些 metadata operator 直接接收 CPU `int[]`/IntArray；但有不少 CPU 派生的标量和控制依赖。**

| Metadata | Device 数据入参 | CPU 侧依赖 | CPU int array |
|---|---|---|---|
| Compressor | `cos/sin`、`cu_seqlens`、`start_pos`、`block_table` | block size、compress ratio、slot format、actual req 数 | 没有 |
| QLI metadata | `actual_seq_lengths_query/key` 都是 NPU Tensor | batch size、max seqlen、head dim、topk、mode、layout | 没有 |
| SAS metadata | `cu_seqlens_*`、`seqused_*` 都是 NPU Tensor | max seqlen、batch size、window、mask mode、layout | 没有 |
| DSA-CP local metadata | NPU `query_start_loc/seq_lens`，Triton 或 Torch 计算 | TP rank/size、token 数、req 数、本地范围 | 没有 |
| DSpark SWA | NPU `block_table/query_start_loc/seq_lens` | speculative token 数、window、block size、输出行数 | 没有 |

C++ schema 也能确认，Compressor、QLI、SAS 都是 `Tensor + int/string/bool`，没有 `int[]`：[operator schemas](https://github.com/vllm-project/vllm-ascend/blob/895a0b1893613b8053f5528067d924c340ed68f5/csrc/torch_binding.cpp#L2350-L2467)。

但是它明确依赖 CPU mirror 来提前算标量：

```python
max_seqlen_q = torch.max(query_start_loc_cpu[1:] -
                         query_start_loc_cpu[:-1]).item()
max_seqlen_kv = torch.max(seq_lens_cpu[:num_reqs]).item()
```

见 [DSA builder](https://github.com/vllm-project/vllm-ascend/blob/895a0b1893613b8053f5528067d924c340ed68f5/vllm_ascend/attention/dsa_v1.py#L791-L810)。MRV1 会把 `query_start_loc.cpu` 和 `optimistic_seq_lens_cpu` 塞进 common metadata，正常路径不需要从 NPU 读回来；但仍保留了 CPU mirror 缺失时的 `seq_lens.cpu()` fallback，这种情况下还是会同步。

所以这里的“异步”边界其实很窄：

```text
CPU batch planning、max/shape/branch 计算：同步
task.run() 和 ACLNN enqueue：同步在主 Python 线程执行
metadata kernel 的 NPU 执行：在独立 stream 异步
consumer：首次使用时等 event
```

`submit()` 里直接循环调用 `task.run()`，并没有 CPU worker thread，[代码在这里](https://github.com/vllm-project/vllm-ascend/blob/895a0b1893613b8053f5528067d924c340ed68f5/vllm_ascend/worker/device_metadata.py#L68-L111)。因此它隐藏不了：

- CPU metadata planning
- Python closure 调用
- operator dispatch/tiling 的 host 时间
- CPU mirror 修正或 fallback 同步

它只能隐藏 **metadata kernel 已经 enqueue 之后的 device execution time**。

### 我觉得真正需要质疑的地方

1. **抽象层级偏早**

   当前只有 DSV4 DSA/DSA-CP 使用，却把协议放到通用 worker 层。后续第二个模型未必能复用这三个 stage。

2. **依赖表达太弱**

   `Callable + enum 排序 + id(tensor)` 没有显式 input/output/lifetime。DSA-CP local metadata 和 compressor 都塞在 `COMPRESSOR` stage，正确顺序部分依赖 task 原始排列，作为“框架”比较脆。

3. **ambient state 太多**

   consumer 通过 forward context 找 executor，再用 tensor id 等待。metadata 自身没有显式携带 ready event，阅读局部代码无法知道数据是否 ready。

4. **QLI/SAS 仍然动态分配**

   Compressor 新增了真正的 `*_out` 固定输出接口；QLI/SAS 仍是 operator 返回临时 1024 Tensor，再 copy 到 persistent buffer。也就是说框架已经很大，但热路径分配问题没有完全收口。

5. **还没有性能证据支撑复杂度**

   当前只有 UT 和 NPU stream/operator smoke，没有端到端 TPOT timeline。必须确认 metadata stream 确实与有用模型计算重叠，而不是最终在第一个 compressor/indexer consumer 处立即等待。

我的判断是：**技术方向可以做，但现在属于“机制合理、集成形态过度”。**

如果只服务 DSV4，我更倾向先做成 DSA-scoped coordinator：由 DSA metadata 对象显式携带 compressor/QLI/SAS ready event，MRV1 只提供一条 stream 和 batch lifecycle，不认识 stage、provider 和 tensor id。等第二个模型出现同样需求后，再抽象成通用 executor。

在接受当前架构前，我至少会要求三组 profiling 对比：

- 原同步路径
- DSV4 内部局部独立 stream
- 当前通用 executor

重点看 host enqueue gap、metadata device time、首次 consumer wait、reuse fence 等待，以及最终 TPOT/p99。否则现在这 700 多行生产代码很可能比实际可隐藏的时间窗口更“大”。
