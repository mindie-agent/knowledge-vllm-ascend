## 1. 架构需要补上“人直接参与领域会话”

我建议把领域执行单元定义为：**上下文独立、可持续交互的领域 Agent 会话**。

人的界面可以看到多个会话，而每个 Agent 仍只接收自己的上下文：

| 对象 | 应该看到什么 |
|---|---|
| 主 Agent | 总目标、用户约束、跨领域决策、必要结果 |
| 领域 Agent | 本领域 Skill、知识、任务过程，以及用户对它的持续指导 |
| 用户 | 当前领域 Agent 公开的分析说明、工具操作、证据和代码变化，并能直接回复 |

具体体验应该是：

1. 你在主会话提出任务，主 Agent 选择领域。
2. **正在承担主要工作的领域 Agent 自动出现在当前关注的面板中。**
3. 你看到它准备沿错误方向调查，直接输入“这里先看 graph replay，不要继续查通信”。
4. 这条指导直接进入**同一个领域会话**，保留此前的调查上下文。
5. 主 Agent 接收必要的决策和结果，领域的完整过程留在领域会话里。

这样，你仍能像现在一样参与研究。**不需要主 Agent 先读完、理解并转述每一步，才能让你看到。**

涉及整体目标的修改需要同步给主 Agent；具体调试指导留在当前领域。固定脚本负责技能和工具的加载边界，研究过程仍允许你不断调整。

## 2. 主要任务与辅助任务应该采用不同交互方式

- **模型适配、疑难排障、算子优化等主要任务：** 使用可见、可直接对话、可接续的领域会话。
- **搜索资料、跑一组测试、检查某个独立问题：** 可以交给后台 Subagent，返回简洁结果。

如果某个 Harness 无法展示并交互其子会话，可以用**固定领域配置的独立前台会话**承载主要工作。它仍然只有该领域的 Skill、MCP 和知识库，符合隔离目标。

因此，我会把当前架构中的“领域 Subagent”改成更准确的 **“可交互领域 Agent”**，并增加用户与它之间的双向路径。

## 3. 当前官方机制能做到多少

这轮是文档核对，还没有做真人交互验收：

- **Codex：** CLI 支持切换查看子 Agent；官方 App Server 提供消息、工具进度、分析摘要等流式事件，以及执行中的 `turn/steer`。有实现基础，但具体客户端能否提供顺手的同屏交互仍要验证。[Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)、[App Server](https://learn.chatgpt.com/docs/app-server)
- **Claude Code：** Agent Teams 明确支持打开成员会话、查看过程并直接发送指导；它目前仍是实验功能。其文档也把频繁往返、持续修改的工作列为更适合主会话的场景，这与你的担忧一致。[Teams](https://code.claude.com/docs/en/agent-teams)、[Subagents](https://code.claude.com/docs/en/sub-agents)
- **DeepSeek Harness：** 可接续子会话已有浏览器侧直接 Queue/Steer 交互。但此前看好的独立 SDK 子进程方案只回传最终结果，没有把子会话过程接到父侧。**不能把两条路径的优势拼起来，认定整体已经满足。** [人机交互机制](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/implemented/feature/2026-08-27-continuable-subagent-human-inbox-control.md)、[SDK 子进程边界](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/subagent/subagent-dsh-sdk/README.md)

## 4. 工具方面的判断

**暂时没有发现必须新增的第三个通用业务 MCP 组件。** 但要补全以下能力：

| 必要能力 | 放在哪里 |
|---|---|
| 远端读、改、运行、作业控制、产物取回 | remote-dev 内选取必要工具，形成完整开发闭环 |
| 本地文件、Git、检索最新文档 | 优先使用 Harness 原生工具或 CLI |
| 领域过程展示、定向输入、会话接续 | **产品的交互与 Harness 适配层，属于必备能力** |
| 多任务共享 NPU 时的资源协调 | 相应场景必须有，可复用现有平台；不要求必装整套 coordinator |

**下一步最值得验证的是：你能否盯着一个隔离的领域 Agent 工作，中途连续纠正几次，它能沿用上下文调整行动，同时主 Agent 的上下文保持精简。** 这个闭环通过了，才足以说明新架构保住了目前最有价值的人机协作方式。

## 1. 新会话可以，原生 fork 要看继承了什么

| 方式 | 历史上下文 | 适合的场景 |
|---|---|---|
| 新建领域会话 | 只传目标、约束和必要证据 | 从框架切到算子等跨领域工作 |
| Fork 已有会话 | 复制分叉点之前的历史 | 同一领域尝试另一个方案 |
| Resume 已有会话 | 延续原来的历史 | 你持续指导同一个领域任务 |

Codex 的 `thread/fork` 和 Claude Code 的会话分支，都会复制已有历史；**fork 本身不会自动清理旧 Skill，也不会自动换成目标领域的工具配置**。[Codex 会话接口](https://learn.chatgpt.com/docs/app-server)、[Claude Code 会话分支](https://code.claude.com/docs/en/sessions)

所以我建议：

- **跨领域：默认新建会话，带必要交接内容。**
- **同领域探索其他路线：允许 fork。**
- **持续纠偏：一直在原领域会话里继续。**

从足够精简的主会话 fork 也可以，但仍须单独落实领域配置。

## 2. “刷新 Skill”可以做，但刷新范围要明确

我会把它设计成两步：

1. **界面刷新可选领域和能力目录。** 主 Agent 获得简短的领域入口，用户也能手动选择。
2. **创建领域会话时加载对应 Skill、MCP 和知识库。** 活动会话保持自己选定的配置。

不宜依赖在一个长期会话里反复替换 Skill 来实现隔离。比如 Claude Code 明确说明：调用后的 Skill 正文会留在会话历史中；Codex 支持目录刷新，但目录刷新并不构成历史清除。[Claude Skill 生命周期](https://code.claude.com/docs/en/skills#skill-content-lifecycle)、[Codex Skill 接口](https://learn.chatgpt.com/docs/app-server)

## 3. 你说的“界面的东西”，确实是产品核心

最小界面可以很简单：

```text
任务：修复模型性能问题
├─ 总览会话       目标、整体进度、跨领域结论
├─ vLLM 会话      框架定位与集成验证
└─ Triton 会话    算子分析与优化 ← 当前正在查看、直接对话
```

点击 Triton 会话，就直接看到它公开的分析说明、工具操作和代码变化。输入框也明确指向 Triton 会话，你的纠正直接送达它。

主 Agent 只接收必要结论和涉及整体目标的变更。**用户能看到的过程范围，可以大于主 Agent 模型收到的上下文范围。** 这就同时保留了隔离和过程 review。

## 4. 技术上能做到多普遍？

**几个主要 Harness 已有实现基础；一个通用 Plugin 能否在所有原生界面提供相同体验，目前不能保证。**

| Harness | 当前可用基础 |
|---|---|
| **DeepSeek Harness** | 已有按会话选择 preset 的界面；每个 preset 可定义工具、提示和 Skill。只允许空会话切换，开始工作后配置固定，与你这个方向很贴合。[官方说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/preset/agent-presets/README.md) |
| **Codex** | App Server 有创建、恢复、分叉会话、流式过程事件和执行中追加指导的接口，可支撑会话界面。[官方接口](https://learn.chatgpt.com/docs/app-server) |
| **Claude Code** | 原生会话分支，加上 SDK 的持久会话和流式输出，可支撑独立会话交互。[会话管理](https://code.claude.com/docs/en/agent-sdk/sessions)、[事件输出](https://code.claude.com/docs/en/agent-sdk/agent-loop) |
| **OpenCode** | SDK 有会话创建、发送消息和事件订阅接口。[官方 SDK](https://opencode.ai/docs/sdk/) |

这些是机制证据，还需要验证“独立能力配置 + 实时过程展示 + 连续指导”的组合。

**我的建议是把目标架构调整为：领域能力包、独立领域会话、会话导航与直接交互。先复用 Harness 已有的多会话界面，补领域选择和任务交接；统一前端作为原生界面不足时的适配方案。** 这样主要研发任务由人持续参与，后台 Subagent 保留给适合独立完成的辅助工作。
