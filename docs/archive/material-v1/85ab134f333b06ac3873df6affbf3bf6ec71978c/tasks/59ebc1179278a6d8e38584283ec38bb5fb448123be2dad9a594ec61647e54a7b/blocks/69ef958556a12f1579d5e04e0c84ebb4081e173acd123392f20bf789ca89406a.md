- **内容层**：公共知识、领域知识、项目知识分别维护。
- **索引层**：支持独立构建和更新的分片，按需加载相关分片。
- **查询层**：先选择相关领域，再检索；结果不足时逐步扩展范围。
- **服务层**：复用公共知识服务与模型资源，避免每个领域都启动一套后台。

公共 CANN、HCCL 等知识被多个领域引用，保存一份即可。较小领域可以共用物理分片，较大领域再独立拆分。

因此：

> **领域边界决定知识的归属；索引分片决定加载与检索成本，两者允许不同粒度。**

分片效果需要同时检查查询延迟、常驻内存、增量更新成本和召回质量。领域切得更细之后，也要保证跨领域经验仍然能够被找到。

## 6. 编排层优先复用原生能力

我建议 VAWS 自己维护：

- 分层领域目录。
- 领域 Agent 的配置和能力选择。
- 委派输入、结果回传与证据引用约定。
- 可复用的领域工作流。
- 知识分片的选择规则。

创建、等待、恢复、取消 Agent，以及 workflow 执行，优先适配客户端原生能力。Codex 已有子 Agent 编排，CC 有子 Agent 和动态 workflows；OMO 的类别路由与技能注入可以作为设计参考。[Codex 子 Agent](https://learn.chatgpt.com/docs/agent-configuration/subagents)

任务编排也应按需要伸缩：

- 单领域任务交给一个合适的 Agent。
- 独立问题分给多个 Agent。
- 有先后依赖的工作形成执行图。
- 需要持续讨论的少量角色保持会话。
- 并行写代码、占用 NPU 时，继续遵守源码和资源归属。

**下一版架构的核心定义可以改为：Plugin 接入 + 分层领域发现 + Agent 编排与上下文隔离 + 按需知识分片 + 公共执行组件。**

首要验收目标是：**随着领域总数和知识总量增长，一个固定任务实际加载的内容仍然保持有界，并且跨领域交接没有丢失必要信息。**

**一个主入口 Skill → 通用 worker 启动器 → 固定领域配置 → 独立子 Agent → 精简结果回传。**

关键改进是：**固定领域的能力配置，按任务创建 Agent。**

- **主 Agent**：只新增介绍／分发 skill，通过原生工具调用启动入口。
- **启动器**：按领域 ID 确定 skills、MCP、知识范围和必要上下文，由机制落实加载边界。
- **领域 worker**：获得充分的专业信息，自主调查和执行；同一子任务可以继续原会话。
- **回传**：结论、证据引用、产物和未知项；详细材料按需展开。

这样可以避免预注册大量领域 Agent，把它们的描述重新塞进主上下文。领域配置也更容易统一维护。

1. **新会话不等于能力隔离。** 例如 CC 的 `skills` 字段控制预加载，并不自动限制其他技能的访问范围。[官方说明](https://code.claude.com/docs/en/sub-agents#preload-skills-into-subagents)
