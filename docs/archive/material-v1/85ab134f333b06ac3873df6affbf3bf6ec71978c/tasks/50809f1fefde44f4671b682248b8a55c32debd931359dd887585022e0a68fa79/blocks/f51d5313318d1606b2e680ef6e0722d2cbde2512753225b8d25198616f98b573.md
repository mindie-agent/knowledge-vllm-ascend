### user
那回答我为什么单算子qliv2比qli要更快，但是整网并不支持端到端比compressor only更快

### assistant:final_answer
本质是：QLI v2 的优势发生在算子核内，但 Full v2 同时增加了 prefill 和每步调用链的成本，核内收益被抵消了。

同一 v0.26.0 环境的数据很明确：

| 场景 | TTFT 变化 | TPOT 变化 | 最终 TPS |
|---|---:|---:|---:|
| 8K/C16 | +7.25% 变慢 | -2.90% 变快 | +3.82% |
| 128K/C1 | +10.70% 变慢 | +8.82% 变慢 | -8.95% |
| 128K/C8 | +6.12% 变慢 | +6.96% 变慢 | -4.84% |

原因主要有三个：

1. Full v2 把 prefill 也切到了 QLI v2  
   QLI v2 的优势主要是纯 decode 小 query 场景。全量替换后，所有场景 TTFT 都回退了 4%–13%，长上下文尤其明显。

2. 单算子测试没有覆盖完整调用链  
   QLI v2 需要额外的 `seqused_k`、`cmp_residual_k` 和 v2 metadata。整网中还包含 metadata 构造、tiling、算子 launch、ACLGraph、MTP、MoE/EP 和调度等待。算子核省下来的时间可能小于这些新增成本。

3. 实际 decode shape 与单算子 benchmark 不同  
   单算子通常是固定 batch、固定长度、纯 decode；整网是动态 batch、不同 KV 长度、MTP1、DP4×TP4×EP。数据显示 8K/C16 能兑现核内收益，但 128K 下 TPOT 本身就回退了约 7%–9%，说明真实长 KV shape 没有复现单算子的优势。

不是大块转连续导致的：当前 QLI v2 wrapper 没有显式 `.contiguous()`，K/K-scale 支持首轴非连续。

所以正确结论是：QLI v2 是“特定纯 decode shape 下更快”，不是“可以无条件替换旧 QLI”。合理方案就是现在这版——纯 decode 才走 QLI v2，任何包含 prefill 的 batch 整批走旧 QLI；下一步真正值得优化的是 v2 metadata/launch 开销和长 KV decode tiling。

### assistant:final_answer
你的理解差一点：当前是“共享 cache 字典，但不共享物理 buffer”。

当前有两个独立的 `[1024] int32` device buffer：

- `qli_metadata_buffer`
- `qli_v2_metadata_buffer`

见 [dsa_v1.py](<redacted:local-path:76f1950b5576>:414)。

每个 forward 新建一个共享的 `common_ratio_to_sas_metadata`：

- 原 QLI 使用 cache key `"qli"`
- QLI v2 使用 cache key `"qli_v2_decode"`
- 多个 DSA/KV group 共享该 cache，metadata 算子通常只生成一次，然后复制到各 builder 自己的 buffer

路由现在是：

```python
use_qli_v2 = num_decodes > 0 and num_prefills == 0
```

见 [dsa_v1.py](<redacted:local-path:76f1950b5576>:814)。

因此：

- 纯 decode：只调用 `npu_quant_lightning_indexer_v2_metadata`
- prefill 或 prefill+decode：只调用原 `npu_vllm_quant_lightning_indexer_metadata`
- 同一个 forward 不会同时调用两套 metadata
- 路由条件本身不检查 `FULL_DECODE_ONLY` 配置；即使 eager 模式，只要是纯 decode 也会走 v2。当前服务恰好使用 `FULL_DECODE_ONLY` graph

所以，如果你的预期是“两套 metadata 共用同一个实际 buffer”，当前还没有做到。现在两个 buffer 是互斥使用的，理论上可以进一步合并成一个，但需要补一次 ACLGraph capture/replay 的 tensor 地址稳定性验证。

### user

### assistant:final_answer
核心原因是：这三组不是同版本 A/B。

- Compressor-only、Full v2：历史 vLLM 0.26.0
- 当前 Mix：K3 vLLM 0.27.1

TTFT 方面，当前 Mix 在产生首 token 前走的是原 QLI，根本不会调用 QLI v2 metadata 或 QLI v2。因此 Mix 的 TTFT 更差不能归因于混合路由，而是 0.27.1 的模型执行、调度、ACLGraph、DP/EP 以及服务运行波动。并发 TTFT 还包含排队和批处理时间，不是纯 prefill kernel 时间。

TPOT 方面，稳定纯 decode 时：

- Full v2：QLI v2
- 当前 Mix：同样是 QLI v2

但当前 0.27.1 集成每步还会执行：

- `seq_lens / 4`
- `seq_lens % 4`
- QLI v2 metadata 构造/缓存复制
- 0.27.1 的 graph replay、调度和 MTP 验证流程

另外服务开启了 MTP1，端到端 TPOT 会受 draft acceptance rate 影响，单算子测试不包含这一部分。

所以当前能确认的是：

- TTFT 回退不是 QLI v2 路由造成的。
- TPOT 回退也不能用 Mix 与 Full v2 的路由差异解释，因为纯 decode 路由相同。
- 没有发现大块 `.contiguous()` 拷贝。
- 这张表只能比较实际部署结果，不能用于定位 QLI 路由的因果差异。

要得到严格结论，需要在同一个 0.27.1 容器里跑 Compressor-only、Full v2、Mix 三组；否则版本差异和 MTP acceptance 会混在结果里。
