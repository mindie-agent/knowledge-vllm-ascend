### assistant:final_answer
是，这里会造成 D2H 同步。

- `qli_seqused_k` 在 NPU 上，`max()` 先启动 NPU reduction，随后 `.item()` 强制等待并把标量取回 Host：[dsa_v1.py](<redacted:local-path:f94c6ac033a4>:1240)。
- metadata cache dict 每次 model forward 都会重新创建，因此纯 decode 下基本每个 forward 都会执行一次，不是只在服务启动时执行：[model_runner_v1.py](<redacted:local-path:c63b8f6bef47>:3129)。
- 前面已经从 `_seq_lens_cpu` 算出了 `max_seqlen_kv`，可以直接改成：

```python
max_seqlen_k=max_seqlen_kv // 4,
```

不需要再做一次 CPU `max`。数学上：

```text
max(floor(seq_len / 4)) = floor(max(seq_len) / 4)
```

而且 PA_BBND 已传 `seqused_k` 时，算子内部优先直接读取 `seqused_k`，实际上不会使用 `max_seqlen_k`：[quant_lightning_indexer_v2_metadata_aicpu.cpp](<redacted:local-path:a57a29ee8089>:268)。

结论：它非常可能是 Full v2 和 Mix 相对 Compressor-only 的 TPOT 退化来源之一，尤其符合每个 decode forward 增加固定同步开销的表现。但它不能解释 Mix 与 Full v2 之间的差异，因为两者都走这行；也不足以单独解释秒级 TTFT 差异。

对，你的理解是对的。当前数据不能证明 Mix 的 prefill 变慢，TTFT 差异主要来自测试不完全配对，以及并发下 decode 对排队的间接影响。

代码上已确认：

- Mix prefill 调用原来的 `npu_vllm_quant_lightning_indexer`。
- 只有 `num_decodes > 0 && num_prefills == 0` 才构建并调用 QLI v2。
- Mix prefill 中原有的两个 `.max().item()`，Compressor-only 也同样存在，所以不是两者差异来源。[dsa_v1.py](<redacted:local-path:f94c6ac033a4>:976)

最明显的证据是三组启动后 warmup TTFT：

| 场景 | Compressor-only | Full v2 | Mix |
|---|---:|---:|---:|
| 8K | 1.389s | 1.500s | 1.488s |
| 32K | 4.518s | 5.094s | 5.104s |
| 128K | 20.953s | 23.253s | 23.254s |

Full v2 和 Mix 几乎完全一致，却一起比历史 Compressor-only 慢。这说明差异是“历史 Compressor-only 那轮”和当前两轮之间的公共差异，不是 Mix 路由导致的。Compressor-only 是 8 月 27 日的数据，当前 Full/Mix 是 8 月 30 日独立拉起的服务，不是同一轮严格 A/B。

并发 TTFT 还会被 decode 影响：8K/C16 下每张 DP 卡无法一次塞下所有 8K prefill，后面的请求需要排队；前面请求进入 decode 后，decode TPOT 会影响后续请求何时拿到首 token。因此即使 prefill 完全一样，Mix 的 decode 调度也可能让并发 TTFT 变化。

另外 32K/128K 使用了 95% shared prefix，Prefix Cache 分散在四个 DP Engine 上。当前 Mix 的 32K/C16 TTFT 从旧测的 4.751s 跳到 2.806s，这种幅度显然不是 prefill 算子变化，而是 DP 路由、缓存命中和排队分组改变。

唯一还不是逐字节一致的地方，是 Mix 把原来 prefill 的直接 QLI 调用收进了 `_indexer_qli`，每个 C4 层多了一次 Python 方法调用和路由判断；理论上可能有很小的 host 开销，但解释不了 128K 约 2 秒的差异。

结论：目前没有证据表明 Mix prefill 本身比 Compressor-only 慢。要把这件事彻底定死，需要用当前同一套源码重新跑 Compressor-only，并用 `max_tokens=1`、无 Prefix Cache、C1 多次重复做严格 A/B；这会完全排除 decode 排队影响。
