### assistant:final_answer
结论：K3 的整除失败不是 KDA state shape 算错，也不需要新增一套 KV-cache 框架；是 Ascend MLA 的自定义 cache spec 没遵守通用 `page_size_padded` 契约。

具体对照：

- Qwen3.5 的 GDN state：
  - conv：`((kernel-1+num_spec), (2*K_heads*K_dim + V_heads*V_dim)/TP)`
  - recurrent：`(V_heads/TP, V_dim, K_dim)`
  - conv dtype 取 `mamba_cache_dtype/model dtype`
  - recurrent dtype 取 `mamba_ssm_cache_dtype`，auto 时与 conv 相同
- K3 的 KDA state：
  - conv：`(kernel-1, 3*num_heads*head_dim/TP)`
  - recurrent：`(num_heads/TP, head_dim, head_dim)`
  - conv 为 BF16，recurrent 固定 FP32

K3 TP8 的实际数值是：

- conv `(3, 4608)` BF16：`27,648 B`
- recurrent `(12, 128, 128)` FP32：`786,432 B`
- MLA block size：`768`
- MLA 实际页：`768 × (512+64) × 2 = 884,736 B`
- Ascend 连续布局要求的公共页：`884,736 + 27,648 = 912,384 B`

旧实现虽然给 MLA spec 写入了 `page_size_padded=912384`，但 `AscendMLAAttentionSpec.page_size_bytes` 自己重写了计算，仍返回 `884736`。所以：

```text
912384 % 884736 = 27648
```

正好余下一个 conv state，最终在 `unify_kv_cache_spec_page_size()` 报不能整除。

Qwen3.5 不触发该问题，是因为它走普通 `FullAttentionSpec`，基类会正确兑现 `page_size_padded`。K3 走 `AscendMLAAttentionSpec`，才暴露这个契约缺口。

最小正确适配是：

1. 将 [kv_cache_interface.py](<redacted:local-path:1019a854d063>) 的 Ascend MLA 自定义计算改为覆盖 `real_page_size_bytes`，让基类统一处理 padding。共享树里这一半修复已经出现，方向正确。
2. `AscendMLAAttentionSpec.merge()` 必须保留 `page_size_padded`。当前 merge 即使只合并一个 spec，也会重新构造对象并丢掉 padding；仅修改属性还不完整。
3. 单测至少覆盖：
   - 原始页 `884736`
   - padded 页 `912384`
   - `merge([spec]).page_size_bytes == 912384`
   - 经过 KV-cache group 创建后 MLA/KDA group 页仍全部为 `912384`
4. 不应修改 `unify_kv_cache_spec_page_size()`，也不应加 K3 专用 LCM 或环境变量绕过。

已有 Ascend model runner 的混合连续布局已经支持 MLA：会从公共页前部跳过 conv padding，再切出 512 维 latent cache 和 64 维 positional cache，因此无需新增 allocator。

另外两个边界：

- K3 虽然取消 RoPE，但仍缓存 64 维原始 positional slice，所以页大小仍应按 `512+64` 算，不能把 `qk_rope_head_dim` 直接置零。
- Qwen3.5 的 GDN conv state 包含 `num_spec`，而现有 `kda_state_shape()` 接收却忽略 `num_spec`。这不影响当前普通 decode，但 speculative decode 不能仅凭复用 Qwen3.5 框架就宣称完整支持。
