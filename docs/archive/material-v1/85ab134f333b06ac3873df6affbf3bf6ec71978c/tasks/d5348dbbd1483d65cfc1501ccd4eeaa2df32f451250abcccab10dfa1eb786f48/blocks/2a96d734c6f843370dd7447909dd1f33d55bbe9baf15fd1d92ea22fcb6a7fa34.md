### 当时是怎么定位出来的

1. 从 P 侧日志确认失败位置

调用已经进入：

```text
kimi_kda.py::_run_prefill
  -> torch.ops._C_ascend.kda_gate_cumsum
```

底层报错是：

```text
Parse dynamic kernel config fail
Op KdaGateCumsum does not has any binary
```

这类错误发生在 kernel 选择/加载阶段，甚至还没有进入 tiling，所以优先怀疑算子包和动态 kernel 配置，而不是计算逻辑。

2. 排除“TP16 的 6 heads 不支持”

P 是 TP16，每卡 6 heads；D 是 TP8，每卡 12 heads。当时把服务请求缩成单卡直调：

```text
H=12, T=1：失败
H=6,  T=1：失败
```

两种 TP 规格在同一旧包上都失败，所以不是 TP16、6 heads 或 unequal-TP 地址映射导致的。

3. 排除 PR #9

PR #9 只修改 Mooncake connector 和 UT，没有修改 KDA AscendC kernel、tiling 或构建脚本；对应 Mooncake UT 是 `109 passed`。因此 PR #9 最多触发了这条执行路径，但没有制造算子错误。

4. 找到关键矛盾

检查安装包后发现：

- `KdaGateCumsum_*.o` 存在；
- 对应的单算子 `*.json` 存在；
- Torch schema `torch.ops._C_ascend.kda_gate_cumsum` 也存在；
- 但总索引 `binary_info_config.json` 里没有：
  - `KdaGateCumsum`
  - `ChunkKdaFwd`
  - `KdaLayoutSwap12`

所以“文件存在”和“运行时说没有 binary”并不矛盾：CANN 通过聚合 manifest 找 kernel，不会遍历目录猜测 `.o` 文件。

5. 从构建脚本确认形成原因

当前脚本明确保留了 `csrc/build`，只清理另外两个输出目录：

[build_aclnn.sh](<redacted:local-path:a700a40217df>:267)

```bash
log "preserving csrc/build and cleaning output dirs"
rm -rf -- output build_out
```

而 `binary_info_config.json` 是一个 CMake `OUTPUT`：

[func.cmake](<redacted:local-path:f12e6a525b4c>:640)

```cmake
add_custom_command(
    OUTPUT ${BINARY_INFO_CONFIG_FILE}
    COMMAND ... ascendc_ops_config.py ...
)
```

复用旧 `csrc/build` 时，Ninja/CMake 可能认为这个聚合文件已经生成，无需重跑。新增 KDA 算子能各自生成 `.o/.json`，但旧聚合索引继续被打包。

6. 用干净重编完成闭环验证

彻底删除：

```bash
rm -rf -- csrc/build csrc/output csrc/build_out
```

然后全量构建。新产物中：

- 三个 KDA op 都进入 manifest；
- Gate/Chunk/Layout 分别产生预期的 `3/7/3` 组 binary；
- H=6/12、T=1/65 四组单卡直调全部通过；
- AscendC 集成测试通过；
- 最终 P=TP16、D=DP2×TP8 的真实 PD 请求通过，输出和 D 直跑一致。

这组“旧包失败 → 干净重编 → 同代码同输入通过”的对照最终确认了根因。

### 怎么避免

最重要的是把“源码切换”和“算子 build cache”绑定起来。

- 在以下情况强制删除 `csrc/build`：
  - 切换 branch/commit；
  - 新增或删除 AscendC 算子；
  - 修改 `build_aclnn.sh` 的算子列表；
  - 修改 op host/kernel、tiling 或 CMake；
  - 更换 CANN、SOC 或编译器版本。

- CI、发布包和正式验证环境一律使用干净构建，不要跨提交复用算子构建目录。

- 构建后增加 package gate，至少验证：
  - `aic-*-ops-info.json` 包含预期 op；
  - `binary_info_config.json` 包含预期 op；
  - manifest 引用的 `.o` 全部存在；
  - KDA binary 结构化统计为预期的 `3/7/3`；
  - 安装目录已经清掉旧 vendor 包。

- 不要只检查：

```python
hasattr(torch.ops._C_ascend, "kda_gate_cumsum")
```

这只能证明 Torch/C++ binding 存在，不能证明设备 kernel 已被 manifest 注册。

- 服务启动前增加最小 smoke：
  - P 规格：H=6；
  - D 规格：H=12；
  - 短序列：T=1；
  - 跨 chunk：T=65。

从构建系统上彻底解决，建议给 build cache 增加 fingerprint，至少包含：

```text
git commit/source hash
CUSTOM_OPS
SOC_VERSION
CANN version
toolchain version
```

fingerprint 变化就清理 `csrc/build`。同时让 `binary_info_config.json` 显式依赖所有单算子 JSON/done 文件，或者每次 package 前强制删除并重新生成 manifest。后者改动小，前者更根本。
