结论：DeepSeek-V4-Flash 的 `QuantLightningIndexer` 不是仓库自己训练出来的一套独立权重，而是三部分组合：

1. 模型结构和 Indexer 权重来自 DeepSeek 官方 V4-Flash checkpoint。
2. LI 算法沿用 DeepSeek-V3.2，针对 V4 的 4 倍压缩 Cache 做了适配。

### 来源

官方 [DeepSeek-V4-Flash config](https://huggingface.[REDACTED_SECRET].json) 的 `compress_ratios` 是：

- layer 0、1：SWA
- layer 2、4、…、42：`compress_ratio=4`，即 CSA/C4，共 21 层
- layer 3、5、…、41：`compress_ratio=128`，即 HCA/C128
- MTP 层也是 SWA

只有 C4 层才实例化 Indexer。官方 [checkpoint 索引](https://huggingface.[REDACTED_SECRET].safetensors.index.json) 里直接带有：

```text
attn.indexer.wq_b.{weight,scale}
attn.indexer.weights_proj.weight
attn.indexer.compressor.{wkv,wgate,norm,ape}
```

所以：

- `indexer.wq_b`、`weights_proj`、Indexer Compressor 权重来自原始模型；
- `indexer_q` 和 Indexer Cache 是运行时生成的；
- `QuantLightningIndexer` 本身没有可训练权重，不存在单独的 “QLI checkpoint”。

算子血缘则是 DeepSeek-V3.2 的 LI。V4 文档明确说 C4 稀疏化“延续 DeepSeek-V3.2 的设计”，A3 Tiling 沿用原设计，新增了压缩倍率对应的阶梯 causal mask，并为 950 增加 FP8/HiF8 和新的 Top-k 实现。[V4 AscendC 算子说明](https://gitcode.com/cann/cann-recipes-infer/blob/master/docs/models/deepseek-v4/deepseek_v4_ascendc_operator_guide.md)

核心 kernel 在：

- [ops-transformer/experimental/attention/quant_lightning_indexer](https://gitcode.com/cann/ops-transformer/tree/master/experimental/attention/quant_lightning_indexer)
- [quant_lightning_indexer_metadata](https://gitcode.com/cann/ops-transformer/tree/master/experimental/attention/quant_lightning_indexer_metadata)

`cann-recipes-infer` 里的 C++ binding 最终调用 `aclnnQuantLightningIndexer`，GE converter 则生成 `QuantLightningIndexer` 节点；不是这里重新实现了一遍 kernel。[recipes 的 Torch binding 文档](https://gitcode.com/cann/cann-recipes-infer/blob/master/ops/ascendc/docs/custom-npu_quant_lightning_indexer.md)

### 端到端怎么配套

```text
主 Attention 的 qr / qr_scale
    └─ indexer.wq_b
       └─ RoPE
          └─ Hadamard（HiF8 路径省略）
             └─ 动态量化 ──────────────► Qindex + Q scale

hidden_states
    ├─ indexer.weights_proj ───────────► W
    │
    └─ Indexer Compressor，ratio=4
       └─ RoPE/Hadamard
          └─ IndexerCompressEpilog
             └─ 写入分页 Cache ───────► Kindex Cache + K scale

QLI Metadata ──────────────────────────► 分核信息
Q、K、W、scales、block_table、metadata
    └─ QuantLightningIndexer
       └─ Top-512 compressed indices
          └─ 作为 cmp_sparse_indices 传给 SparseAttnSharedKV
```

固定配套参数是：

- `Q heads=64`，`K heads=1`
- `head_dim=128`
- `topk=512`
- `compress_ratio=4`
- `layout_query=TND`
- A3/普通 FP8 的 Key Cache：`PA_BSND`
- causal `sparse_mode=3`
- Metadata 输出为长度 1024 的 `int32` 分核信息，并在相同 C4 层间复用

模型接线在 [indexer.py](https://gitcode.com/cann/cann-recipes-infer/blob/master/models/deepseek_v4/models/modules/indexer.py)，Top-k 输出随后作为 `cmp_sparse_indices` 交给 SAS；因此 QLI、Indexer Compressor、Indexer Cache、Metadata 和 SAS 是一整套，不能只装一个 QLI 算子。

### 三种量化路径

| 平台/方案 | Q 与 Indexer Cache | Scale / W | 调用接口 |
|---|---|---|---|
| A3 W8A8 | INT8，动态 Per-Token-Head A8/C8 | FP16 scale；`weights_proj` 输出 FP16 | `torch.ops.custom.npu_quant_lightning_indexer` |
| 950 MXFP8 | FP8 E4M3，动态 Per-Token-Head | FP32 scale；W 为 FP32 | 同上，经 custom binding |
| 950 HiF8 | HiF8、Per-Tensor 路径 | FP32；当前源码还会量化 `weights_proj` 和 Indexer Compressor Linear | `torch.ops.cann_ops_transformer.quant_lightning_indexer` |

完整量化边界可见 [V4 推理指南的量化策略](https://gitcode.com/cann/cann-recipes-infer/blob/master/docs/models/deepseek_v4/deepseek_v4_inference_guide.md)：A3 推荐 W8A8，950 支持 MXFP8-MXFP4 和 HiF8-MXFP8-MXFP4。

### 二进制配套关系

标准 `models/deepseek_v4` 路径依赖镜像里预装的三层组件：

- `custom_transformer` vendor：QLI、QLI Metadata、Compressor、SAS，来自 `ops-transformer`
- `customize` vendor：IndexerCompressEpilog、partial rotary 等，来自 `cann-recipes-infer`
- `custom_ops` wheel：注册 `torch.ops.custom.*` 并提供 GE converter
