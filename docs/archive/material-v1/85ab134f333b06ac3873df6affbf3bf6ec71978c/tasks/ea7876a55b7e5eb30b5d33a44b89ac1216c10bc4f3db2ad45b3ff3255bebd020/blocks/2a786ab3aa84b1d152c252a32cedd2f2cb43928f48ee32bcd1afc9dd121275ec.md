## 对照上游后，当前还缺的关键契约

优先级从高到低：

1. FULL dummy run 仍可能通过 stale block-table 行写入已释放并重新分配的 block。

   当前 v0.26 的 `move_row()` 不清空源行：[block_table.py](<redacted:local-path:7ea59ec448e0>:142)。Ascend dummy path 又直接提交这些行，并且只在 capture 阶段重建 capture metadata：[model_runner_v1.py](<redacted:local-path:72b57aaf9356>:3260)。

   上游后来专门修复了“dummy Mamba 写 stale row”：清空 `move_row` 源行、dummy table 置零，并在 FULL replay 重新 staging metadata。这个机制和“前一个请求结束后，后一个请求被历史污染”高度吻合。[上游 6fbbcf215](https://github.com/vllm-project/vllm/commit/6fbbcf2151c34cd9313c223b8cbf19afa77f2ea6)

2. Hybrid prefix hit 只裁剪第一个 full-attention group。

   实际 rank32 capture 有 5 个 `AscendMLAAttentionSpec` group、1 个 draft `FullAttentionSpec` group 和 14 个 Mamba group：[capture 中的 draft full group](<redacted:local-path:879ecdf73c44>:2160)、[Mamba group](<redacted:local-path:879ecdf73c44>:2529)。

   上游已经证明旧 coordinator 在多 full-type group 下可能保留超过共同命中边界的 block list，随后请求会把不属于自己的 prefix block 当成自己的并写入。这对当前拓扑是直接适用的，不只是理论风险。[上游 a5836312d](https://github.com/vllm-project/vllm/commit/a5836312dfe895dbd8dd88693f79a6d81026eeef)

3. Mamba align state 可能以错误的 token boundary 加入 prefix cache。

   投机 decode 会让 state 覆盖尚未接受的 draft token，但旧逻辑仍可能把它按完整 prefix boundary 缓存。下一个请求命中后恢复的是“状态位置”和“哈希声称位置”不一致的 recurrent state。这更容易表现为稳定精度下降，而不是物理 NaN。[上游 8472b0161](https://github.com/vllm-project/vllm/commit/8472b0161acde55aa6cd4008703a20c986040a17)

4. 当前 compact physical layout 仍不是一个闭合契约。

   Ascend 让 target MLA 与 Mamba 共享 raw tensor，但 MLA 被切成全局 compact K/V 区域，Mamba 被切成全局 compact conv/recurrent 区域：[MLA view](<redacted:local-path:72b57aaf9356>:4225)、[Mamba view](<redacted:local-path:72b57aaf9356>:4304)。它们都没有遵守 scheduler 所规划的统一 physical page stride。

   `419c315` 只隔离了 draft GQA：[patch_kv_cache_utils.py](<redacted:local-path:fc21ac7f3c87>:127)，没有消除 target MLA/Mamba 之间同类结构风险。

## 建议的系统性方案

短期正确方案不是强推首轴非连续，而是建立通用的“layout capability”：

- `CONTIGUOUS_DIM0_ONLY`：当前 KDA/GDN causal-conv、draft GQA/FIA。
- `STRIDED_DIM0`：已经支持 stride0 的 MLA preprocess/prolog。
- 只有物理寻址规则相同的 layer 才能共享 backing。
- KDA/Mamba、target MLA、draft GQA 分到各自兼容的 compact pool；容量规划统一计算所有 pool 的每-block 字节数。
- 删除 K3 模型名判断，改由 backend/operator capability 决定是否隔离。

长期再给 causal-conv、recurrent KDA/GDN 增加显式 `state_block_stride`，等所有写、读、copy、zero、offload 都支持后，再切到上游 page-first 布局。

下一步验证顺序建议：

1. 先做纯静态 layout manifest：输出每个 cache view 的 base、storage offset、shape、`stride(0)`、自然 block bytes、物理 block stride，并对真实 block-table ID 做区间重叠断言。

2. 用当前 5 MLA + 1 draft full + 14 Mamba 拓扑做 CPU coordinator 回归，验证 `a5836312d` 前后是否返回越界 block list。

3. 对 exact writer/victim 用例分别做三个单变量 A/B：

   - 只移植 `6fbbcf215` 的 stale-row/FULL replay 语义；
   - 只移植 `a5836312d`；
   - 只启用 capability-based pool 隔离。

4. `8472b0161` 作为必需正确性修复单独验证 prefix replay logits；不要和物理污染修复混成一个 patch。

如果只选一个最先做的运行时 A/B，我会选 `6fbbcf215`；如果只选一个必须重构的方向，我会选 capability-based physical pool planner。前者最符合“历史请求触发”，后者才是终结 backing collision 补丁链的办法。
