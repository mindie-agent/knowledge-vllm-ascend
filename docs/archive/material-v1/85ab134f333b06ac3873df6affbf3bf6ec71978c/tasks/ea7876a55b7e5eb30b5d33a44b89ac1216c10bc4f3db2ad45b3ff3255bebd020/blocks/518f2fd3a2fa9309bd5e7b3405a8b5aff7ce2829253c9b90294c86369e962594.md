## 3. 旧公共 pool 的真实物理布局

而是全局 SoA：


不同 layer 对同一块 raw storage 的解释是：

| 物理区间 | KDA 解释 | MLA 解释 |

| `46,080 B/block` | conv state | padding |

| `49,152 B/block` | padding | rope/K-PE |

- KDA 的 conv 首轴连续；
- KDA recurrent state 首轴连续；
- MLA K 首轴连续；

## 5. group 与物理 pool 是怎么对应的

加入 GQA 后，最大 group 长度是 5，所以普通 vLLM allocator 创建 5 个 raw pool：

```text
T0 T1 T2 T3 T4
```

每个 group 的第 i 个 layer 使用 `T_i`：

```text
G0 MLA:  layer3  -> T0
         layer23 -> T1
         ...
         layer83 -> T4

G5 GQA:  layer93 -> T0
         layer94 -> T1
         ...
         layer97 -> T4
```

也就是说：

- 同一个 group 内的 5 个 layer：
  - 共享同一张 block table；
  - 使用相同的 block ID 序列；
  - 但各自在不同的 `T0...T4` 里存数据。
- 不同 group：
  - 有独立 block table；
  - 从同一个全局 `BlockPool` 分配 block；
  - 同时存活的 block ID 按设计不会重复；
  - 但相同 slot 的 layer 会共享同一个 raw pool。

对应 allocator 逻辑见 [kv_cache_utils.py](<<redacted:local-path:b8dd889167fe>/vllm-core-v0.26.0/vllm/v1/core/kv_cache_utils.py:1396>)。Coordinator 确实只创建一个全局 BlockPool，再为每个 group 创建 manager，见 [kv_cache_coordinator.py](<<redacted:local-path:b8dd889167fe>/vllm-core-v0.26.0/vllm/v1/core/kv_cache_coordinator.py:90>)。

所以答案是：

- 同一个 group 内的 layer 共享 block ID；
- 不同 group 不共享同一组 block ID；
- 但不同 group 可能共享同一个 raw tensor；
- 安全性的前提是不同 spec 对 block ID 到物理地址的解释必须一致。

## 6. GQA K 的 49,152 B 到底怎么来的

当前 draft：

```text
global Q heads  = 64
global KV heads = 16
TP               = 16
head_dim         = 64
dtype            = BF16 = 2 B
scheduler block  = 384 tokens
```

本 rank KV heads：

\[
16/16=1
\]

因此单 token、单层、本 rank 的 K：

\[
1 \times 64 \times 2=128\ \text{B}
\]

一个 384-token scheduler block：

\[
384 \times 128=49,152\ \text{B}=48\ \text{KiB}
\]

V 完全相同：

```text
GQA K = 49,152 B
GQA V = 49,152 B
GQA KV page = 98,304 B
```

FIA 内部使用 128-token kernel block，因此也可以写成：

```text
一个 128-token K micro-page：
128 × 1 × 64 × 2 = 16,384 B

一个 scheduler block 有 3 个 micro-page：
3 × 16,384 = 49,152 B
```

注意 49,152 B 只算一层 GQA 的 K。整个 5-layer GQA group：

```text
5 × K       = 245,760 B
5 × (K + V) = 491,520 B
```

## 7. 为什么旧的直接共池会碰撞

在没有独立 GQA pool 的旧直接共池解释里，GQA 的实际 KV 只有 98,304 B，但其 spec 被 pad 到公共的 488,448 B。

worker 会把 GQA K/V 放在 raw pool 的尾部：

```text
[ B × 390,144 padding ][ B × 49,152 GQA K ][ B × 49,152 GQA V ]
```

而 MLA/KDA 的解释是：

```text
[ B × 46,080 ][ B × 393,216 MLA-K/SSM ][ B × 49,152 MLA-rope ]
```

因此：

- GQA V 与 MLA rope lane 的 base 和 stride 都一致；
- GQA K 落在 MLA-K/SSM 大 lane 的尾部；
- 但 GQA K 的 block stride 是 49,152 B；
- MLA-K/SSM 的 block stride 是 393,216 B。

所以即使：

```text
target group block id != GQA group block id
```

两套不同的：

```text
base + block_id × stride
```

仍可能算到同一段物理 backing。

这不是因为 K/V 交错，也不是因为首轴非连续。两边的 K、V 都是首轴连续的；问题是不同 compact stride 被放进了同一个物理 lane。

历史 dump 中：

```text
target layer 23 / group 0 / block 5224
draft layer 94 / group 5 / block 1969
```

就是不同 group、不同 block ID，却落到了相同物理 backing。

## 8. 如果“之前”特指 419c 的 GQA 独立池版本

那个版本没有改变上述 20 个 scheduler group：

- 仍然只有一个 GQA group：`G5`
- GQA group 内仍然是 5 个 layer 共享一张 block table

它只改变物理 tensor：

```text
5 个 regular common pools：每个 page 488,448 B
5 个 GQA isolated pools： 每个 page 98,304 B
```

每个 GQA layer 一个独立的 98,304 B backing，并在里面分成：

```text
[all K blocks: 49,152 B/block]
[all V blocks: 49,152 B/block]
```

所以它是：

```text
1 个 GQA scheduler group
5 个 GQA layer physical pools
```

不是 5 个 GQA group，更不是 6 个 GQA group。

最后，49,152 B 是当前 `TP16 + block_size=384` 下的结果，不是固定模型常量。通用公式是：

\[

=
block\_size
\times \max(1,16/TP)
\times 64
\times 2
