```text
[conv]
[MLA K / Mamba SSM]
[MLA V]
[GQA K]
[GQA V]
```

不是“复用原公共物理页”，而是给公共页追加两个新 lane，把页从 `488,448 B` 扩成 `586,752 B`。地址上可以隔离，但它属于扩页方案，不是我们想要的对齐方式。

正确方向应该是：GQA 不新增区域，而是复用 `MLA K / Mamba SSM` 的 `393,216 B` lane。

现有 backing 实际是全局 SoA：

```text
[所有 parent 的 conv]
[所有 parent 的 MLA-K / Mamba-SSM]
[所有 parent 的 MLA-V]
```

不是每个 parent 都物理连续地重复 `[conv][SSM][V]`。代码现在也是先跳过整段 conv，再切整段 MLA K 和 MLA V；Mamba 则从开头依次取 conv、SSM。[model_runner_v1.py](<redacted:local-path:8cc75f65b2a9>:4225)

对于某个 parent `p`，其 SSM lane 为：

```text
393,216 B = 24 × 16,384 B
```

其中 `16,384 B` 是一个 128-token GQA K 或 V kernel page。正确划分应当是：

```text
MLA-K / Mamba-SSM lane of parent p, 393,216 B

┌──────────────────────── 196,608 B ────────────────────────┐
│ K(s0) │ K(s1) │ K(s2) │ K(s3)                            │
│ 49,152│ 49,152│ 49,152│ 49,152                           │
└────────────────────────────────────────────────────────────┘
┌──────────────────────── 196,608 B ────────────────────────┐
│ V(s0) │ V(s1) │ V(s2) │ V(s3)                            │
│ 49,152│ 49,152│ 49,152│ 49,152                           │
└────────────────────────────────────────────────────────────┘
```

也就是：

```text
conv lane       ：GQA 不使用
SSM / MLA-K lane：[4 个 GQA K][4 个 GQA V]
MLA-V lane      ：GQA 不使用
```

因为每个 384-token GQA block 是：

```text
K = 49,152 B = 3 × 16,384 B
V = 49,152 B = 3 × 16,384 B
K + V = 98,304 B
```

所以恰好：

```text
4 × 98,304 = 393,216 B
```

一张 parent 公共页可以容纳 4 个 GQA 逻辑 block，而物理页大小仍然是 `488,448 B`。GQA 真正没使用的只有：

```text
conv + MLA-V = 46,080 + 49,152 = 95,232 B
```

#### 保证首轴连续的映射

令：

```text
U = 16,384 B
b = 一个 384-token GQA 逻辑 block
(p, s) = allocator 为 b 分配的 parent 和 subslot
s ∈ {0,1,2,3}
c ∈ {0,1,2}  # 384 / 128 三个 kernel block
```

在 SSM lane 中建立两个普通连续 view：

```text
K_base = SSM_lane_base
V_base = SSM_lane_base + 12U   # 196,608 B
```

block table 中写入：

```text
j(p,s,c) = 24p + 3s + c
```

于是：

```text
K address = K_base + jU
V address = V_base + jU
```

parent 0 的局部布局就是：

```text
kernel-page  0..2   -> K(s0)
kernel-page  3..5   -> K(s1)
kernel-page  6..8   -> K(s2)
kernel-page  9..11  -> K(s3)

kernel-page 12..14  -> V(s0)
kernel-page 15..17  -> V(s1)
kernel-page 18..20  -> V(s2)
kernel-page 21..23  -> V(s3)
```

这里 K view 和 V view 自身都是普通连续 tensor，不需要首轴 `as_strided`。跨 parent 时 block ID 有空洞，但 paged-attention 本来就允许 block table 中的 ID 不连续；“block ID 不连续”和“tensor 首轴非连续”是两回事。

#### 这也修正了之前记录的交错公式

之前的方案是：

```text
K0,V0,K1,V1,...
```

并使用：

```text
[24p+2s, 24p+8+2s, 24p+16+2s]
```

数学上可以通过错位 K/V view 实现，但没有必要，而且不符合我们现在确认的“K 一整块、V 一整块”的布局。更合适的是上面的：

```text
[K(s0)..K(s3)][V(s0)..V(s3)]
kernel IDs = [24p+3s, 24p+3s+1, 24p+3s+2]
```

#### scheduler 侧不能只改 reshape

这里仍然必须保持：

```text
scheduler-visible block_size = 384
kernel block_size = 128
```

不能把 GQA `FullAttentionSpec.block_size` 改成 `1536`。`4:1` 是物理 parent/subslot 关系，不是 scheduler token block 的定义。

因此 allocator 还必须具备以下语义：

- GQA block 占一个 `(parent, subslot)`。
- 同一 parent 最多容纳 4 个 GQA block。
- MLA 或 Mamba block 占整个 parent。
- parent 中只要存在任意活跃 GQA subslot，MLA/Mamba 就不能取得该 parent。
- GQA 五层共享同一个逻辑 block table，并在五个 backing pool 上使用相同 `(p,s)`。
- zero、copy、swap、prefix-cache refcount、recompute 都必须按同一布局描述映射，不能继续假定“一逻辑 ID 等于一整页”。

所以最终结论是：追加 `[GQA K][GQA V]` 不应作为最终方案；把 block size 改成 1536 也不对。正确方案是保持 384，在原 `MLA-K/Mamba-SSM` lane 内采用“四个 K 连续区 + 四个 V 连续区”的 parent/subslot 布局。

对，你这个判断是对的。当前“把 GQA K/V 都交错塞进第二条 lane”的 4:1 方案需要推翻。

正确的共享 backing 是三条 SoA lane，而不是额外追加 GQA K/V：

| lane | MLA | Mamba | GQA |
|---|---|---|---|
| T1：46,080 B | padding | conv | padding |
| T2：393,216 B | NoPE K | SSM | K + padding |
| T3：49,152 B | PE/V lane | padding | V |

TP16、384 token 下：

- GQA K = 49,152 B
- GQA V = 49,152 B
- 所以 `K packing ratio = 393216 / 49152 = 8`
- 但 `V packing ratio = 49152 / 49152 = 1`

而当前 4 倍是通过：

```text
393216 / (GQA K + GQA V)
= 393216 / 98304
= 4
```

算出来的，本质就是强行把 K/V 一起放进 T2。当前代码也确实这么做了：[patch_kv_cache_utils.py](<<redacted:local-path:b8dd889167fe>/vllm-ascend-v0.26.0rc-dspark-mla-linear-ci/vllm_ascend/patch/platform/patch_kv_cache_utils.py:76>) 选择了单一 SSM lane，[model_runner_v1.py](<<redacted:local-path:b8dd889167fe>/vllm-ascend-v0.26.0rc-dspark-mla-linear-ci/vllm_ascend/worker/model_runner_v1.py:4645>) 再把 V 做成相对 K 偏移一个 kernel page 的重叠 view。这和原有三 lane 契约 [model_runner_v1.py](<<redacted:local-path:b8dd889167fe>/vllm-ascend-v0.26.0rc-dspark-mla-linear-ci/vllm_ascend/worker/model_runner_v1.py:4908>) 是冲突的。

核心结论是：当前 `488,448 B` 公共页下，K/V 的 packing ratio 分别是 8 和 1；而 FIA 只有一张 K/V 共用 block table，因此不能在保持首轴连续的同时正确表达这两个映射。

所以后续应该：

- 删除当前 `kv_block_id_stride=2` 和 T2 内 K/V 交错方案。
- 保持 scheduler 可见 block size 为 384，不修改 `FullAttentionSpec.block_size`。
- 将 layout 显式描述为独立的 K lane 和 V lane，并增加 `k_pack_factor == v_pack_factor` 的规划期校验；当前配置应直接校验失败。
- 在“不独立建池、不支持首轴非连续”的约束下，唯一不改 FIA 接口的共享 padding 方案，是把 V lane 扩到 `393,216 B`，形成：

```text
conv 46,080
K/SSM 393,216
V     393,216
总页  832,512 B
```

这样 GQA K/V 都是 8:1，可以在 scheduler 以下做 parent/subslot 映射，不改变 384-token 语义。但代价是公共页明显膨胀。

这也意味着之前的 `0.303 GiB` GQA waste 和合计 `<1 GiB` 结论不再成立；它依赖错误的 T2 内 K/V 交错。如果维持原页并做朴素 1:1 padding，1Mi、5 个 GQA layer/pool 的浪费是约 `4.9615 GiB/TP rank`。若扩 V lane 做正确的 8:1，GQA 自身浪费仅约 `0.0757 GiB`，但五个公共 pool 的页膨胀成本约 `4.3755 GiB`。因此这里没有一个“直接照搬 Qwen3.5 padding”且没有代价的方案；Qwen3.5 的前提是 dense K/V lane 本来就是对称的。
