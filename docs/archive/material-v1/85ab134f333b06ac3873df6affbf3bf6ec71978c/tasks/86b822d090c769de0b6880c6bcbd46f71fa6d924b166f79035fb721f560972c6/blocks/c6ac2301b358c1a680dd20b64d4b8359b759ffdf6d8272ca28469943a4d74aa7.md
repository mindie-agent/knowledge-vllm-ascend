## P1

1. `chat_template_kwargs` 信任边界不完整。

   [patch_kimi_k3_chat_params.py:40](<redacted:local-path:25157a6eee66>:40) 的 denylist 未覆盖 `conversation`、`add_generation_prompt`、`return_tensors`、`padding`、`truncation`、`max_length` 等。[renderer:159](<redacted:local-path:5e5f8b31b75c>:159) 又将合并后的 kwargs 直接透传：

   - `conversation` 会造成重复关键字 `TypeError`；
   - `return_tensors` 会破坏 flat `list[int]` 契约；
   - 截断或关闭 generation prompt 可切断 K3 结构标记。

   应在所有 server/request defaults 合并后采用严格 allowlist，并固定 `tokenize=True`、`return_dict=False`、`add_generation_prompt=True`，禁止 padding/truncation/tensor 输出。顶层自定义 `chat_template` 也不应在 [renderer:149](<redacted:local-path:5e5f8b31b75c>:149) 静默丢弃，应明确拒绝。

2. 漏掉 `structured_outputs`。

   [chat params:101](<redacted:local-path:25157a6eee66>:101) 只拒绝 `response_format`。vLLM 0.23.0 的直接 `request.structured_outputs` 仍会从生成首 token 起施加 grammar，与 K3 必需的 XTML envelope 冲突。应同步拒绝，直到有按 response phase 生效的 grammar。

3. `tools + tool_choice:null` 被错误拒绝。

   [chat params:106](<redacted:local-path:25157a6eee66>:106) 与 [parser:163](<redacted:local-path:b28d94adae9a>:163) 都拒绝显式 `null`。vLLM 0.23.0 通用契约将 `None` 视为 auto；这也是 OpenAI tools 的默认语义。最小修正是局部解释为 auto，不必修改请求对象。

4. XTML “严格解析”仍存在静默兼容分支。

   - [kimi_k3_xtml.py:350](<redacted:local-path:9c8a59f4728f>:350)：final 输出缺失 `THINK_START` 不报错。
   - [kimi_k3_xtml.py:377](<redacted:local-path:9c8a59f4728f>:377)：thinking 关闭时缺失 `RESPONSE_START` 也不报错。
   - 缨失 `THINK_END` 或 `RESPONSE_END` 时返回 `protocol_complete=False` 的 snapshot，但适配器从不检查该字段。

   这会把 plain text、未闭合 reasoning 或半截 response 当正常结果，正是应消除的隐式 fallback。应至少在 `finish_reason=stop` 时要求完整 envelope；`length` 可保留合法前缀，因此最好把 finish reason 传入严格校验。

5. parser 输出错误被误报为 HTTP 400。

   [kimi_k3_xtml.py:52](<redacted:local-path:9c8a59f4728f>:52) 继承 `ValueError`，vLLM 0.23.0 会把它归类为客户端 Bad Request。但 malformed 模型输出、required 未调用属于生成/服务错误。应拆分：

   - 请求模式错误：`VLLMValidationError`；
   - 模型协议错误：`GenerationError` 或等价 5xx 类型。

6. forced tool 的 stream/non-stream content 契约不一致。

   [parser:481](<redacted:local-path:b28d94adae9a>:481) 可同时返回 response content 和工具调用；流式会发出该 content，但 vLLM 0.23.0 的 named/required 非流式 serving 分支硬编码 `content=""`。应选择并统一语义；K3 协议允许 response block 后接 tools，建议保留 content。
