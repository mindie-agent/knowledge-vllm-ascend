看完当前 [架构稿](https://github.com/vllm-ascend-workspace/vllm-ascend-workspace/issues/195)，**整体骨架已经清楚，真正还可能影响架构或范围的，主要剩这三点。**

### 1. 六端支持，是否包含跨 Harness 协作

这两种目标的工程范围差别很大：

- Cursor 中的 vLLM 会话，与 Cursor 中的 Triton 会话协作。
- Cursor 中的 vLLM 会话，与 Kimi 中的 Triton 会话协作。

**我的建议：先让六端各自具备完整体验，跨 Harness 会话互通作为后续扩展。** 领域资产共用；跨客户端通信会进一步涉及身份、会话寻址和消息接续，需要单独设计。目前讨论里没有明确要求这一层。

### 2. 领域内部的 Skill，还要不要进一步按需发现

我们已经确定领域隔离，但 vLLM 域本身还会包含模型适配、部署、调试、profiling、量化等大量能力。**如果进入这个领域就暴露全部 Skill description，原来的问题仍可能在域内出现。**

我的建议是：

> **简短领域入口 → 按任务发现相关能力 → 加载具体 Skill。**

领域内部可以按主题组织能力，知识检索也可以限定项目、版本和主题；这些内部分类不必都变成新的会话领域。需要定的是“按需发现”的架构要求，各端如何实现后面再看。

### 3. 领域配置与用户已有配置，谁决定最终加载范围

例如用户原本安装了很多全局 Skill 和 MCP。安装我们的领域插件之后，它们是否仍然全部进入领域会话，目前没有明确。

**我的建议：领域会话的有效能力组成应当明确：**

> **用户选定的通用基础能力 + 当前领域按需能力 + 必要协作工具。**

适配器负责兑现这个范围，用户原有全局设置保持不被静默修改。否则我们自己的包虽然拆开了，实际会话仍可能加载很多无关内容。

---

**这三点补齐后，我认为架构层面就基本能定了。** GUI、具体 API、进程拆分和仓库目录继续留到各端实现；成果集成、共享代码/NPU、知识维护这些职责，当前稿已经有方向，无需现在展开。
