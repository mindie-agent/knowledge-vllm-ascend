### vaws 当前最关键的缺口

1. **现有 serving 是单机流程。** TP16×DP4 会按单个宿主机需要 64 张卡计算；PD 流程也是逐个启动独立服务，不是 K3 四机共同加入一个分布式作业。[设备计算](<redacted:local-path:5bdb5d78c7d3>:340)、[PD 启动流程](<redacted:local-path:d4c62b5bb585>:378)

2. **停止主 PID 不等于清完整个服务。** 当前清理仍围绕记录的主 PID，覆盖不了历史上自行 `setsid` 的 worker/EngineCore 残留；`Unexpected HELLO`、旧 coordinator 占端口仍可能重现。[停止实现](<redacted:local-path:8c52eefd9436>:125)

3. **启动成功的判定太浅。** 默认超时 300 秒，只检查进程、`/health` 和 `/v1/models`。K3 历史上单个 rank 加载就花过 783.8 秒，图捕获可能 15–20 分钟；也发生过 health=200、引擎却不再产 token。[就绪检查](<redacted:local-path:214707ae4473>:448)

4. **通用环境管理不等于 K3 配方。** `VLLM_VERSION`、完整插件列表、Gloo 网卡、native-compat、完整算子产物仍需显式固定。最新的 [#65 本机镜像选择](https://github.com/maoxx241/vllm-ascend-workspace/pull/65) 能减少重复下载，但“最新镜像”不等于“K3 已验证环境”。

我的建议是：**采用 vaws 做代码、环境和运行记录的底座，同时补 K3 固定启动配方、四机联合生命周期、按归属清理残留、分阶段超时及真实请求验收。** 仅把现有 SSH 命令换成 remote-dev MCP，收益会很有限。

本次仅做历史检索和源码核对，没有改动或重启远端服务，也没有把上述可避免性判断当成实测结果。

## 1. vaws 的并行问题具体在哪里？

它现在并非不支持并行：已经有独立 session、worktree、容器、日志和本地租约。问题是这些机制还不能保证多个独立任务互不干扰。

| 当前边界 | 对多任务的影响 |
|---|---|
| 租约主要保存在各工作区本地 | 不同 clone、不同开发机的任务可能各自认为同一张卡可用 |
| 跨 agent 协调是可选的 | 手工 SSH、其他客户端可以绕过 |
| 队列只放行队头 | 队头等 16 卡时，即便空闲 8 卡，后面的 2 卡任务也不能运行 |
| NPU 租约绑定 session，停服务不释放 | 一个任务已经回去改代码，仍可能占着逻辑租约 |
| 容器使用 host 网络、privileged，并共享挂载 `/home`、`/tmp` 等 | 独立容器不等于端口、设备和文件都隔离 |

这些是当前[租约规则](<redacted:local-path:277d5d995552>:58)、[队列实现](<redacted:local-path:499fb43a699a>:754)和[容器配置](<redacted:local-path:7569a04be1d7>:1919)的实际边界，不只是使用习惯问题。

### 我建议怎么解决

关键是把“开发任务”和“占用硬件的一次运行”拆开：

- **开发任务长期存在**：独立代码目录、分支、任务 ID，可以同时写代码、检索、审查。
- **远端运行按需申请资源**：启动验证才申请卡、端口和容器；整段验证结束并确认进程、显存释放后归还，而不是等整个任务删除。
- **统一资源分配入口**：不同工作区、不同客户端共享同一份资源状态。受管启动必须持有有效租约；仍允许的手工入口应明确属于协作边界，不能宣称强隔离。
- **改善排队策略**：允许不会延误已预约大任务的小任务先运行，同时防止大任务长期饿死。K3 四机任务要整组预留，不能拿到两台后一直占着等另外两台。
- **按运行隔离可写内容**：源码、构建目录、日志、临时文件和端口各自独立；权重、镜像及内容寻址缓存可以共享。

不过，**一套 K3 已占满四机 64 卡时，另一套完整 K3 就只能排队**。合理目标是“开发并行、小验证穿插、大验证有序运行”，不是让调度器创造额外硬件。

## 2. submodule 对 agent 确实不够友好吗？

**对你这种频繁切分支、跨 vLLM/Ascend 修改、多任务并行的场景，确实增加了明显负担。**

主要不是 agent 看不懂代码，而是需要同时处理多层 Git 状态：

- 父仓库记录的是子仓库提交指针，业务代码的 diff、commit、push 在子仓库里。
- 默认 `submodule update` 会把子仓库检出到父仓库记录的提交，通常处于 detached HEAD。[Git 官方说明](https://git-scm.com/docs/git-submodule)
- 父仓库切换分支，不等于两个业务仓库的开发分支都按预期切换。
- 再叠加 worktree，复杂度更高；Git 官方目前仍提醒，含 submodule 的 superproject 多工作树支持不完整。[Git worktree 限制](https://git-scm.com/docs/git-worktree#_BUGS)

vaws 还有一个具体风险：`ensure_worktree` 的已有目录复用路径会再次执行递归 `submodule update`。这可能切回父仓库锁定版本，或因本地修改而失败；不能把它当成无副作用的“恢复任务”。[对应代码](<redacted:local-path:7acb72900f59>:340)

## 3. 我会选择的改造方向

**把 vaws 从“业务代码的父仓库”变成“独立的开发与运行工具层”。**

具体来说：

- Agent 默认就在任务自己的 `vllm-ascend` 仓库中工作；需要修改 vLLM 时，再关联对应的独立仓库。
- vaws 支持登记任意仓库路径，不强制它们必须是自己的 submodule。
- 用运行清单记录 `vllm SHA + ascend SHA + 未提交内容快照 + 镜像/算子产物身份`，保留目前 submodule 提供的版本配对能力。
- 每任务使用独立 worktree；对仍有递归 submodule、生命周期兼容性未验证的仓库，可采用独立 clone。
- CATLASS 这类业务仓库内部的依赖 submodule 可以保留，不需要一刀切拆掉。

**优先级上，我会先补资源调度和运行隔离，再增加“外部仓库模式”。** 现有 submodule 模式保留给固定版本复现；你的高频开发任务用独立仓库模式。这样不必推倒 vaws，也不会把两类问题混在一起解决。

以上是源码核对后的改造建议，本次没有修改实现。
