### What this PR does / why we need it?

This PR adds production Kimi K3 support on top of
`releases/v0.23.0`.

The implementation includes:

- local Transformers-compatible Kimi K3 text, vision, and processor
  configurations, plus vLLM model registration;
- the exact Kimi K3 SiTU activation and decomposed routed/shared MoE
  execution, avoiding kernels that fuse SwiGLU;
- Kimi K3 MLA without RoPE, with the new sigmoid output gate applied
  before `o_proj`;
- KDA prefill through AscendC and decode/speculative decode through
  Triton, including cache-layout and attention-metadata handling;
- BF16, ModelSlim W4A8, and packed MXFP4 weight-loading support;
- focused CPU and Ascend NPU coverage for the new model, MLA, MoE,
  quantization, and KDA paths.

#### Relationship to existing PRs

The first commit carries the final source delta from #141 because Kimi
K3 prefill depends on its AscendC operators:

- `chunk_kda_fwd`
- `kda_gate_cumsum`
- `kda_layout_swap12`
- the corresponding `chunk_gated_delta_rule_fwd_h` updates

That commit is tree-equivalent to the current #141 head. Since #141 is
currently an open cross-repository PR, this draft includes the operator
delta so that the Kimi K3 implementation can be reviewed and tested as
a complete stack. If #141 lands first, the first commit will be dropped
or rebased onto the merged commit.

This implementation intentionally does not use #142. That PR is
explicitly a fake-weight, text-only smoke adapter whose KDA/MLA paths
are lightweight rather than production implementations.

No new KDA backend-selection environment variable is introduced.
Supported prefill shapes use AscendC directly; Triton is used for
decode/speculative decode. The standalone Triton chunk test is retained
only as numerical reference coverage and is not a production prefill
fallback.

### Does this PR introduce _any_ user-facing change?

Yes.

Users can load the Kimi K3 configuration and instantiate the registered
`KimiK3ForCausalLM` and `KimiK3ForConditionalGeneration` model paths on
vLLM Ascend.

The PR also exposes the KDA custom operators required by the production
prefill path under `torch.ops._C_ascend`.

Existing non-Kimi models keep their current activation, RoPE, KDA, and
quantization behavior.
