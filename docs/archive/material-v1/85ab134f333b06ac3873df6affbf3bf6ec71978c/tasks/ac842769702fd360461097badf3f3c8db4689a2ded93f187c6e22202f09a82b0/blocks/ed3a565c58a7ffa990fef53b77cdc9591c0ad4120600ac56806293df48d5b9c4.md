## 1. 总体布局

对每个 raw tensor `Tᵢ`，内存按 SoA 组织：

```text
Tᵢ =
[所有 block 的 L0]
[所有 block 的 L1]
[所有 block 的 L2]
[所有 block 的 L3]
```

也就是说：

- 每一行/lane 是一个连续 Tensor。
- 每一列是同一个物理 block/page。
- 不是 `[block0 的 L0-L3][block1 的 L0-L3]...` 这种逐 page 交错布局。

TP16 下：

| Lane | 每 block 大小 | Mamba/KDA | MLA | DSpark GQA |
|---|---:|---|---|---|
| L0 | 46,080 B | conv state | PAD | PAD |
| L1 | 393,216 B | recurrent/SSM state | K-NoPE | PAD |
| L2 | 49,152 B | PAD | K-RoPE | GQA-K |
| L3 | 49,152 B | PAD | PAD | GQA-V |
| 合计 | **537,600 B** |  |  |  |

因此三类逻辑 page 分别是：

- Mamba page：使用 `L0 + L1`。
- MLA page：使用 `L1 + L2`。
- GQA page：使用 `L2 + L3`。

共享关系是：

```text
Mamba recurrent.data_ptr == MLA NoPE.data_ptr
MLA RoPE.data_ptr         == GQA K.data_ptr
GQA V                     == 独立追加的 L3
```

## 2. TP16 shape 与 page size 计算

已敲定参数：

```text
TP = 16
scheduler block_size = 384 tokens
kernel block_size = 128 tokens
num_speculative_tokens = 7
dtype(MLA/GQA/conv) = BF16 = 2 B
dtype(recurrent) = FP32 = 4 B
```

### L0：KDA conv state

K3 配置：

```text
num_heads = 96
head_dim = 128
short_conv_kernel_size = 4
```

每 TP rank：

```text
local_conv_dim
= 3 × num_heads × head_dim / TP
= 3 × 96 × 128 / 16
= 2,304
```

状态长度：

```text
state_len
= short_conv_kernel_size - 1 + num_speculative_tokens
= 4 - 1 + 7
= 10
```

单 block shape：

```text
(2,304, 10)
```

根据 `is_conv_state_dim_first()` 也可能表现为 `(10, 2,304)`，元素数不变。

大小：

```text
2,304 × 10 × 2 B
= 46,080 B
```

整体 view：

```text
(N, 2,304, 10) BF16
```

其中 `N=num_blocks`。

### L1：Mamba recurrent / MLA K-NoPE

Mamba recurrent shape：

```text
local_heads = 96 / 16 = 6
shape = (6, 128, 128)
dtype = FP32
```

大小：

```text
6 × 128 × 128 × 4 B
= 393,216 B
```

MLA NoPE 的等价 shape：

```text
scheduler view: (N, 384, 1, 512)
kernel view:    (3N, 128, 1, 512)
dtype: BF16
```

大小：

```text
384 × 1 × 512 × 2 B
= 393,216 B
```

两者大小完全相同，所以共享 L1。

### L2：MLA K-RoPE / GQA-K

MLA RoPE：

```text
scheduler view: (N, 384, 1, 64)
kernel view:    (3N, 128, 1, 64)
dtype: BF16
```

大小：

```text
384 × 1 × 64 × 2 B
= 49,152 B
```

DSpark GQA 全局 `num_key_value_heads=16`，TP16 后每 rank 为 1 个 KV head：

```text
GQA-K shape = (3N, 128, 1, 64)
GQA-K bytes = 384 × 1 × 64 × 2
            = 49,152 B
```

所以 GQA-K 直接复用 L2。

### L3：GQA-V

```text
GQA-V shape = (3N, 128, 1, 64)
GQA-V bytes = 49,152 B
```

现有三个 lane 不再有安全空间容纳 V，因此追加 L3。

### 最终 page size

原有成熟 page：

```text
L0 + L1 + L2
= 46,080 + 393,216 + 49,152
= 488,448 B
```

追加 GQA-V：

```text
final page_size
= 488,448 + 49,152
= 537,600 B
```

即每个 raw pool 的 page 增加约 `10.06%`，但 raw tensor 数量仍是 5，不增加第六个 pool。

L0 = 46,080 × scale

## 4. 地址计算

设：

```text
N  = num_blocks
Bᵢ = raw tensor Tᵢ 的基地址
p0 = 46,080
p1 = 393,216
p2 = 49,152
p3 = 49,152
```

TP16 下各 lane 基地址：

```text
L0_base = Bᵢ
L1_base = Bᵢ + N × p0
L2_base = Bᵢ + N × (p0 + p1)
L3_base = Bᵢ + N × (p0 + p1 + p2)
```

block ID 为 `b` 时：

```text
addr(L0, b) = L0_base + b × p0
addr(L1, b) = L1_base + b × p1
addr(L2, b) = L2_base + b × p2
addr(L3, b) = L3_base + b × p3
```

因此实际 pointer offset 是：

```text
conv                = base
recurrent / NoPE    = base + N × 46,080
RoPE / GQA-K        = base + N × 439,296
GQA-V               = base + N × 488,448
```

所有导出的 conv、recurrent、NoPE、RoPE、GQA-K、GQA-V view 都是 contiguous。

## 5. 384 调度块到 128 kernel block 的映射

调度器、Prefix Cache、BlockPool 看见的始终是：

```text
physical/scheduler block_size = 384
```

Attention kernel 使用：

```text
kernel block_size = 128
blocks_per_phys_block = 384 / 128 = 3
```

物理 block ID `b` 在 worker block table 中展开为：

```text
b -> [3b, 3b + 1, 3b + 2]
```

token 在该物理 block 内的位置 `x`：

```text
kernel_subblock = floor(x / 128)
kernel_offset   = x % 128
kernel_block_id = 3b + kernel_subblock
slot            = kernel_block_id × 128 + kernel_offset
```

Mamba group 不做该展开：

```text
kernel_sizes = [0]
```

它仍直接使用一个 384-token 物理 block 对应的一组 conv/recurrent state。

## 6. KV group 怎么分

实际层数：

```text
MLA/full-attention = 24 层
KDA/Mamba          = 69 层
DSpark GQA         = 5 层
总计               = 98 层
```

上游 grouping 规则：

```text
group_size = min(24, 69, 5) = 5
```

然后按 family 分组，并使用 `layers[i::num_groups]` 的跨层步进组织方式：

- MLA：`ceil(24/5)=5` 组，大小为 `5,5,5,5,4`。
- Mamba：`ceil(69/5)=14` 组，大小为十三个 5 加一个 4。
- GQA：`ceil(5/5)=1` 组，大小为 5。
- 总数：`5 + 14 + 1 = 20` 个 KV group。
- 20 个 group 的 `block_size` 全部为 384。

同一 group 内的最多 5 层共享同一张 block table，但分别放在五个 raw tensor slot 中。

## 7. 五个 raw tensor 怎么组织

最终仍只有：

```text
T0, T1, T2, T3, T4
```

每个：

```text
shape(raw) = (N × 537,600,) int8
size       = N × 537,600 B
offset     = 0
block_stride = 0
```

分配规则：

```text
group.layer_names[0] -> T0
group.layer_names[1] -> T1
group.layer_names[2] -> T2
group.layer_names[3] -> T3
group.layer_names[4] -> T4
```

跨不同 group、处于同一 slot 的层共享同一个 raw tensor：

- `T0–T3`：各自 `shared_by` 20 层。
- `T4`：因为 MLA 和 Mamba 各有一个四层尾组，所以 `shared_by` 18 层。
- 总计：`20×4 + 18 = 98` 个唯一 layer。

五个 pool 的总内存：

```text
total_raw_bytes = 5 × N × page_size
```

TP16：

```text
每个全局 block ID 的五池成本
= 5 × 537,600
= 2,688,000 B
≈ 2.5635 MiB
```

可分配 block 数：

```text
N = floor(available_memory / (5 × 537,600))
```

若设置 `num_gpu_blocks_override`，则以 override 为准。

## 8. BlockPool、Prefix Cache 和生命周期

最终版完全保留 v0.26 原有生命周期：

- 一个全局 `BlockPool(num_gpu_blocks=N)`。
- 20 个 group manager 共用这个 BlockPool。
- 每个 group 有自己的 block table。
- 同一 group 内的层共享 block table。
- scheduler/hash/prefix-hit 语义仍以 384 token 为单位。
- worker 仅在 Attention kernel 入口把物理 ID 展开成三个 128-token ID。
- 不新增 parent refcount、subslot bitmap、GQA 专用 BlockPool 或新的 block-ID namespace。
- copy、swap、free、Prefix Cache replay 继续传递原物理 block ID。
- `page_size_padded` 只负责让三类 spec 的物理 page size 统一到 `537,600 B`。

识别器只在以下条件全部满足时启用四平面：

- 同时存在 `AscendMLAAttentionSpec`、`MambaSpec` 和 padded GQA `FullAttentionSpec`。
- 不混入其他 cache spec。
- Mamba 必须是 `mamba_cache_mode="align"`。
- 所有 spec 的 block size 相同。
- 所有 Mamba 层的 state shape/dtype 相同。
- 所有 MLA 层的 unpadded page size 相同。
- GQA-K 和 GQA-V 的实际大小都必须精确等于 L2 的 `49,152 B`。
- 当前 page size 只能是旧的 `488,448 B` 或已经扩展后的 `537,600 B`。

不满足时直接不启用，不做近似匹配。
