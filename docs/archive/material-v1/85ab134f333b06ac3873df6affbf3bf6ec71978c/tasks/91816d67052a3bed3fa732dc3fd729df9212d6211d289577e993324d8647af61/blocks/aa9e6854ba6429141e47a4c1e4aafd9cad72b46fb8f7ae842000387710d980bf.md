### assistant:final_answer
对，上一条漏掉了 0.26 MLA DSpark 四机，而且此前把不同 `gpu_memory_utilization` 放在一起比较了。

0.26 PR #13277 最终 QuaRot MLA 四机运行：

- 拓扑：`TP16 × DP4 × EP64`
- Prefix Cache：开启
- `gpu_memory_utilization=0.8`
- 四个节点均为：`GPU KV cache size: 371,160 tokens`
- 384 block 对齐上限：`370,944`
- 实际启动参数：`max_model_len=135000`

所以它的 KV 理论上限约为 **371K decimal / 362.25K binary**，建议首次尝试 `--max-model-len 360000`。关闭 Prefix Cache 的历史运行稍高，为 `374,122 tokens`。

修正后的比较是：

| 版本与方案 | memory util | KV capacity |
|---|---:|---:|
| 0.26 MLA DSpark 四机 | 0.8 | **371,160** |
| 0.27 MLA DSpark 四机 r1 | 0.8 | **246,896** |
| 0.27 MLA DSpark 四机 r2 | 0.9 | **409,463** |
| 0.27 GQA mixed 四机 | 0.9 | **419,604** |

因此不能直接用 `0.26 MLA 371K` 对比上一条的 `0.27 MLA 409K`：后者多给了 0.1 的显存预算。同为 0.8 时，0.26 实际比 0.27 多约 124K token。

原因首先是可用 KV 内存不同：

- 0.26：`13.76 GiB`
- 0.27：`9.31 GiB`

两者每 GiB 对应的 token 数其实很接近，所以这个差距主要是 0.27 模型/runtime/图占用增加了约 4.45 GiB，不能归因成 KV 分组方案本身退化。

0.26 没有保留下来的四机 `gpu_memory_utilization=0.9` 实机结果。按预算线性外推大约可到 **536K**，但这只是估算，正式结论仍应以重新拉起实测为准。

### assistant:commentary
你的判断是对的：当前 `a4a90067a` 里的 `block_size=384`、`page_size=488448` 是 TP16/C16 这一种实例的严格匹配值，不是通用布局描述。TP size 或 cache/计算精度改变后，它大概率会静默回退到 vLLM 通用分组，而不是继续使用四组方案；这虽然避免错算，但功能会“失效”。我会分别核对 0.26 的 allocator/runner 接口差异，以及 TP8、C8 下真实 spec/page 的生成路径，再给出应当配置化到哪一层。

### assistant:commentary
0.26 这边比“直接把 0.27 patch 搬过去”更微妙：它已经有 `UniformTypeKVCacheSpecs`，但物理缓存仍是四平面专用布局。也就是说可以只移植“调度所有权分组”，不必同时重做 allocator；这是破坏性最低的路径。反过来，如果连 0.27 的三平面/488448 页面一起搬，风险会明显上升。

### assistant:commentary
关于 “C8” 我会在结论里拆成两种含义：如果你指并发 8，它不改变单页几何；如果你指 KV-cache C8/INT8，它会改变真实 K/V 字节数。两者不能混为一个配置维度。当前常量真正明确会失效的是 TP8：已有实例的逻辑块/公共页会从 `384/488448` 变成 `768/976896`。

### assistant:final_answer
结论：0.27 的“混合调度分组”可以移到 0.26，整体属于中等风险；但不能直接 cherry-pick，也不能把 `384/488448` 一起写死搬过去。正确做法是让 block/page 从实际 `KVCacheSpec` 推导。

### 写死值确实不通用

当前 0.27 实现把下面两个值写死在匹配器里：

- `block_size = 384`
- `page_size = 488448`

见 [patch_kv_cache_utils.py](<redacted:local-path:8d91dd792d59>:25)。

实际几何大致是：

| 场景 | spec block size | 0.27 公共 page | 当前匹配 |
|---|---:|---:|---|
| TP16、C16 KV | 384 | 488,448 B | 成功 |
| TP8、C16 KV | 384 | 976,896 B | 失败 |
| TP16、C8 KV | 768 | 488,448 B | 失败 |
| TP8、C8 KV | 768 | 976,896 B | 失败 |

这里修正一下我前面的表述：TP8 本身主要让每 rank 的 head/state 翻倍，所以 page 翻倍；它不必然把 spec block 改成 768。看到 runtime scheduler block 768，也可能是 DCP2 的有效 scheduler block。真正的 KV-cache C8 会因为单 token 字节减半，为了继续和 SSM page 对齐，把 spec block 从 384 推导到 768。

这些值本来已经能从 Mamba state、TP 后本地 KV heads 和 cache dtype 推导，见 [patch_mamba_config.py](<redacted:local-path:9b5426819617>:64)。因此 grouping 层不应该再重复写死。

如果你说的 C8 是“并发 8”，它不改变 block/page，只改变同时请求的 block 需求和 ACLGraph capture shape；如果是 W4A8C8 但 KV 仍是 BF16，也不改变上述几何。只有真正启用 C8/INT8 KV cache 才会影响 block 推导。

### 移到 0.26 的破坏性

分三种搬法：

1. 直接 cherry-pick：高风险且不可行  
   我做了只读 `git apply --check`，当前提交在 0.26 上有 6 个路径冲突，包括 grouping、BlockTable、model runner 和测试。更关键的是，0.26 四平面会先把公共 page 从 `488448` 扩成 `537600`，所以当前严格匹配器即使解决冲突也不会触发。

2. 只移植混合分组，保留 0.26 四平面：中等风险，推荐第一阶段  
   分组从：

   - 20 个 scheduler groups，约 20 次 builder

   改成：

   - `[29, 23, 23, 23]` 四个 scheduler groups
   - MLA、GQA 两类 attention builder，加三个 Mamba builder，共 5 次 build

   0.26 已经有 `UniformTypeKVCacheSpecs`，DSpark proposer 也已经会解包 inner spec，见 [dspark_proposer.py](<<redacted:local-path:1cf05cb5abb6> k3/vllm-ascend-pr13277-ci-fix/vllm_ascend/spec_decode/dspark_proposer.py:164>)。主要补齐四处：

   - 通用 mixed-group planner
   - Mamba uniform-group 识别和 copy
   - BlockTable 的 Mamba kind 判断
   - model runner 的 accepted-token/max-block 计算

   物理 page 继续用 0.26 的结构化四平面描述符，而不是写死值，见 [kv_cache_interface.py](<<redacted:local-path:1cf05cb5abb6> k3/vllm-ascend-pr13277-ci-fix/vllm_ascend/core/kv_cache_interface.py:27>)。

3. 连物理布局一起切成 0.27：中高风险  
   需要同时取消第四个 GQA-V plane，让 page：

   - TP16：`537600 → 488448`
   - TP8：`1075200 → 976896`

   每页减少 9.14% 字节，相同 KV 预算下 block 数约增加 10.06%。但这同时改变 scheduler ownership、物理 alias、reshape/slicing 和 Prefix Cache 生命周期，容易重新碰到 0.26 历史上的碰撞问题，不建议和 grouping 一次性回移。

### 应当怎样通用化

不建议增加一个用户填写的 `page_size=488448` 配置。应该生成一个内部 layout/grouping plan：

- 保留严格的 K3 DSpark 语义识别：target MLA、draft GQA、align Mamba。
- 从所有实际 spec 中取得共同 `block_size` 和对齐后的 `page_size_bytes`。
- `num_speculative_blocks` 从 Mamba spec 读取，不写死 7。
- attention group 大小由实际层数得到：`24 + 5 = 29`。
- Mamba group 数动态计算：`ceil(69 / 29) = 3`，均分成 `23/23/23`。
- TP、DCP、cache dtype 只作为推导输入和日志信息，不参与数字常量匹配。
- 已识别为 K3 GQA DSpark、但布局能力不满足时，应明确报错或强 warning，不能静默退回 20 组而没人发现。

我的建议顺序是：

1. 先把 0.27 当前 matcher 改成结构推导，覆盖 TP16/TP8、C16/KV-C8。
2. 回移到 0.26，先保留四平面，只解决 `20 builds → 5 builds`。
3. 在 153 做 TP16/TP8 的 cold/hit、accept/reject、ACLGraph 和多并发验证。
4. 最后单独评估是否删除第四平面，回收约 9.14% page 字节。

这样第一阶段不会同时动 grouping 和物理布局，返工面最小。
