设物理 block 数为 `N`，每条 raw tensor 大小都是：

```text
N × 488448 B
```

前23条 MLA/Mamba 共享 tensor 的三平面是：

```text
P0:  46080 × N
P1: 393216 × N
P2:  49152 × N
```

不同 owner 对它的解释是：

```text
MLA:    [padding 46080N] [K-NoPE 393216N] [K-RoPE 49152N]
Mamba:  [conv    46080N] [SSM    393216N] [padding 49152N]
```

每个 plane 内 block 首轴连续。代码也是先切连续区间，再普通 `.view()`，见 [model_runner_v1.py](<redacted:local-path:587f2bc5ea43>:4413)。

5条 GQA tensor 则是：

```text
GQA: [padding 390144N] [K 49152N] [V 49152N]
```

它也是首轴连续，但 plane 边界与 MLA/Mamba 不一样。所以严格说，当前不是“全局统一三平面”，而是：

> 三平面 MLA/Mamba 共享区 + 5 条独立 padded GQA lane。

没有增加四平面的 `P3 GQA-V`。

### 分组为什么这样安排

当前分组是：

```text
Group 0: 24 MLA + 5 GQA = 29
Group 1: 23 Mamba
Group 2: 23 Mamba
Group 3: 23 Mamba
```

关键是 Group 0 中刻意先放24个 MLA，再放5个 GQA，见 [分组顺序](<redacted:local-path:8e617ce639e5>:149)。

最终29条物理 tensor：

```text
slot  0–22: MLA + 3个Mamba group，共4个shared_by
slot 23:    最后1个MLA，独占
slot 24–28: 5个GQA，独占
```

测试明确锁定为：

```text
shared_by数量 = [4] × 23 + [1] × 6
```

见 [物理布局测试](<redacted:local-path:2714eadc934d>:284)。

这个顺序很重要：它保证 GQA 不会落进前23条 MLA/Mamba 共享 tensor。否则，同一条连续 raw tensor 会被 GQA 按 `padding/K/V` 切分、又被 Mamba 按 `conv/SSM/padding` 切分，plane 边界不一致，需要重新审计 zero、copy、prefix hit 和 block reuse。

### Padding的实际影响

当前没有让 GQA 复用 MLA 的 P2，也没有增加 P3，而是直接把 GQA 补到488448：

- MLA：`442368 → 488448`，浪费9.43%。
- Mamba：`439296 → 488448`，浪费10.06%。
- GQA：`98304 → 488448`，浪费79.87%。

这正是混合方案的主要 KV 代价。换来的收益是：

- 不改变当前连续 plane reshape。
- 不引入第四平面。
- 不修改 kernel 的首轴 stride 假设。
- 20个 group 降到4个。
- metadata build 降到5次。

### 完整链路考虑

实现中同时覆盖了：

- Uniform Mamba group 的识别；
- Mamba copy buffers；
- accepted-token state；
- block table/slot mapping；
- KV zeroing；
- scheduler spec 解包；
- DSpark draft attention group；
- ACLGraph 与 Prefix Cache 实机请求。

所以当前连续布局不是遗漏，而是这个版本主动选择的兼容边界。

不过还有一个值得补强的点：现有测试通过 `[4]×23+[1]×6` 间接保证 GQA 位于尾部，最好再增加一个显式断言：

```text
所有GQA tensor.shared_by中不得出现Mamba layer
```

这样以后有人调整层注册顺序时，会直接失败，而不是等实机出现 plane alias 问题。

当前真实布局是：

```text
P0 =  46080N

```

分别解释为：

```text
MLA:

P0 [conv 46080N]

```

所以当前确实是统一的三个物理平面，GQA-K 位于 P1，GQA-V 位于 P2，没有第四平面。

你画的是：


```text

你的： [K | padding]
```

### 为什么当前把K放在P1尾部

现有通用 attention reshape 是：

```python
padding_size = total_size - k_size - v_size
raw_kv = raw_tensor[padding_size:]
k = raw_kv[:k_size]
v = raw_kv[k_size:]
```

因此天然得到：

```text
[全部padding][连续K][连续V]
```

也就是：

```text
P0 padding
P1 padding + K
P2 V
```

这样 K/V 相邻，可以直接用两个连续 slice 加普通 `.view()`，不需要 GQA 特判。

如果改成你画的 `[K | padding]`，布局会变成：

```text
P0 padding
P1 K + padding
P2 V
```

K 和 V 中间存在 `344064N` 的间隔，需要分别按固定 offset 构造 view：

```text
K offset = 46080N
V offset = 439296N
```

这在技术上完全可行，而且 K、V 各自仍然是首轴连续的；但需要同时修改 MRV1/MRV2 reshape、copy/zero/offload 相关假设并补测试。

### 是否值得改

单从 KV 容量看不值得：

- 两种方式总 page 都是488448 B。
- GQA有效数据仍是98304 B。
- 浪费仍是390144 B，即79.87%。
- 分组仍是 `[29,23,23,23]`。
- metadata build仍是5次。

因此当前选择 `[padding | K]` 是为了复用通用的“连续 K/V 位于 raw tensor 尾部”逻辑，不是因为不能做你画的布局。

结论就是：

> 现在确实是三平面；你的理解基本正确。当前只是把 GQA-K 放在 P1 的尾部，而不是P1的头部。两者容量和分组完全相同，区别只在 reshape/view 的偏移复杂度。

### user
那我的另一个问题是，如果gqa和mla支持首轴非连续之后，padding的量是否会减少，对于gqa的dspark来说


### assistant:commentary
首轴非连续本身不会减少 padding；它只是让逻辑 K/V 能以较大的物理 block stride 正确索引。是否省 KV，取决于物理 allocator 是否同时停止给 GQA 分配488448字节的公共页。下面我把“只改stride”和“连物理页一起改”分开算。

### assistant:final_answer
会不会减少，取决于“首轴非连续”是否同时改变物理分配：

| 方案 | GQA 单层每 block 物理页 | 有效 KV | padding | 是否省显存 |
|---|---:|---:|---:|---:|
| 只支持首轴非连续 | 488,448 B | 98,304 B | 390,144 B，79.87% | 不省 |
| 非连续 + GQA 独立紧凑页 | 98,304 B | 98,304 B | 0 | 省 |

原因是首轴非连续通常只是把逻辑 view 表示成：

```text
block_i     起点 = base + i × 488448
block_{i+1} 起点 = base + (i+1) × 488448
```

每个 block 只使用其中 98,304 字节，中间的 390,144 字节空洞依然存在。也就是说，非连续 stride 恰恰可以“跨过 padding”，但不会自动消灭 padding。

对于当前 5 层 GQA DSpark：

```text
每个 pool block 可减少：
5 × (488448 - 98304)
= 1,950,720 B
```

当前一个 pool block：

```text
24 × 488448 + 5 × 488448
= 14,164,992 B
```

如果 GQA 使用紧凑物理页：

```text
24 × 488448 + 5 × 98304
= 12,214,272 B
```

结果是：

- 每个 pool block 减少 13.77%
- 同样的 KV 内存理论上可以增加约 15.97% 的 block 数
- 按之前约 37.16 GiB 的 KV allocation 归一化估算，可以少占约 5.12 GiB
- 分组仍然可以保持 `[29, 23, 23, 23]`
- metadata builder 仍然是 5 个，不需要因为紧凑页重新变回 20 个组

但这要求的不只是 kernel 支持首轴非连续，还要同步修改：

- KV cache planner 按每个 tensor 的真实 page size 计算容量
- physical cache allocation 支持同一 scheduler group 内不同物理 page stride
- V1/V2 reshape 和 slot mapping 使用各层自己的 block stride
- block copy/zero、prefix cache、offload、connector、ACLGraph 等链路不能继续假设所有 tensor 都是 488,448 B/page

所以准确结论是：

> 首轴非连续是减少 GQA padding 的必要能力之一，但不是充分条件。只改 view/stride，GQA padding 一字节都不会减少；只有 allocator 和 planner 同时把 GQA 的物理页从 488,448 B 收缩到 98,304 B，才能真正获得约 13.77% 的整个 KV pool 节省。

### assistant:commentary
先给一个判断方向：vLLM 0.27.1 的数据结构已经能表达部分能力，但“同一调度组内，MLA 用 488448、GQA 用 98304，并按各自 stride 分配和执行”不是一个现成的、可直接打开的端到端特性。我正在逐项确认它在哪一层会被强制统一。

### assistant:final_answer
结论：vLLM 0.27.1 的核心框架已经支持大部分基础能力，甚至已经有接近我们目标的 packed KV allocator；但当前 vLLM-Ascend 的 K3 路径没有端到端接上。因此不是“vLLM 完全不支持”，而是“Ascend 侧还缺执行链路”。

| 能力 | vLLM 0.27.1 Core | 当前 vLLM-Ascend K3 |
|---|---|---|
| MLA+GQA 共用一个 scheduler group/block table | 数据结构支持 | 已通过混合分组实现 |
| 同一 group 内各层 page size 不同 | 支持 `UniformTypeKVCacheSpecs` | 当前进入分组前已把 GQA pad 到 488448 |
| 按真实 page size 紧凑分配 | 支持 packed layout | 当前被 Ascend 非 packed planner 替换 |
| 首轴非连续/block stride | GPU runner 支持 | Attention 部分支持，完整 packed backing 未支持 |
| Prefix Cache/block ownership | 支持，与物理布局基本解耦 | 分组侧已支持 |
| Mamba packed page | planner 能表达，但 GPU runner也缺少完整 offset 处理 | 未支持 |
| block zero/CoW copy | vLLM GPU packed backing 路径基本支持 | Ascend zeroer 仍假设统一 page size |
| P/D、offload、ACLGraph | 部分组件 stride-aware | 仍需按 connector 和图模式实机验证 |

最关键的是，vLLM 已经有：

```python
KVCacheTensor(
    size=total_size,
    offset=byte_offset,
    block_stride=block_stride,
)
```

定义见 [kv_cache_interface.py](<redacted:local-path:0ae70e65a083>:945)，planner 会把同一 group 的不同大小页面紧凑排列，并让不同 group 的地址空间复用：

```text
block_stride = max(sum(group_i 每层真实 page_size))
```

实现见 [kv_cache_utils.py](<redacted:local-path:1020163726d8>:1283)。

套到 K3：

```text
Attention group:
24 × 488448 + 5 × 98304 = 12,214,272 B

每个 Mamba group:
23 × 488448 = 11,234,304 B

最终 block_stride:
max(12,214,272, 11,234,304)
= 12,214,272 B
```

这正好就是我们前面计算的紧凑方案：GQA 不再承担 390144 B/page 的 padding。

vLLM GPU runner也能根据 `offset + block_stride` 建立首轴非连续 view，见 [attn_utils.py](<redacted:local-path:cf2ad27aa709>:183)。

但有三个现实阻点：

1. 通用 hybrid 路径会先统一 page size

   [kv_cache_utils.py](<redacted:local-path:1020163726d8>:1070) 会把不能整除的 GQA page padding 到最大 page，所以 K3 必须在这一步之前完成特殊分组并保留 GQA 的 98304 B。

2. Ascend 显式替换了上游 packed planner

   当前代码把 `_get_kv_cache_config_packed` patch 成了 Ascend 的非 packed/分平面实现，见 [patch_kv_cache_utils.py](<redacted:local-path:8e617ce639e5>:407)。

3. Ascend worker 仍按连续 tensor 切 K/V/Mamba

   当前大量使用连续 `.view()`，见 [model_runner_v1.py](<redacted:local-path:587f2bc5ea43>:4479)；zeroer 还明确断言所有 attention page stride 相同，见 [utils.py](<redacted:local-path:0ff6fb62fd0f>:116)。

因此实现策略应该是：

- 保留现在 `[29,23,23,23]` 的 scheduler 分组；
- 在 page-size unification 之前识别 K3；
- 复用 vLLM 的 `offset/block_stride` packed planner；
- 给 Ascend V1/MRV2 的 MLA、GQA、Mamba 都建立 block-strided view；
- zero/CoW 直接按整个 12,214,272 B block slab 操作一次；
- 最后验证 Prefix Cache、DSpark、Mamba copy、Mooncake/Ascend Store 和 ACLGraph。

也就是说，这个方向在 vLLM 架构上是成立的，不需要重新设计 scheduler 或 BlockPool；主要工作是把上游已经存在的 packed physical layout 完整移植到 Ascend worker 链路。



### user
那是不是意味着只要我的mla和gqa的kv读写的算子支持非连续了就可以切换这个跟上游vllm几乎一致的方案了？


### assistant:final_answer
基本方向是对的：MLA/GQA KV 读写算子支持首轴非连续，是切换到上游 packed KV 方案的核心前提。但它是必要条件，不是唯一条件。

如果字面采用上游的单一 packed backing：

```text
block_stride = 12,214,272 B
layer_page_offset = 每层在 block slab 内的偏移
block_i 地址 = base + i × block_stride + layer_page_offset
```

需要保证以下链路全部使用这个 stride：

- GQA KV 写入：reshape/cache/slot mapping 写入。
- GQA KV 读取：prefill、decode attention。
- MLA KV 写入：MLA prolog/cache 写入。
- MLA KV 读取：prefill、decode MLA。
- Mamba：如果也放进同一个 packed backing，Mamba state 读取、写入和跨 block copy 同样必须支持非连续首轴。

框架侧还需要接上这些工作：

1. 在 page-size unification 之前完成 K3 分组，避免 GQA 先被 padding 到 488448 B。
2. allocator 使用上游的 `offset + block_stride` packed layout。
3. V1/MRV2 worker 根据 offset 和 stride 建立 view，不能再直接连续 `.view()`。
4. `num_blocks` 按 12,214,272 B 计算。
5. zero、Prefix Cache CoW copy 按整个 packed block slab 操作。
6. P/D、offload、ACLGraph 验证不会把 strided tensor 隐式转成 contiguous 或按错误步长传输。

其中 scheduler 基本不用再改：

```text
groups = [29, 23, 23, 23]
metadata builders = 5
```

也不会改变 block table 和 Prefix Cache 的逻辑 block 语义。

需要特别区分两种实现：

- 上游式单 packed backing：MLA、GQA，以及 Mamba 都需要 stride-safe。
- Ascend 多 tensor 紧凑版：保留 MLA/Mamba 当前连续平面，只给5层 GQA 分配 98304N；这种方式甚至不要求 GQA 首轴非连续，但物理布局不像上游 packed 方案。

因此我的建议是：

> 如果 MLA、GQA 和 Mamba 的实际 KV/state 访问都能接受运行时 `stride(0)`，就直接迁移到上游 packed layout；不需要重新设计 scheduler 和 BlockPool，主要是补齐 Ascend allocator、view、zero/copy 和 connector 链路。

最小实机切换门槛应当是：

- 连续和非连续 layout 输出一致；
- 至少跨两个物理 block ID，避免只测 block 0 掩盖 stride 错误；
- DSpark 7 token 正确；
- Prefix Cache hit/CoW 正确；
- ACLGraph replay 正确；
- 最后确认 GQA page 确实为 98304 B，pool stride 为 12,214,272 B，而不是仍被 padding 到 488448 B。
