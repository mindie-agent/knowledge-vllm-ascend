## 2. 正式物理排布

不再让每个 layer 都占用 `488448B`：

| Layer | 每个 384-token block 的真实 payload |
|---|---:|
| MLA | `K-NoPE 393216 + K-RoPE 49152 = 442368B` |
| GQA | `K 49152 + V 49152 = 98304B` |
| Mamba | `conv 46080 + SSM 393216 = 439296B` |

分组仍采用当前混合方案：

- Group 0：24 MLA + 5 GQA
- Group 1～3：各 23 Mamba

每个 group 内按 layer 紧密排列；不同 group 的布局可以重叠，因为一个物理 block id 同时只属于一个 KV group。

```text
Attention slab:
[MLA0 442368][MLA1 442368] ... [MLA23 442368]
[GQA0 98304] ... [GQA4 98304]

Mamba slab:
[Mamba0 439296] ... [Mamba22 439296]
```

计算结果：

- Attention slab：`24×442368 + 5×98304 = 11108352B`
- 每个 Mamba group：`23×439296 = 10103808B`
- 统一物理 `block_stride = max(...) = 11108352B`

每个 component 都是：

```text
shape      = [num_blocks, ...]
stride[0]  = 11108352 / dtype_size
offset     = group 内 layer offset + component offset
其他轴     = 连续
```

因此已经没有固定“三平面”概念，而是一个 packed slab；MLA、GQA、Mamba 的页内都不再填充。

相对当前四组但每层 padding 到 `488448B` 的方案：

- 当前 stride：`29 × 488448 = 14164992B`
- 正式 packed stride：`11108352B`
- 每个物理 block 少 `3056640B`，下降 `21.58%`
- 同等 KV 预算理论上可增加约 `27.52%` 的物理 block 数

GQA 原来的 `390144B/block` padding、MLA 的 `46080B/block`、Mamba 的 `49152B/block` 都消失。Mamba group 仍会有 `1004544B` slab 尾部空洞，但它只在 Mamba-owned block 上出现；K3 align 模式每组常驻 `2+7=9` 个状态块，长上下文下这部分会被快速摊薄。

## 3. 384 block 是关键发布门槛

正式方案必须让：

```text
scheduler block size = 384
kernel block size    = 384
```

否则用 128 kernel block 时，地址是：

```text
3b+k -> b*physical_stride + component_offset + k*128-token-page
```

单一 `as_strided(stride[0])` 描述不了这种两级 stride。

beta.2 的 FIA checker 已允许 K3 非量化 GQA/MLA 使用 384 block，但仓库里没有找到完整的“384 + 首轴 stride”端到端回归。因此必须先在 153 对下面组合做 release-gate：

- FIA GQA：block 384、首轴非连续 K/V
- FIA MLA：block 384、首轴非连续 K-NoPE/K-RoPE
- ScatterPaKvCache：block 384、首轴非连续 destination
- MLA writer：block 384、首轴非连续 destination

如果 FIA 384 不过，就不能直接启用 packed slab；不能悄悄退回当前 128 virtual-block reshape。

## 4. 正式算子链

| 路径 | 正式算子 |
|---|---|
| GQA read | beta.2 FIA，读取运行时 `keyBnStride/valueBnStride` |
| GQA write | beta.2 `aclnnScatterPaKvCache`，直接支持首轴非连续 cache |
| MLA read | beta.2 FIA，分别读取 NoPE/RoPE stride |
| MLA fused write | beta.2 `MlaPrologV3`，但必须先通过 block 384 ACLNN 实测 |
| MLA fallback write | RMSNorm/RoPE 后调用官方 `aclnnScatterNdUpdate` |
| Mamba conv | 最新 FLA `CausalConv1D`，使用 `convStateStride0/1` |
| Mamba SSM | 最新 FLA recurrent KDA，使用 `stateStride0/1/2` |

你对 ScatterNd 的纠正是对的：`npu_scatter_nd_update_v2` 是临时实现，正式路径必须删除并替换为 CANN 9.1 的官方 `aclnnScatterNdUpdate`。但它不应该成为 GQA writer；beta.2 下 GQA 应直接使用更专用的 `ScatterPaKvCache`。`:codex-annotation{index="1"}`

另一个边界是 `MlaPreprocess`：当前文档把 PA block size 固定为 128，因此它不能作为这个 384 packed 方案的正式 MLA writer。优先验证 `MlaPrologV3`；其 README 声明支持首轴非连续，但 ACLNN 参数表仍有不一致，必须验证实际发布包，而不能只看 kernel 源码。

## 5. Model runner 改造

正式实现不应继续添加 K3 专用 tail slice，而应实现一套 MRV1/MRV2 共用的 component-layout builder：

- `KVCacheTensor.offset/block_stride` 描述跨层 slab。
- `KVCacheSpec` 描述 layer 内 component：

  - GQA：K、V
  - MLA：K-NoPE、K-RoPE
  - Mamba：conv、SSM

- 每个 component 独立构造 `as_strided`，保证只有首轴非连续。
- Ascend attention cache 改成 blocks-first 契约。
- `kernel_block_size=384` 后，block table 不再做 `b → [3b,3b+1,3b+2]` 展开。
- slot mapping 恢复成普通的 `block_id×384 + token_offset`。
- MRV1/MRV2、ACL Graph、sleep/wake、KV connector、P/D、prefix copy 全部读取真实 `stride(0)`，不能重新假设连续。

当前硬编码 `_KIMI_K3_PAGE_SIZE_BYTES=488448` 和“Attention K/V 位于 allocation tail”的逻辑都属于过渡实现，应在 packed layout 接通后删除。

## 6. 分组和 metadata build

物理布局与 metadata build 仍需分开看：

- scheduler group：4 个
- Attention group 内部又会按 backend/spec 分成 MLA、GQA 两个 subgroup
- 再加 3 个 Mamba group

所以第一阶段实际是：

```text
MLA 1 + GQA 1 + Mamba 3 = 5 次 build
```

不是 4 次，但已经不是 20 次。

最终 metadata 目标应是：

```text
MLA template   1
GQA template   1
Mamba template 1
其余 Mamba group 只 update block_table/slot_mapping
总计 3 次完整 build
```

这里必须补 MRV2 cache key 和 updater，覆盖 ubatch、spec accept/reject、prefix hit/miss、chunked prefill、ACL Graph buffer 生命周期。不能直接照搬 MRV1 的简单缓存。

## 7. 推荐落地顺序

1. 在 153 安装 beta.2 候选包和最新 FLA，先完成四个 block-384 首轴 stride 单算子测试。
2. 实现通用 packed component descriptor 和 MRV1/MRV2 共用 view builder。
3. 接入 4 个 scheduler group，先接受 5 次 build，验证真实 KV block 数和显存收益。
4. 接通 GQA/MLA/Mamba 完整读写、copy、offload、P/D 和 ACL Graph。
5. 最后实现 MRV2 metadata updater，把 5 次完整 build 降到 3 次。
6. 删除三平面 tail slicing、`488448` 硬编码、临时 ScatterNd V2；[#13821](https://github.com/vllm-project/vllm-ascend/pull/13821) 只保留为 CANN 9.1/v0.26 backport，不再作为 beta.2 正式算子来源。

这套方案的核心取舍是：首轴非连续不是为了继续容纳 padding，而是为了彻底取消按 layer 的统一页 padding；384 kernel block 则是让 packed slab 能被算子用一个首轴 stride 正确表达的必要条件。

## 结论

当前 4 机 A3 拓扑实际是 `DP4 × TP16 × EP64`。KV cache 按每个 DP engine 的 TP16 replica 计算，四台机器不会把 KV pool 合并给单条请求。

| DSpark | 实机 KV pool | 384 block 对齐上限 | 建议首次拉起值 | 已实机拉起 |
|---|---:|---:|---:|---:|
| MLA | 409,463 tokens | 409,344 | `400000` | `135000` |
| GQA 混合分组 | 419,604 tokens | 419,328 | `410000` | `135000` |

因此简化回答是：

- MLA DSpark：大约可以拉起 **400K context**。
- GQA DSpark 混合分组：大约可以拉起 **410K context**。

这里的 K 按十进制理解。如果按 `1024 tokens = 1K`，分别约为 `399.75K` 和 `409.5K`。

- MLA：`Available KV cache memory: 15.44 GiB`，`GPU KV cache size: 409,463 tokens`。
- GQA：`15.55 GiB`，`419,604 tokens`。
- 模型自身 `max_position_embeddings=1,048,576`，不是当前限制。
- DSpark 配置中的 `max_model_len=4096` 是 draft 工作窗口，不限制 target 长上下文；128K 已经实机跑通。

需要严格区分：`400K/410K` 是根据 profiler 和 384 block 对齐得到的可启动判断，还没有实际用对应 `--max-model-len` 重启验证。当前真正拉起过的是 135K，真正完成请求验证的是 128K。
