- 新文档首次分配一次固定路径；正文、标题、脱敏结果变化都只更新该路径。现有 50 个文件直接沿用原路径。
- pending 按稳定路径保存，记录最新 `content_digest`。候选规范路径仅用于本地重复捕获匹配，不能只用当前的 `candidate.name`。
- 跨 Agent 修订通过显式目标 Git 路径关联；不能用标题、相似内容或新内容摘要判断身份。CLI/客户端需可传入并返回该路径。
- 内容摘要相同是幂等判断；摘要不同将同记录重新置为待提交。已有开放 PR 时保留 branch/PR，向该 PR 推送修改。
- PR 已合并或关闭后的修订，应从最新 upstream 建立新提交分支，文档路径保持不变。`gitops.py:53` 当前复用旧分支而忽略 `start_ref`，必须避免把旧 PR 分支直接当新轮次基线。

现有实现有三处会阻止修订：`submit.py:82` 的提前返回、`:127` 对 `pr_open` 的提前返回，以及 `publishing.py` 只轮询 `pr_open`。另一个入口问题是 `capture.py:65` 按标题寻找候选，改标题会创建新候选；若 MCP 也要支持同候选改标题，需要可选目标引用贯通 MCP、capture、queue_capture。

最值得补齐的生命周期测试：

| 场景 | 必须证明 |
|---|---|
| 首次贡献、原内容重试 | 一个 pending、一个文件、一个 PR |
| 同候选修改正文或标题 | digest 改变，路径、开放 PR 不变，Git diff 仅 `M` |
| 不同目录同名候选 | 不会错误复用文档身份 |
| 无 pending 的另一 Agent 更新已有 hash 文件 | 原路径 `M`，不新增文件 |
| 合并后再修订 | 新 PR 基于最新 upstream，保留其他人的改动 |
| 关闭后修订 | 新轮次，不返回旧的终态结果 |
| 已合并内容被 reviewer 改过，原候选重复捕获 | 不自动重开 PR 恢复旧文本 |
| 修改仅发生在被脱敏片段 | 公共摘要相同，无新提交 |
| 修改后脱敏失败，再修复 | 同记录恢复；失败稿不提交，候选保持原样 |
| push 成功、创建 PR 失败后重试 | 复用远端分支；不会重复 PR |
| `knowledge` / `experience` 同名同内容 | 身份、路径、pending 分离 |
| 提交期间再次 prepare | 旧提交完成不能覆盖新修订 |

最后一项是改为稳定 pending 后新增的实际竞争风险：`run_once` 的锁目前不覆盖 `queue_capture`。旧 `submit_pending` 回写旧记录时会覆盖新内容摘要。应复用现有锁，或回写前重读 pending、保留更新后的内容与待提交状态。
