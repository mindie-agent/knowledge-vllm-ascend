结论：

- `release/0.23.0` 已有可复用的 hybrid prefix-cache 命中断言：vLLM 的 `tests/v1/core/test_prefix_caching.py::test_prefill_hybrid_model_combinations` 覆盖 `full + mamba`，首请求断言 `num_computed_tokens == 0`，第二个共享 3 个 block 前缀的请求断言 `num_computed_tokens == 3 * block_size`。
- vllm-ascend 的 Qwen3.5 用例 `tests/e2e/pull_request/one_card/_310p/test_dense_model_310p.py::test_qwen3_5_dense_prefix_mamba_cache_tp1_fp16` 只比较 cache on/off 输出，不足以证明真实命中。
- 不应给 K3 增加 `supports_mamba_prefix_caching=True`。这个标记代表支持 `"all"` 模式；K3 KDA 当前只具备 `"align"` 的 checkpoint/copy 语义。K3 已有 `IsHybrid`、`HasInnerState` 及三个 Mamba state hook，能直接复用 align 路径。

推荐验证方式：

1. 使用同一 engine 顺序执行两次相同 `TokensPrompt`，不要批量同时提交。
2. 显式配置：
   - `enable_prefix_caching=True`
   - `mamba_cache_mode="align"`
   - 开启 chunked prefill
   - 暂不启用 PCP/MTP
3. 根据运行时最终解析出的 `cache_config.block_size` 构造至少 2～3 个完整 block 的 prompt，不能硬编码常见 block size，因为 hybrid recurrent state 可能扩大它。
4. 拦截 `SchedulerOutput`：
   - 首次请求应为 `num_computed_tokens == 0`
   - 第二次应至少 `>= block_size`
5. 同时比较 cache on/off 的 greedy token 和 chosen-token logprob；建议额外断言第二次 KDA prefill 的 `prefill_has_initial_state=True`，直接证明 recurrent state 被恢复。
