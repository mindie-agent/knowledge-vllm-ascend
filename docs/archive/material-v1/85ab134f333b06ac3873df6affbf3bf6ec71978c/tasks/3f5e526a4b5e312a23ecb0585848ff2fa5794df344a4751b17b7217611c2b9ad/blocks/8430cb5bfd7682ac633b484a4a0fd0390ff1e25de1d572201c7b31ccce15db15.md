第二处是 full-causal draft 语义。

### 根因

MRV1 Block5 每请求 target verification token 数为：

```text
uniform_decode_query_len = num_speculative_tokens + 1 = 6
```

SP TP16 又要求 graph token 数能被 16 整除。满足两个条件的最小值是：

```text
LCM(6,16) = 48
```

当前 vLLM 使用：

```python
multiple_of = max(6, 16)  # 16
```

然后检查 `16 % 6`，因此错误地判定“无解”。事实上 48、96 都是合法解。这个约束来自 vLLM 通用的 MRV1 spec-decode + SP 组合，不是 Ascend 特有约束；截至当前 upstream main 仍是这套 `max()+互整除` 实现。[vLLM compilation.py](https://github.com/vllm-project/vllm/blob/main/vllm/config/compilation.py)

推荐的上游逻辑是：

```python
multiple_of = uniform_decode_query_len
if tensor_parallel_size > 1 and self.pass_config.enable_sp:
    multiple_of = math.lcm(
        uniform_decode_query_len,
        tensor_parallel_size,
    )
```

只要最大 capture size 不小于 LCM，就总有合法 gear，不应提示用户关闭 SP。

### 下游对 48/96 的支持

静态路径未发现需要额外修改：

| 实际请求数 | 实际 token | SP 初步 padding | graph gear | padded requests |
|---:|---:|---:|---:|---:|
| 1–2 | 6–12 | 16 | 48 | 8 |
| 3–5 | 18–30 | 32 | 48 | 8 |
| 6–8 | 36–48 | 48 | 48 | 8 |
| 9–10 | 54–60 | 64 | 96 | 16 |
| 11–13 | 66–78 | 80 | 96 | 16 |
| 14–16 | 84–96 | 96 | 96 | 16 |

关键路径均能成立：

- `CudagraphDispatcher` 要求 full uniform decode gear 能被 6 整除；48/96 满足。
- SP 要求最终 token 数能被 TP16 整除；48/96 满足。
- `BatchDescriptor.num_reqs` 分别得到 `48/6=8`、`96/6=16`。
- Ascend FIA metadata 会以 6 token 为单位补 dummy request，`query_start_loc` 最终到达 48/96。
- graph 参数字典使用 dispatcher 最终生成的 capture descriptors，不存在 16/32 硬编码。
- static-kernel gear 会按 `max_num_seqs×6=96` 过滤，最终保留 `[48,96]`。
- 当前 draft `enforce_eager=True`，不会额外要求 draft graph gear。

可维护性上，不建议在 [platform.py](<redacted:local-path:6ccb83b8079e>:1080) 再实现一遍 LCM；那里只负责平台默认容量和 TP gear 对齐，通用 spec-decode 对齐仍应由 vLLM `CompilationConfig` 统一负责。

### 性能影响

48 是合法但较粗的最小 gear。单请求会从 6 token pad 到 48 token，不过 SP 后每个 TP rank 处理 3 个 token。相比原来 Block7 的 `LCM(8,16)=16`，Block5 低并发 padding 明显更大，TPOT 需要实际比较：

- SP + `[48,96]`
- SP 关闭 + 6-token 系列 gear

这是性能选择，不是正确性修复的理由；当前功能默认仍应保留 SP。
