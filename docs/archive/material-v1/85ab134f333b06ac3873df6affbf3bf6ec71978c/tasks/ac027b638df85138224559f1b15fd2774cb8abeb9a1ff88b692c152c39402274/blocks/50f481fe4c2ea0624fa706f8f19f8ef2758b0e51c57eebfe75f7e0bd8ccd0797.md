### assistant:final_answer
结论：`N mod 4` 确实改变 P1/P2/P3 的 4 KiB 对齐，但现有证据不支持把 hit-only 精度问题直接归因于该对齐。

- 四平面相对 raw base `B`：

  - P0=`B`
  - P1=`B + 46080N`
  - P2=`B + 439296N`
  - P3=`B + 488448N`

  P1/P2/P3 的模 4096 均为 `1024*(N mod 4)`。因此 N=17064、5164、5168 对齐；5166 为 +2048；5167 为 +3072。
- P1/P2/P3 block stride 都是 4096 的整数倍；P0 stride=46080，block 地址本来就随 `block_id mod 4` 在四种 4 KiB residue 间循环。若 Mamba copy 有普遍 4 KiB 硬约束，旧 N=17064 也无法保证 P0 所有 block 对齐。
- 当前 Triton Mamba copy 将地址转为 `uint8*` 后 masked byte-copy，没有 4 KiB 假设。MLA 的 scatter/FIA Python 调用链也没有此断言；当前地址至少保持 1024-byte 对齐。
- miss896 第二段确定会走与 hit 相同的 `prev0→curr2`：

  1. DSpark 的 `use_eagle()` 为 true；896 首段被 `_mamba_block_aligned_split` 截到384。
  2. 首段：computed=0、scheduled=384，`curr=ceil(384/384)-1=0`，prev=-1，不复制。
  3. 第二段：computed=384、scheduled=512，`prev=0`，`curr=ceil(896/384)-1=2`，收集 0→2 metadata。
  4. `model_runner_v1` 在 `_model_forward` 前实际执行 `do_mamba_copy_block`。

  因而 miss 正常而 hit 必坏不能由“是否执行 0→2 copy”解释。对 P1/P2/P3 而言物理 block ID 也不改变 4 KiB residue，进一步削弱纯 plane-base alignment 假设；差异仍应聚焦 cached source 内容、ownership/COW、block table 或 P0 block-ID residue。
