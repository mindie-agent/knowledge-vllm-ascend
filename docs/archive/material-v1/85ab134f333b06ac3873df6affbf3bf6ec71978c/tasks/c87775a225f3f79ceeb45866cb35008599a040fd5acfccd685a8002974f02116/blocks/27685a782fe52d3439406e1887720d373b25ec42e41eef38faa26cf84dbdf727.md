目前实际是这样运行的：

| 阶段 | 触发条件 | 当前行为 | 是否额外调用模型 |
|---|---|---|---|
| 插件加载 | Codex 为任务加载已启用插件 | 暴露一个入口 Skill、知识与远程开发两个 MCP，以及两条 hook | 不会，但说明和工具定义会增加上下文 |

其中 `Stop` 对应一轮结束，并不代表整个业务任务完成。当前只注册了 `SessionStart` 和 `Stop`，没有工具调用 hook，也没有 `SessionEnd`、`Interrupt` 的专门收尾处理。[当前配置](<redacted:local-path:d119974389ce>)、[Codex 生命周期说明](https://developers.openai.com/zh-Hans/docs/hooks)

**“进入插件”目前主要靠 Agent 行为，还没有独立的激活接口。**

你可以显式调用 `$mindie-agent`；Agent 也可能根据 Skill 描述判断任务适用。随后 Skill 指导它调用 `knowledge_query`。真正改变后端状态的是这次工具调用，读取 Skill 本身不会登记领域。

**当前最值得调整的，是检索和采集资格被绑在了一起。**

代码中，`knowledge_query` 会登记 session，即使没有检索结果；`knowledge_use` 也会登记。这个登记持久保存，目前没有退出、过期或切换状态。[登记逻辑](<redacted:local-path:4e23ebc13a69>:181)

因此会出现这样的情况：

> 某轮查过一次 vLLM 知识 → session 获得采集资格 → 后面回复“好的，谢谢” → Stop 仍可能把它送给整理模型 → 整理模型再判断没有值得保存的内容。

现有去重和预算能限制次数，却没有解决“这一轮是否值得调用模型”的问题。采集内容也只有最终回复，不是完整的工具证据链。

我建议详细设计先明确以下边界：

1. **激活独立于检索。** 明确 session 绑定哪个领域、是否开启采集、何时退出；普通查询保持只读。
2. **区分回合结束与成果形成。** Stop 只作为候选事件；先用确定性条件判断是否有新成果、失败经验或待评价记录，再决定是否调用整理模型。
3. **明确取消和恢复。** 用户中断、关闭任务、服务重启、插件升级时，哪些后台工作取消、哪些直接丢弃，都有固定规则。
4. **分别定义整理与裁判预算。** 当前二者共用每 session 6 次额度，领域熔断也会影响同一服务中的其他 session；这些保守默认值还需要产品层面的取舍。
5. **状态可见。** 用户能看到“未激活／已绑定／采集关闭／预算耗尽／故障暂停”，不用从报错和后台日志猜测。

刚刚回读的本机状态是：**两条新版 hook 仍待重新信任，当前自动采集被跳过；知识服务在线，后台队列为空，最近一小时维护调用为 0。** 目前新收集内容默认只留本地，自动发布关闭。
