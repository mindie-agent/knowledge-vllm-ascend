1. P0：K3 MoE 当前无法按 upstream main 的 Python API 构造。

`vllm_ascend/models/kimi_k3_text.py:200-221` 调用：

```python
FusedMoE(
    activation="situ",
    situ_beta=beta,
    situ_linear_beta=linear_beta,
)
```

但 upstream vLLM 的 `FusedMoE`：

- `vllm/model_executor/layers/fused_moe/layer.py:100-146` 没有 `situ_beta`、`situ_linear_beta` 参数。
- `layer.py:217-218` 会执行 `MoEActivation.from_str("situ")`，而 upstream 枚举没有 `situ`。
- `layer.py:397-418` 已提供正式的 `runner_cls` / `runner_args` 扩展点。

因此这里会先遇到未知 keyword 或未知 activation；现有 UT 没有覆盖真实 factory 构造。

建议：

- upstream factory 仍传 `activation="silu"`，仅用于 gated shape、专家权重布局等通用语义。
- K3 显式传 `[REDACTED_SECRET]`。
- 通过 `runner_args` 传 `SituActivationConfig`。
- 由 K3 runner 在 Ascend Python 执行路径中选择 SiTU，不给全局 factory 增加未知字符串和参数。

2. P1：`REGISTERED_ASCEND_OPS` 中 K3 注册方式确实是补丁式且类型错误。

位置：

- `vllm_ascend/utils.py:733-735`
- `vllm_ascend/utils.py:780-781`
- `vllm_ascend/models/kimi_k3_text.py:387-394`

问题：

- `KimiGatedDeltaNetAttention` 是 `PluggableLayer`，upstream 定义见 `custom_op.py:32-100`，却通过 `CustomOp.register_oot` 注册。
- 两套接口目前碰巧共享 `op_registry_oot`，所以“能用”依赖 vLLM 内部实现细节。
- 注册是进程全局的，会替换所有 `KimiGatedDeltaNetAttention`，而不是只影响 `KimiK3TextConfig`。
- `kimi_kda.py:113-120` 只有 A-log loader 做了 K3 类型限制，其余执行行为仍会污染别的 Kimi Linear 模型。

最干净的重构是：

- 从 `REGISTERED_ASCEND_OPS` 删除 K3 条目。
- `KimiK3DecoderLayer` 直接构造 `AscendKimiGatedDeltaNetAttention`。
- 删除 `tests/ut/ops/test_kimi_kda.py:32-34` 这种验证补丁注册实现细节的 UT。

upstream `PluggableLayer.register_oot` 虽是正确 API，但这里 K3 模型和实现都归插件所有，直接组网比全局替换更合适。

3. P1：SiTU 被横向注入通用 FusedMoE，形成了 K3 特例扩散。

涉及：

- `moe_stage_contracts.py:70,146`
- `moe_runtime_args.py:133`
- `moe_comm_method.py:443-444`
- `moe_mlp.py:316-354,670-746`
- `fused_moe.py:761-840`

具体表现：

- 通用 MoE contract 被扩成 `str | MoEActivation | SituActivationConfig`。
- FUSED_MC2 在 forward 中用 `isinstance(..., SituActivationConfig)` 静默退回通用路径。
- shared expert 每次 forward 用 `hasattr(weight_scale)` 和 activation 类型推断执行能力。
- 这不是一次性的能力选择，而是把能力探测散落在运行热路径。

建议把 SiTU 选择提升到 K3 runner 初始化阶段：

- K3 runner 显式选择支持 SiTU 的 MoE 路径。
- 初始化时确定量化模式、shared/routed 执行方式以及 MC2 是否可用。
- forward 只执行已经选定的策略，不再通过 `hasattr`、`isinstance` 做动态能力发现。
- 通用 MoE contract 不应直接依赖 K3 专属类型；若确实需要扩展，定义统一的 Ascend activation spec，而不是不断增加模型专属 union。

4. P1：固定 C++ ABI 的 Python 调用重复，没有单一适配层。

同一 ABI 与魔数重复在：

- `moe_mlp.py:45,251-271`

包括：

- `torch.ops._C_ascend.dequant_situ_quant`
- `torch.ops._C_ascend.situ_mx_quant`
- `SITU_MX_DST_TYPE_E4M3FN = 36`

建议增加唯一 Python SiTU ABI adapter，集中负责：

- `linear_beta=None` 到 ABI 值的转换。
- `dst_type=36` 等 ABI 常量。
- shared/routed 两种输入的参数整理。
- 一次性 schema 校验。

C++ ABI 保持原样；只是消除 Python 侧两套调用协议。
