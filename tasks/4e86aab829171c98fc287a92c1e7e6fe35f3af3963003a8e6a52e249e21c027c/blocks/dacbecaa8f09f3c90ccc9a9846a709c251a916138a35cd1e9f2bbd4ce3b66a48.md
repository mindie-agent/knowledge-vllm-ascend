### assistant:final_answer
结论：不是 Kimi K3 processor 注册失败，而是 vLLM 的多模态缓存快路径绕过了它的 `__call__`。

远端实测：

- 实际注册类型正确：`KimiK3MultiModalProcessor` + `KimiK3Processor`。
- 不带 processor cache 的 dummy processing 正常。
- 带 `MultiModalProcessorOnlyCache` 时稳定复现：
  `vision_chunks invalid` → 空 MM kwargs → `_merge_mm_kwargs` `IndexError`。
- 仅临时加入 Kimi K2.5 风格的 `_call_hf_processor` override 后，同一测试成功返回 1 个 `vision_chunk` item。

原因是 `BaseMultiModalProcessor._apply_hf_processor_mm_only` 会根据子类是否 override `_call_hf_processor` 选择路径。K3 当前没有 override，于是调用 generic `call_hf_processor_mm_only`；后者只处理 `images/videos/audio`，不支持 `vision_chunks`，也不会调用 [KimiK3Processor](<redacted:local-path:22fb28f07509>:37)。

最小修复是在 [KimiK3MultiModalProcessor](<redacted:local-path:8652d4720dea>:142) 增加与 Kimi K2.5 相同的 override：

```python
def _call_hf_processor(
    self,
    prompt: str,
    mm_data: Mapping[str, object],
    mm_kwargs: Mapping[str, object],
    tok_kwargs: Mapping[str, object],
) -> BatchFeature:
    # Force cached vision_chunk misses through the joint text/MM path.
    return super()._call_hf_processor(prompt, mm_data, mm_kwargs, tok_kwargs)
```

不建议改成直接调用 `self.info.hf_processor`，否则会绕开 `InputProcessingContext` 的统一参数处理。

Qwen3.5 没有这个问题，是因为它复用的 `Qwen3VLMultiModalProcessor` 已 override `_call_hf_processor`，并且主要使用 generic helper 原生支持的 `images/videos`。Kimi K2.5 的同名空 override 正是为 `vision_chunk` 缓存场景准备的。
