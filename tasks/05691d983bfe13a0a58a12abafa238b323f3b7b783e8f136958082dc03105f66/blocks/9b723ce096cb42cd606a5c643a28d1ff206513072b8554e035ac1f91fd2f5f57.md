## 结合窗口收敛，我更新后的头号嫌疑：idle 间隙的 dummy run / DP wave 收尾，拿着已结束请求的残留缓冲继续写真实缓存块

这个窗口里 host 代码不能直接写显存，能写 state 的设备侧执行只剩一类容易被忽略的东西：**warm 结束到 hit 到达之间的空转步**。TP16×DP4 下 DP0 独跑 B2，wave 收尾/协调期间 DP0 很可能执行 1-2 个 FULL_DECODE dummy 回放（DP1-3 全程都在 dummy）。关键在于 dummy 回放用的是**持久缓冲的现状**：

- 请求结束时，持久 block table 的 row0 并不会清空，仍是 warm 的 `[143, 132, b2, 0, 0, ...]`；
- KDA spec 路径的状态槽恰恰取自块表前 `num_spec+1` 列（`spec_state_indices = bt[:, :8]`）——即 `[143, 132, b2, 0×5]`：**col0 是 143，col3 以后是 block 0**；
- KDA/GDN 递归在零输入下是**恒等传递**（decay≈1、无更新项时 S' = S），所以 dummy 回放完全可以把从 poison 槽读进来的初始态**逐字节原样**写到另一个槽——这正好解释"143 的内容 == block 0，字节级一致"这个最反直觉的签名：不需要任何 memcpy，一次零输入的 spec 状态链就能把 block 0 的 `0x7fffffff` 原样搬进 col0=143。

三个旁证：这类 bug 家族在这套代码里真实存在过——PR 第一个 commit（GDN backport `637d49d04`）修的就是"refresh captured non-spec decode buffers / clear stale speculative graph inputs"；你们工作目录里还留着历史实验脚本 `run-k3-dspark-r9-size16-gdn-dummy-reset.sh`（当年就跟 dummy reset 干过仗）；且 16/16 rank 完全一致、与任何同步无关、确定性复现，都符合"所有 rank 回放同一张图"的特征。
