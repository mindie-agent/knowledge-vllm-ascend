### 为什么以前看起来需要同步

四平面修改把原始 backing 解释为：

```text
[Conv] [Mamba SSM / MLA NoPE] [MLA RoPE / GQA K] [GQA V]
```

页面从 488448 扩到 537600 bytes，但 scheduler block 仍是 384 token。[布局识别](<<redacted:local-path:b8dd889167fe>/vllm-ascend-v0.26.0rc-dspark-four-plane-publish-candidate/vllm_ascend/core/kv_cache_interface.py:26>)、[reshape](<<redacted:local-path:b8dd889167fe>/vllm-ascend-v0.26.0rc-dspark-four-plane-publish-candidate/vllm_ascend/worker/model_runner_v1.py:4011>)。

历史 dump 已经观察到更直接的证据：draft layer 94/block 1969 与 target layer 23/block 5224/page 15672 落到相同物理 backing；随后 target KV 首次读到 448 个 NaN。这个证据更符合物理地址/所有权冲突，而不是尚未完成的异步写。

`torch.npu.synchronize()`只能保证本 worker 的 NPU streams 上已提交任务完成；它不是 HCCL 全卡 barrier，也不能：

- 把两个错误别名的逻辑 block 分开；
- 修正错误的 block ID、stride 或 plane offset；
- 清除已经写进 backing 的污染。

它会改变后续 warm、zero、copy 的完成顺序，所以顺序实验中可能恰好把污染区域覆盖回来。尾部无同步 control 也恢复，正是这种携带效应的证据。

### 建议的真正修复方向

重点不应继续找同步位置，而应验证同一个物理布局描述是否统一驱动：

- allocation / `shared_by`；
- block table、slot mapping 和 384→3×128 展开；
- reshape 的 plane offset/stride；
- zero、copy/swap 和 prefix replay；
- parent/subslot 生命周期和 refcount。

首先应对当前最新 head 与独立 GQA pool 版本做 fresh-service B2 A/B，并直接证明 layer 94/block 1969 与 layer 23/block 5224 的地址区间不再重叠。只有物理地址唯一性成立后仍能复现，才值得继续用 producer event 替代全设备同步定位真实 side-stream race。
