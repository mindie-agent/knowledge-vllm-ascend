### CANN 9.1 写 KV 箐子的判断

`aclnnScatterPaKvCache` 不能解决这个问题。

[CANN 9.1 ScatterPaKvCache 文档](https://www.hiascend.[REDACTED_SECRET].md)里的 `scatterMode="Nct"` 以及 `strides/offsets` 描述的是源 `key/value` 非连续，不是目标 `keyCacheRef/valueCacheRef` 的 block stride；目标 cache 在非连续 Tensor 一栏也不支持。因此它不能直接写：

```text
physical block stride > block_size * heads * head_dim
```

目前最可用的官方候选是 `aclnnIndexPutImpl`：

- [CANN 9.1 IndexPutImpl 文档](https://www.hiascend.[REDACTED_SECRET].md)允许 `selfRef` 为非连续 Tensor。
- TorchNPU 的 `Tensor.index_put_` 已直接映射到 `aclnnIndexPutImpl`，[op-plugin 实现](https://github.[REDACTED_SECRET].cpp)。

GQA 可以直接表达为：

```python
slots = slot_mapping[:num_actual_tokens].long()
block_ids = slots // block_size
block_offsets = slots % block_size

key_cache.index_put_(
    (block_ids, block_offsets),
    key[:num_actual_tokens],
    accumulate=False,
)
value_cache.index_put_(
    (block_ids, block_offsets),
    value[:num_actual_tokens],
    accumulate=False,
)
```

这在功能契约上满足目标 cache 首轴 stride，但还不能直接判断性能可接受。CANN 内部对某些 indexing shape 可能退化成 contiguous 临时张量再 `ViewCopy`，必须在 153 上确认以下三点：

1. padding/相邻平面完全不被覆盖；
2. ACLGraph capture/replay 正常；
3. decode `T=1` 和典型 prefill 下，相对 `npu_scatter_pa_kv_cache` 的耗时与 workspace。

另一个备选是仓库现有的 `npu_scatter_nd_update_v2`。它已经把目标 Tensor 的真实 stride 传进算子：

[`torch_binding.cpp`](<redacted:local-path:5ce75f691883>:1780)

这对 `[token, 2] = [block_id, block_offset]` 的 GQA 写入语义正合适。它目前只注册了 `ascend910b/ascend910_93`，所以：

- 153 如果是 A2/A3，可以和 `IndexPutImpl` 一起实测比较；
- 如果最终要覆盖 950/A5，还需要补 arch35 注册和构建验证。

### assistant:final_answer
对，这个修正是对的。:codex-annotation{index="1"} 我之前把自定义 `npu_scatter_nd_update_v2` 放进候选方案不合适；它是 CANN 9.1 正式支持首轴非连续前的临时版本，不应该继续扩展。

CANN 9.1 正式的 [`aclnnScatterNdUpdate`](https://www.hiascend.[REDACTED_SECRET].md)明确支持：

- `varRef` 首轴 stride 大于连续布局期望值；
- 其余各轴连续；
- 直接基于非连续 view 更新，不先把 `varRef` 转成连续 Tensor；
- A2、A3 均支持；
- `varRef` 支持 FP16、BF16、INT8 等类型；
- 默认确定性执行。

这和我们的 GQA cache view 完全匹配：

```text
varRef:  [num_blocks, block_size, num_kv_heads, head_dim]
stride0: physical_page_size / dtype_size
indices: [num_tokens, 2]             # block_id, block_offset
updates: [num_tokens, num_kv_heads, head_dim]
```

TorchNPU 已经直接暴露：

```python
torch_npu.npu_scatter_nd_update_(cache, indices, updates)
```

底层就是 `aclnnScatterNdUpdate`，[op-plugin 映射在这里](https://github.[REDACTED_SECRET].cpp)。仓库现有 SFA 路径也已经调用正式接口，例如 [`sfa_v1.py`](<redacted:local-path:98ff6d135e43>:1380)。

因此 GQA writer 应改成：

```python
slots = slot_mapping[:num_actual_tokens]
indices = torch.stack(
    (slots // block_size, slots % block_size),
    dim=-1,
).to(torch.int32)

torch_npu.npu_scatter_nd_update_(
    key_cache,
    indices,
    key[:num_actual_tokens],
)
torch_npu.npu_scatter_nd_update_(
    value_cache,
    indices,
    value[:num_actual_tokens],
)
```

更完整的链路里，`indices` 不应在每个 attention layer 临时构造。应该在 `prepare_inputs`/attention metadata 阶段由 flat `slot_mapping` 生成一次 `[T,2]` buffer，然后全部 GQA 层复用，避免 20 层重复除法、取模和 `stack`，同时方便 ACLGraph 使用固定地址。

修正后的优先级是：

1. 主方案：CANN 9.1 `torch_npu.npu_scatter_nd_update_`。
2. `index_put_`：只保留为正确性对照，不再作为正式候选。
3. 自定义 `npu_scatter_nd_update_v2`：停止扩展，并逐步删除。

删除临时 V2 不能只处理 GQA。目前它还被这些链路使用：

- DSA compressor/indexer：[`device_op.py`](<redacted:local-path:b2b96c6e9f46>:700)
- MiniMax M3：[`minimax_m3.py`](<redacted:local-path:0f111da39d6d>:131)
- 自定义 binding：[`torch_binding.cpp`](<redacted:local-path:5ce75f691883>:1780)
- 自定义源码及构建注册：`csrc/moe/scatter_nd_update_v2`

比较安全的迁移顺序是：先给正式算子补首轴 stride、非零 storage offset、guard plane、ACLGraph 测试；再替换全部调用点；最后删除 V2 的 C++、binding、meta 和构建项。

所以现在 GQA 写 KV 的结论可以从“缺少可用算子”修正为：

> CANN 9.1 已有规格完全匹配的正式算子；当前缺的是接入、metadata 中复用 `[block_id, block_offset]` indices，以及 153 上的图模式和性能验证。
