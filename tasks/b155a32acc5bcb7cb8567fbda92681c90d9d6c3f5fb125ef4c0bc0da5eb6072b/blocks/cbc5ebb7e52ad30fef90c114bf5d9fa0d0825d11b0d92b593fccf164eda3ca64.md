Annotation 1：同意，这个旧补丁不是有效修复方向。

SGLang 的处理并不是给 dummy row 塓 `accepted_tokens=0`，而是：

- 图内按 batch bucket 补齐。
- 图输出后按 `raw_bs × token_width` 裁掉 padding。
- acceptance、draft KV、KDA state commit 都只处理真实请求。
- verify 阶段的 KDA persistent state 不立即更新，验收后才按真实 `accept_lens` 提交。

因此旧补丁只修改 dummy 的 accepted-token 哨兵，无法排除 padded logits、hidden states 或 KDA scratch 对后续状态的污染。vLLM 更应对齐 SGLang 的“graph padding 不越过 graph runner 边界”语义。

建议直接做如下 A/B：

1. 使用 issue #32519 的 SGLang 镜像和启动参数，但换成当前 vLLM 的同一条连续中文请求。
2. 两侧统一 GQA DSpark 权重、greedy、K=7、verify=8、关闭 prefix/radix cache。
3. 测 `max_tokens=8/16/32/64/128`，先并发 1，再并发 32，记录逐个 verify block 的接受长度。
4. vLLM 再仅切换 eager 与 `FULL_DECODE_ONLY`；如果只有 ACLGraph 出现 `None` 或接受率持续衰减，就集中检查：
   - 图退出时 logits/target hidden/aux hidden 是否裁到真实 token 数；
   - acceptance 数组是否仍包含 dummy request；
   - draft KV 与 KDA commit 是否只提交真实请求；
   - position、slot、accepted state 是否从第二个 block 开始漂移。

判定会很直接：

- 第一个 block 就与 SGLang 分叉：查 proposer 输入、aux hidden、mask/position。
- 开始正常、随后下降：查 draft KV/KDA accepted-state commit。
- 仅 ACLGraph 异常：查 padding/裁剪边界。
- 两边同样低：才考虑 GQA checkpoint 本身对该请求的接受能力。

另外，issue #32519 只证明这套 SGLang 部署能够运行，没有给同一连续中文请求的接受率，因此不能拿它的简单请求直接判定 vLLM 的 10.64% 异常；必须跑同 workload 才有对照价值：[SGLang issue #32519](https://github.com/sgl-project/sglang/issues/32519)。
