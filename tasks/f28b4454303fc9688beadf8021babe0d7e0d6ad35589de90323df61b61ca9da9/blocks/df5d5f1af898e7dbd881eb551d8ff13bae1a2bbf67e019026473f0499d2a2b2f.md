静态审阅结论：

- 当前 K3 profile forward 没有 `max_model_len` 相关的 NPU 张量形状。KDA/MLA profile metadata 为 `None`，只执行固定 token 数量的投影和输出；因此不应修改 K3 forward。

- 本地 worker 的 pre-exit peak override 在当前已回退 pre-KV graph capture 的流程中是冗余的，但不会自行制造 maxlen 依赖。
- 已找到的显式 maxlen 分配均不支持成为当前峰值根因：
  - NPU block table 在 profile 前分配，而且只有 KB 级。
  - MLA chunked-prefill workspace 位于 `attention/utils.py:76-101`，但在显存 profile 后的 KV/backend 初始化阶段才创建。
  - KDA cache/block-size 配置同样在 profile 后生效。

若严格 A/B 确实复现，最小安全修复是先拆分指标，而不是把 lazy allocation 移到 profile 前：

```text
B = profile 前 current allocated
A = profile 后 current allocated
P = profile 区间 peak allocated

persistent = max(A - B, 0)
transient  = max(P - max(A, B), 0)
total      = P - B
```

KV 预算继续使用 `total`；日志分别输出 persistent profile buffers 与 transient activation。简单提前或扣除 lazy buffer 会让该部分既不计入 weights，也不计入 non-torch，导致 KV 过量分配和潜在 OOM。
