### 阻断：`activate` 可接受已消失的 supervisor guard

在 [.agents/lib/vaws_npu_coordination.py:1029](<redacted:local-path:83d6f4042a92>:1029)：

```python
if not process_guard_busy(process_guard, completion_confirmed=True):
    raise CoordinationError("managed supervisor is no longer present")
```

`completion_confirmed=True` 会绕过 `retain_until_release`。当 guard 格式合法、boot id 正确、但 marker 已不在 `/proc` 时：

```python
process_guard_busy(guard, completion_confirmed=True) == False
```

于是 `activate()` 反而继续接受一个已经丢失的 supervisor。可复现竞态是：`job_host_pid()` 成功后、`activate()` 前杀掉 supervisor，再提交同一 guard；lease 会进入 active，但 `go` 随后看到 supervisor 丢失并变成 `uncertain`，无法自动收敛释放。

这不是现有 `process_guard_busy` 默认语义可直接替换解决的问题，因为默认调用会因 `retain_until_release` 保守返回 busy。最小修复建议是增加明确的 `process_guard_present()` 检查，activation 必须要求 marker 当前存在；`completion_confirmed` 只允许用于 release。

知识库查询该签名无既有匹配。未修改文件、未跑 unittest/NPU。

### 其余边界确认

- setsid 且清除 marker 的后代：supervisor 存活时由 ancestry 捕获，stop 会继续 drain。
- supervisor crash：当前会保守保持 `uncertain/orphaned_busy`，不会错误释放；代价是需要显式人工 reconciliation。
- timeout/stop：不会杀 subreaper anchor；anchor 卡死时 force 也可能无法自动收敛，这是当前安全优先边界。
- lease release：managed 路径只有在 remote `quiet` 后才带 `completion_confirmed=True`，这部分逻辑方向正确。
