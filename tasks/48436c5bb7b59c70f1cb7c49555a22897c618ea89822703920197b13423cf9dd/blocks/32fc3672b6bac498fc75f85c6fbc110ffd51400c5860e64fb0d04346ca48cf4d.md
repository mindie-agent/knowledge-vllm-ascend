**我们自己的开发范围应尽量收敛到三个接入点：**

- `vaws init`：安装配置、创建两个 fork、接入各 Agent 客户端。
- 贡献发布：把整理后的知识脱敏，转换成可审阅的 Git diff 并提交 PR。
- 公共知识流转：连接 Grok 审核、按类型收录、合入后的同步导入。

其中，公共 PR 的去重可以复用引擎查找候选和处理记忆更新的能力，再接入审核规则；不能把现成的“记忆合并”直接当作跨用户、并发 PR 去重已经完成。

**OpenViking 最大的待验证点，是它与 Git 内容库之间的转换成本。** 它有自己的 URI、metadata 和存储约定，已有 OVPack 导入导出，但这属于迁移能力。我们要验证它能否在不修改核心存储的情况下，完成“可读文件 → PR → 另一台机器导入”，并保留来源、适用条件和更新关系。[OVPack 文档](https://github.[REDACTED_SECRET].4.19/docs/en/guides/09-ovpack.md)。

如果这里需要大改核心，备选就是 **Basic Memory + Docling**：前者负责 Markdown、索引和 MCP，后者负责 PDF、Office、OCR 等解析。它更贴近 Git 文件流转，但经验自动归纳与合并需要更多集成。[Basic Memory](https://github.com/basicmachines-co/basic-memory)、[Docling](https://github.com/docling-project/docling/blob/v2.126.0/README.md)。

组合时让一个主体统一负责存储和索引；Docling 这类互补能力作为依赖接入。fork 保留上游结构，定制优先放在配置、模板和适配层，方便持续跟进上游。

我已把[设计稿](<redacted:local-path:5cea93e5ea4e>)改成这个复用策略。**下一步最有价值的是验证 OpenViking 的 Git 内容往返成本**，这比继续细化自研架构更能决定选型；目前结论来自源码和接口核对，尚未部署实测。

决定性因素是 **QMD 更贴合文件直接归 Git 管理的路径**：修改、改名、删除后的索引更新，以及从仅含 Markdown 的 Git clone 重建索引，都已验证。Basic Memory 的写入和 metadata 工具更完整，但它先接受数据库变更、再异步落盘，接 Git 发布还需要确认文件同步完成。

具体组合建议是：

- **QMD + 本地多语言 embedding**：复用索引和检索，默认关闭查询扩写、重排。
