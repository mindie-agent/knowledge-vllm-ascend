`enforce_eager` 两层语义需要分开：

1. 顶层 `--enforce-eager`

   Core 会同时关闭 `torch.compile` 和 CUDAGraph/ACLGraph：[vllm.py](<redacted:local-path:9768c8c05d6b>:1167)。这是当前 run 已经命中的路径。

2. speculative config 中的 `"enforce_eager":true`

   在 Ascend proposer 中首先用于令 `self.use_cuda_graph=False`：[llm_base_proposer.py](<redacted:local-path:2532dd20186b>:204)。它本身主要是 draft graph 开关，不应一般化为等价于全局关闭 compile。

   但当前配置还启用了 `enable_flashcomm1=true`，因此 draft 构造时会进入 `_maybe_eager_context`，临时把 compilation mode 设为 `NONE`；`@support_torch_compile` 随即把 draft 模型永久标成 `do_not_compile`：
   - [utils.py](<redacted:local-path:3a8d47f9b1f8>:194)
   - [decorators.py](<redacted:local-path:39c6f34466be>:390)

   此外 DSpark proposer 自身还无条件设置 `self.use_cuda_graph=False`：[dspark_proposer.py](<redacted:local-path:0d90b0a0ceac>:78)。

还有两个容易混淆的点：

- Ascend 的 `fuse_qknorm_rope` 默认开启，只表示编译路径运行时会把 `QKNormRopeFusionPass` 加入 pass manager；当前没有进入编译路径，所以它完全未执行。
- 当前 probe 补丁确实额外调用了一次 `DeviceOperator.split_qkv_rmsnorm_rope` 来记录 `layer0_*_fused` 和 delta，但这是诊断旁路。真实返回值仍来自 separate `q_norm → k_norm → rotary_emb → attention`，不能把 probe 中的 fused 数值理解为实际 forward 使用了 fusion。

补充：该 DSpark checkpoint 的 `head_dim=64`，而当前 GraphFusion pattern 仅对 `head_size==128` 注册替换；以 draft attention 元信息初始化时会打印：

```text
QKNorm and Rope fusion not enabled: head_dim 64 is not equal of 128
```

因此当前低接收率不能归因于“vLLM 实际走了 GraphFusion QKNorm+RoPE，而 SGLang 没走”。更合理的对比是当前 vLLM separate eager 路径与 SGLang fused `split_qkv_rmsnorm_rope` 的逐层数值差异。此次只读审计没有修改任何本地或远端文件。
