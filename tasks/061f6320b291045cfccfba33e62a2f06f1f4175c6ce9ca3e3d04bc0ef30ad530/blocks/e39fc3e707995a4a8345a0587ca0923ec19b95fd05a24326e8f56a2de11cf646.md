最可能根因排序：

1. AscendC 存在明确的“返回有效 Tensor，但内容从未写入”路径。

   - Torch adapter 使用 `at::empty_like(value)` 分配输出：
     `csrc/attention/recurrent_kda/recurrent_kda_torch_adpt.h:117`
   - kernel 遇到非法 `cu_seqlens`、任意有效长度 sequence 的非法 slot、或 initial slot 解析失败，会直接结束整个 core：
     `csrc/attention/recurrent_kda/op_kernel/recurrent_kda.h:201-238`
   - slot 校验位置：
     `csrc/attention/recurrent_kda/op_kernel/recurrent_kda.h:242-307`
   - arch35 版本也有相同控制流：
     `csrc/attention/recurrent_kda/op_kernel/arch35/recurrent_kda.h:204-242`

   这不会抛 Python 异常，也不会返回 `None`，而是把未初始化显存作为正常输出返回。它非常符合“服务健康、图捕获成功、首 token 后语义立即损坏”的表现。

2. Triton 与 AscendC 的 null-slot 语义不一致。

   - Triton 在 `state_idx <= 0` 时把当前 program 当成无效请求并返回：
     `vllm_ascend/ops/triton/kda/fused_recurrent_kda.py:99-108`
   - AscendC 仅将 `<0` 或 `>=capacity` 判为非法，slot 0 被当成正常 cache：
     `csrc/attention/recurrent_kda/op_kernel/recurrent_kda.h:269-276`
   - vLLM 图模式会使用 null block，并通过重复 `cu_seqlens` 构造零长度 dummy row：
     `vllm_ascend/ops/gdn_attn_builder.py:331-368`
   - worker 还会将 graph dummy block table 填为 0：
     `vllm_ascend/worker/model_runner_v1.py:3065-3069`

   正常情况下零长度 row 会先跳过；但一旦 ACLGraph replay 中 `query_start_loc` 和 slot metadata 有一步错位，AscendC 就会读取 slot 0，或因 `-1` 直接让整个 core 退出，留下未写输出。

3. 现有 compiled-wrapper 测试没有覆盖真实的 module-owned cache。

   `_forward` 实际从 `self.kv_cache` 取 persistent state：
   `vllm_ascend/ops/kimi_kda.py:409`

   现有测试却把 state 作为显式 `forward` 参数传入 `_run_recurrent`。它能验证 schema functionalization，但不能证明 ACLGraph replay 会把 `self.kv_cache` 的更新传给下一 token。这仍是高优先级嫌疑。

4. `None` 返回契约本身在当前 f9/8e312d 已经闭合。

   - Python 接单 Tensor：`vllm_ascend/ops/kimi_kda.py:275-295`
   - schema：`csrc/torch_binding.cpp:2615-2620`
   - meta：`csrc/torch_binding_meta.cpp:790-827`
   - native 返回：`recurrent_kda_torch_adpt.h:117-148`

   原始 `84e806f` 确实存在 `out, _ = op` 与 tuple alias 契约问题，但 f9 已修复。HTTP 响应中的 `content=null` 更像 reasoning 未闭合后的上层表示，不等于 native operator 返回了 Python `None`。

5. gate、layout 和 TP16 head 映射未发现足以解释该故障的静态分歧。

   safe gate 公式一致；K3 TP16 的 `H=HV=6, K=V=128` 下 output layout/head mapping 一致。数值差异是 Triton L2 norm 使用 `sqrt(sum + 1e-6)`，AscendC 没有 epsilon；正常真实投影下不太可能导致稳定无限复读。

建议最小正向修复：

- adapter 输出改为确定性初始化，例如 `zeros_like(value)`，先消除 silent garbage。
- kernel 不应因某个 sequence 的非法/null slot 结束整个 core；应只跳过对应 row，并保证其输出为零。
- 明确统一 slot 0、`NULL_BLOCK_ID`、`PAD_SLOT_ID` 的语义。
- 增加 module-owned `self.kv_cache` 的 compile + graph replay 多 token 回归，不能只测显式 state 参数。

真实 5 层/TP16 单算子 fixture 至少保存：

- 每层每步 `q/k/v/raw_gate/beta`
- `state_before/state_after`
- `cu_seqlens/state_indices`
- `A_log`、flat `dt_bias`
- output 的类型、shape、stride、dtype

同文件 CPU reference 测试必须断言：

- 返回对象是 defined Tensor，绝非 `None`
- output 全部覆盖预设 poison/sentinel，且全部 finite
- active slot 更新，untouched slots bitwise 不变
- step N 的 `state_after` 等于 step N+1 的 `state_before`
- 每步 output/state 同时对齐 Triton 和同文件 reference
- 覆盖 graph padding：`cu_seqlens=[0,1,1,...]`、`state_indices=[real_slot,0,...]`
- 单独覆盖 positive-length slot 0、`-1`、out-of-range，确保不会产生未写输出或连带终止其他有效 sequence

所有后续若需编译，应固定使用 `MAX_JOBS=256` 或 `-j256`。

### assistant:final_answer
根据 Triton kernel，这个 case 的期望行为不是“后面 15 个无效 row 输出为 0”，而是：

- 第 0 个有效 row：
  - `bos=0, eos=1`
  - 处理 token 0
  - 写入 `out[:, 0]`
  - 更新 active state slot 2

- 后面 15 个 padding row：
  - 都是 `bos=1, eos=1`
  - `T=eos-bos=0`
  - Triton 在读取 `state_indices` 之前直接 `return`
  - 不读取 slot 0
  - 不更新任何 state
  - 不写任何 output

关键点是 Triton 的 output 由 `torch.empty_like(k)` 分配。因此：

```text
out[:, 0]     必须是正确、有效的结果
out[:, 1:16]  未定义，不保证为 0
```

这些零长度 row 并不分别对应 token 1–15；它们全部指向相同的 terminal offset 1，没有消费任何 token。

所以当前红测的断言是正确的：

1. 只比较 `ascendc_out[:, :active_tokens]`，不检查 padding tail。
2. active slot 必须与 Triton/reference 一致。
3. 其他 state slot 必须保持不变。
4. 不应该要求 `out[:, 1:16] == 0`。

另外，尾部的 `state_indices=[0,...,0]` 在这个 case 中不会被 Triton 读取，因为 `T==0` 的判断发生在 state 读取之前。只有当某个正长度 row 使用 slot 0 时，Triton 才会将其视为 null row，并且同样不写 output/state。

因此 AscendC kernel 的最低正确修复应是：

```text
允许 cu_seqlens[-1] <= QKV capture capacity
处理 cu_seqlens 覆盖的有效 token
跳过零长度 row
不更新 dummy state
```

把 padding output 显式清零属于更安全的确定性增强，但不是 Triton 当前保证的语义，也不应作为这个兼容性用例的必要断言。



### user
当前的问题是什么，在有padding的场景下ascendc的kernel会不写有效的row吗


### assistant:final_answer
是的。当前问题就是：存在 graph padding 时，AscendC kernel 连有效 row 也不会写。

以当前红测为例：

```text
QKV capacity = 16
cu_seqlens = [0, 1, 1, ..., 1]
```

语义上：

- row 0：长度 1，有效，必须计算并写 output、更新 state。
- row 1–15：长度 0，应直接跳过。

但 AscendC 在进入逐 row 循环前执行全局校验：

```cpp
return cu_seqlens[-1] == T;
```

此时：

```text
cu_seqlens[-1] = 1
T = QKV capacity = 16
```

因为 `1 != 16`，整个 kernel core 提前返回，row 0 根本没有被处理。因此：

- 有效 row 的 output 没写；
- 有效 state slot 没更新；
- adapter 返回的 output 来自 `empty_like`，内容未定义；
- 没有直接报错，服务仍可能保持健康，但 decode 结果被破坏。

这与 Triton 不同。Triton逐 row 处理：

- row 0 正常计算；
- row 1–15 因长度为 0 分别跳过；
- 不要求 `cu_seqlens[-1]` 等于 capture capacity。

所以需要修复的核心条件是：AscendC 应允许

```text
cu_seqlens[-1] <= QKV capture capacity
```

然后正常处理 `[0, cu_seqlens[-1])` 内的有效 token，跳过零长度 padding row。当前红测已经通过 state 未更新稳定证明了有效 row 被整体漏写。
