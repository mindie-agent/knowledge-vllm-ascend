### ① 冻结实验身份

```text

模型与权重
prompt token hash
request ID
DP / TP rank
实验开关
```

效果：

> 先证明比较的是同一份代码、同一个请求，避免把版本漂移当成精度差异。

---

### ② Agent 生成采集脚本

Agent 为所有 rank 生成统一记录格式：

```text
{
  request,
  dp,
  tp,
  step,
  stage,
  layer,
  group,
  block,
  shape,
  finite_count,
  hash
}
```

效果：

> 不让 64 个进程各说各话；后续脚本可以直接 join、排序和比较。

---

### ③ 64 rank 粗粒度扫描

只扫描：

```text
最后完成的阶段
当前 collective 序号
错误 / 超时
请求是否返回
```

效果：

> 先判断是一个 rank 掉队，还是所有 rank 在同一个位置等待。

真实结果：

```text
所有 TP rank 停在同一阶段
→ 排除单 rank 掉线
→ 向更早的异步计算继续追
```

---

### ④ 目标 DP 的 16 TP 结构化采集

全量健康扫描覆盖 64 workers；精度定位则只聚焦问题所在 DP 的 16 个 TP rank：

```text

worker-tp00.jsonl
...
worker-tp15.jsonl
```

效果：

> 既保留全局视角，又避免一上来 dump 64 份大 Tensor。

### ⑤ 清洗与统一字段

Agent 自动完成：

```text
去重
request-aware chunk 合并
统一 stage 名
统一单调时钟
补齐 rank 和 block 身份
生成 manifest 与文件 hash
```

这里可以讲一个很真实的细节：

> 最早一版采集器把三个 prefill chunk 当成三个请求。Agent 在分析时发现 request ID 相同，主动修正为“按请求去重”，避免用错误样本做根因判断。

这个细节很好，因为它说明 Agent 不只是处理日志，也会检查日志本身是否可信。

### ⑥ 按业务身份对齐

不要按日志行号，也不要只按墙上时间，而是按：

```text
request ID
+ step
+ stage
+ layer/group
+ logical block
```

再额外建立：

```text
logical block → physical page/address
```

效果：

> 即使各 rank 打印速度不同，也能比较“同一个请求的同一个状态”。

---

### ⑦ 计算轻量指纹并比较


效果：

> 大段日志被压缩成“每个阶段一行指纹”；只有发现差异的层和块才升级为定向 Tensor dump。
