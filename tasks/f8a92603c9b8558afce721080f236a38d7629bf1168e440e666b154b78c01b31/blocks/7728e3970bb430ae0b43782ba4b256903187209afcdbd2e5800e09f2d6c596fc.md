## output-copy 为什么可以排除

async-on 确实有一个潜在生命周期缺口：

- `AsyncGPUModelRunnerOutput` 在 side stream D2H，并只由 `get_output()` 同步。
- multiproc 只在 `output_rank` 调用 `handle_output/get_output`；非 output rank 的 wrapper 从不显式 close/discard。
- `AsyncModelRunnerOutput` 也没有 discard 契约：[outputs.py:297](<redacted:local-path:d7dec7b07cab>:297)。

但 async-off：

- stream 不创建；
- [model_runner_v1.py:2353](<redacted:local-path:9c7b6dd8cdd5>:2353) 的 wrapper 分支不可达；
- r7 仍在首 `execute_model` 挂。

所以该生命周期缺口是独立潜在缺陷，不是当前卡死的必要原因。

## Mamba global-stream 的真实但非 H0 缺口

现有 wait 位置偏晚：

1. 下一 `execute_model` 先执行 `_update_states`：[model_runner_v1.py:1777](<redacted:local-path:9c7b6dd8cdd5>:1777)。
2. `_prepare_inputs` 先把 block table H2D commit：[model_runner_v1.py:831](<redacted:local-path:9c7b6dd8cdd5>:831)。
3. 到 [model_runner_v1.py:1049](<redacted:local-path:9c7b6dd8cdd5>:1049) 才同步上一 global-stream event。
4. 而 fused Mamba postprocess 持有 persistent block-table device tensor：[mamba_utils.py:1103](<redacted:local-path:c71ecbe1faba>:1103)。

因此上一 global kernel 读取 block table 时，下一 step 的 H2D 有理论竞争。它可能影响长 prefix、request condense/preemption、acceptance 变化，但 DP3 新请求首 execute 没有上一 post-sample producer，不能解释 short-H0。

无全局同步的修复 seam 是：在下一 `execute_model` 进入 `_update_states` 前，让 current stream `wait_event(num_accepted_tokens_event)`；保留后面的 host event synchronize，用于真正读取 accepted-count CPU buffer。这样先保护 device block table，再在 CPU 消费点等待 D2H。

## ACLGraph/update-stream 语义

- target FULL graph 才创建 `update_stream`：[model_runner_v1.py:3547](<redacted:local-path:9c7b6dd8cdd5>:3547)。
- `ENPU_ENABLE=false` 时顺序是 replay 后 update；FULL replay 前 wrapper 会 current-stream synchronize：[model_runner_v1.py:2611](<redacted:local-path:9c7b6dd8cdd5>:2611)、[acl_graph.py:252](<redacted:local-path:664fe8fc8993>:252)。
- `ENPU_ENABLE=true` 时 runner 先同步并 update，再 replay。
- DSpark 自己 eager，不存在 draft ACLGraph update stream。

因此 r7 需要先从日志确认首 execute 的 `cudagraph_mode`。如果是 `NONE`，ACLGraph/update-stream 也不在 fatal 路径；如果是 `FULL`，应检查 update ExternalEvent 是否每个 MLA layer、每个 rank 等量执行。

## 最小 event seam 与测试

若仍要对 draft producer 假设做代码级反证，最小 seam 是：

- `_propose` 完整返回后记录一个 runner-owned event，不能只在 `precompute_and_store_context_kv` 后记录，因为后续 query forward 仍使用 L2/L3。
- 下一 target `_model_forward` 前由 current stream `wait_event`。
- worker 串行模型下，一个 event 加 pending flag 足够；顺序为 `record_i → wait_{i+1} → record_{i+1}`。未来若引入同 worker 真并行，再改成 per-batch/ring event。

该 seam 在正常 current-stream 契约下应是 no-op；若它改变结果，才说明存在隐藏 stream/runtime 契约问题。它无法修复当前首 execute H0。

最小单测建议：

- mock stream/event，断言 `_propose` 返回后 record，下一 target 前且仅一次 wait。
- 非四平面或非 Qwen3 DSpark 不触发 event。
- 两轮验证 `record1/wait1/record2/wait2`，防 event 重用错误。
- async-off 断言 valid-count/output-copy stream 为 `None`，且不构造 `AsyncGPUModelRunnerOutput`。
- Mamba 回归测试断言 producer event 的 device wait 发生在 `_update_states` 和 `commit_block_table` 之前。
- multiproc async-on 测试覆盖非 output rank wrapper 的明确 discard/lifetime closure，但作为独立修复，不和 H0 混绑。
