### assistant:final_answer
看过了，问题大概率在 All2All dispatcher，不是 AllGather。

在 [token_dispatcher.py](<redacted:local-path:eb39abe40739>:479)：

```python
with_quant = token_dispatch_input.quant.dispatch_with_quant
```

而 `dispatch_with_quant` 对 `QuantType.MXFP4` 固定返回 `True`。这会进入第 498 行，对激活做 FP4 动态量化，随后第 654 行调用 `npu_moe_init_routing_v2`。这条路径在 A5 MXFP4 上有已知的数据类型/packed shape 识别问题，容易出现 routing tiling 或维度错误。

核心问题是：权重为原生 MXFP4，不等于 dispatcher 必须对激活做 MXFP4 通信量化。两种语义被 `dispatch_with_quant` 混在一起了。

建议 All2All 对 MXFP4 暂时关闭 dispatcher 量化：

```python
with_quant = (
    token_dispatch_input.quant.dispatch_with_quant
    and token_dispatch_input.quant.quant_type != QuantType.MXFP4
)
```

同时第 654 行必须跟着加 `with_quant` 判断：

```python
if with_quant and scale_type == torch.float8_e8m0fnu:
```

否则关闭量化后，`dynamic_scale_after_all2all` 是 `None`，仍会在 `.view()` 处报错。

这样 dispatcher 使用 BF16/FP16 通信，MLP 收到 `dynamic_scale=None` 后，会在 [moe_mlp.py](<redacted:local-path:865a9ff9d3c7>:364) 内重新执行 MXFP4 动态量化，功能链路是完整的，只是暂时没有 FP4 通信带来的性能收益。

另外，AllGather 路径第 357–361 行已经实现了类似保护，所以如果实际报错来自 `TokenDispatcherWithAllGather`，需要再结合完整堆栈确认。当前我只做了定位分析，没有修改代码。
