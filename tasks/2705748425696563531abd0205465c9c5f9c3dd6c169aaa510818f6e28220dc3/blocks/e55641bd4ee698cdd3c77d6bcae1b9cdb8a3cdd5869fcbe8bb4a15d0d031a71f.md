### 可以复用现有代码

已有的 [NPU coordinator](<redacted:local-path:499fb43a699a>:248) 已经包含队列、租约和事件记录。建议在它上面增加 MCP 接口：

- **协商操作**：请求让卡、同意、延后、拒绝。
- **消息操作**：读取事件、确认已读，支持断线后继续读取。

所有实例必须访问**同一份资源权威状态**，不能每个工作树各存一份独立的分配记录。也不必另建仓库，可以先作为当前仓库的独立模块，保持现有 `remote-dev` 工具接口不变。

### 但“做成 MCP”不等于“不需要常驻”

| 形态 | 适用场景 |
|---|---|
| 每个客户端启动 stdio MCP，共用主机侧状态 | 按需申请、轮询协调，无需额外常驻服务 |
| 共享的 Streamable HTTP MCP 服务 | 多客户端统一接入，后台持续处理等待队列 |

stdio 通常由客户端启动子进程；Streamable HTTP 支持独立服务接受多个客户端连接。[官方协议说明](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/transports/streamable-http.mdx)

**如果希望“卡一释放，后台就推进等待请求”，我推荐第二种。** 协调循环直接放在 MCP 服务里，不需要再启动另一个协调 daemon，也不需要常驻一个 LLM。服务应部署在稳定在线的管理机上，并做好鉴权。

还有两个边界要保留：

- **MCP 消息不会自动让暂停的 Agent 开始工作**，仍需事件轮询或客户端唤醒接入。
- **同意让卡不等于已经释放**，必须确认原任务退出、资源空闲后才能重新分配。

所以我的选择是：**独立协调 MCP + 复用已有协调内核；`vaws-top` 后续接入展示即可。** 前面 #66 的租约安全修复仍然需要做。

### 我建议拆成三个层次

| 层次 | 保存什么 | 生命周期 |
|---|---|---|
| **Session** | 任务身份、实际代码工作树、偏好与约束 | 长期存在，不必绑定机器 |
| **Environment** | 镜像、依赖、模型及构建产物的版本化环境 | 可提前准备、缓存复用 |
| **Run + Lease** | 本次执行使用的机器、容器、卡和端口 | 执行时绑定，结束后归还资源 |

这样，同一个 session 今天可以在 A 机器验证，明天在 B 机器跑性能；**已经运行的任务仍固定在其执行环境中，不意味着支持运行中迁移。**

### 正常使用应该是这样的

你说“验证这个修改，需要两张卡”，Agent 提交环境和资源需求，MCP 选择兼容且可用的机器，准备隔离环境、取得租约，再通过现有远程工具同步代码并执行。结束后回收结果、释放算力，session 和可复用缓存保留。

人不用参与日常排队、协商，但可以通过对话明确指定：

- “这个任务只用 155。”
- “给任务 A 预留四张卡一小时。”
- “没有空闲资源就等，不要影响其他任务。”

这些应成为可查询、有记录的约束或预留，不能默认理解成强行停止别人的任务。

### 环境提前准备也应独立出来

仓库已经有 prepared-image 缓存，可以作为起点。进一步可以提前拉镜像、安装依赖、缓存模型和兼容的构建产物，**无需因此长期占卡**。真正需要 NPU 的 smoke、模型加载和预热，则在取得租约后进行。

共享的是环境缓存；每次执行仍需要隔离的可写目录，并校验实际代码、依赖和产物版本，避免不同任务互相污染。

**所以我会把第一版目标定为：独立 MCP、机器资源池、环境预备、按运行分配租约，以及通过 Agent 对话显式控制资源。** 核心改动是这套生命周期，MCP 是它的统一入口；现有远程读写和执行工具继续复用。

### 1. 本地修改后增量同步，不等启动时再搬代码

### 2. 按实际变化复用编译产物

| 本次变化 | 应有行为 |
|---|---|
| Python 逻辑变化，原生依赖未变 | 同步源码，复用已有原生产物 |

缓存要匹配**源码及构建依赖摘要、SoC、CANN、Python/torch ABI、编译选项**。算子产物应连同注册库、配置和元数据完整保存，不能只复制一个 `.so`，也不能直接搬带旧绝对路径的 `CMakeCache`。

### 3. 提前准备完整、验证过的版本组合

**CANN + torch/torch_npu + vLLM + VA + 算子产物 + 启动环境配置**

这样，MCP 负责分配兼容环境和资源，remote-dev 负责远端操作，同步与构建层负责让最新代码尽早就绪。**Agent 要启动服务时，大部分准备工作已经完成，只需处理本次修改带来的差异。**
