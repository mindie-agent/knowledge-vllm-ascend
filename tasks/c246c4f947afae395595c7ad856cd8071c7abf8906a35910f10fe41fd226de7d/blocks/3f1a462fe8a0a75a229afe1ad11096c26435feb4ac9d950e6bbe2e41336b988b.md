### 来源链

```text
DeepSeek-V4-Flash checkpoint
  └─ compressor.wkv / wgate / ape / norm.weight
        ↓
cann-recipes-infer Compressor 模块
        ↓ torch.ops.custom.compressor(...)
cann-recipes-infer custom_ops PyTorch binding
        ↓ aclnnCompressor
ops-transformer custom_transformer vendor
        ↓
Ascend AICore Compressor kernel
```

DeepSeek 官方参考实现里的 [`Compressor`](https://huggingface.[REDACTED_SECRET].py) 本身就是：

- `WKV` 投影生成被压缩的 KV；
- `WGate + APE` 产生组内权重；
- softmax 后对 token 做加权聚合；
- RMSNorm；
- 对部分维度做 RoPE；
- Indexer 那一路还会做 Hadamard rotation。

官方 [`config.json`](https://huggingface.[REDACTED_SECRET].json) 直接给出了 `compress_ratios=[0,0,4,128,4,128,...]`。官方 checkpoint 里也确实带着 `self_attn.compressor.*` 和 `indexer.compressor.*` 权重，不是运行时临时生成的；recipe 的 [`load_weights`](<redacted:local-path:58d969d48b31>:2772) 会把它们装进模型。

### C1、C4、C128 怎么配套

以下是按 Python 的零基 layer index 表示；文档若说“奇数/偶数层”，通常按人类的一基编号，所以看起来会反过来。

| 类型 | 层 | Compressor 配置 | 后续注意力 |
|---|---|---|---|
| C1 | 0、1 | 不压缩 | 仅 128-token SWA |
| C4 / CSA | 2、4、…、42 | `ratio=4, coff=2`，8-token 重叠窗口 | SWA + LI 筛选出的稀疏 compressed KV |
| C128 / HCA | 3、5、…、41 | `ratio=128, coff=1` | SWA + 全部 dense compressed history |

C4 实际上每层有两条逻辑 Compressor：

- Attention Compressor：`head_dim=512`，输出 `sfa_cmp_kv`。
- Indexer Compressor：`head_dim=128, rotate=True`，输出 `li_cmp_kv`，随后 Lightning Indexer 选 top‑512 compressed blocks。

对应构造在 [`compressor.py`](<redacted:local-path:cfa70a61a41b>:43) 和 [`indexer.py`](<redacted:local-path:0e6a081f76c3>:47)。C128 没有 Indexer，压缩后的历史直接作为 dense compressed 分支送入 SAS。最终不是两个 attention 结果再相加，而是同一次算子调用同时传：

- `ori_kv`：最近 128 token 的 SWA cache；
- `cmp_kv`：压缩历史；
- `cmp_sparse_indices`：仅 C4 提供。

调用编排可看 [`modeling_deepseek.py`](<redacted:local-path:58d969d48b31>:1350)。

### 底层算子如何接入

模型侧最终调用在 [`compressor.py`](<redacted:local-path:cfa70a61a41b>:312)：

```python
torch.ops.custom.compressor(
    x,
    wkv,
    wgate,
    ape,
    norm_weight,
    cos,
    sin,
    state_cache,
    state_block_table,
    cu_seqlens,
    seqused,
    start_pos,
    ...
)
```

输入除了四组模型权重，还有：

- FP32 的跨请求/跨 decode `state_cache`；
- 对应的 paged block table；
- RoPE cos/sin；
- `cmp_ratio`、`coff`、`norm_eps`；
- prefill/decode 的长度及起始位置。

仓库里的 [`npu_compressor.cpp`](<redacted:local-path:ae0b184f758e>:72) 只是 PyTorch binding，核心是调用 `aclnnCompressor`。真正的 AICore 源码在 [`ops-transformer`](https://gitcode.com/cann/ops-transformer/tree/master/experimental/attention/compressor)。运行时必须同时 source：

- `opp/vendors/customize/bin/set_env.bash`
- `opp/vendors/custom_transformer/bin/set_env.bash`

前者主要是 recipe 的配套自定义算子，后者才包含 Compressor、SAS、Lightning Indexer 等 transformer 算子。

### 如果你指的是 SGLang 单 NPU + CPU MoE 那套

这条集成不会直接使用 `models/deepseek_v4/.../compressor.py`，而是给 SGLang 的 NSA Compressor 打补丁，但最后仍调用同一个 `torch.ops.custom.compressor`。

仓库的干净 CANN 9.0 安装脚本钉死了：

- `ops-transformer`: `dd9f31f34`
- `cann-recipes-infer`: `c5cc95e`
- `sgl-kernel-npu`: `2026.6.2`

见 [`setup_dsv4_env_from_clean_cann.sh`](<redacted:local-path:801ff080f628>:61)。它会从 `ops-transformer` 构建：

```text
compressor
sparse_attn_sharedkv
sparse_attn_sharedkv_metadata
quant_lightning_indexer
quant_lightning_indexer_metadata
```

另外补丁兼容了两种 Compressor ABI：

- CANN 9.0+：单个交织 `[KV state | score state]` cache；
- CANN 8.5 私有版本：KV state、score state 分开。

由 `KT_NSA_COMPRESSOR_MODE=single|split` 控制，启动脚本会根据 CANN major version 自动选择。相关兼容来自 [MR/PR #682](https://gitcode.com/cann/cann-recipes-infer/pull/682)。

最后一个容易混淆的点：仓库虽然有 `ops/pypto_python/impl/compressor_pypto.py`，但它目前更像参考/算子示例；当前提供的 V4‑Flash 配置默认 `enable_pypto: False`，主模型 Compressor 仍走 `torch.ops.custom.compressor → aclnnCompressor → ops-transformer kernel`，不能把 PyPTO 文件当成当前生产链的来源。
