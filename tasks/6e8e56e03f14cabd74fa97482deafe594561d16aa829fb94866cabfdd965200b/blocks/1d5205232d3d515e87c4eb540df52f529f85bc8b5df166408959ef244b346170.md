## 1. 现在到底发生了什么

调度器操作的是逻辑 block ID，例如 block 1969、5224。它并不关心 block 最终位于哪段设备内存。

物理层必须保证：

```text
同一个逻辑 block ID → 每个 KV group 都映射到自己的合法物理区域
不同逻辑 block ID → 物理区域绝不能重叠
```

但当前 K3 组合中，target MLA/KDA、Mamba state 和 DSpark GQA draft 被放进了同一个 raw backing。不同 consumer 又按照各自的紧凑布局解释这块内存：

```text
target_addr(block) = base + target_offset + block * target_effective_stride
draft_addr(block)  = base + draft_offset  + block * draft_effective_stride
```

因为：

```text
target_effective_stride != draft_effective_stride
```

所以存在两个不同的 block ID，使其地址区间相交。

现有 dump 已经捕捉到一个真实交点：

- DSpark draft layer 94，block 1969
- target layer 23，block 5224
- 两者展开后指向相同的物理 backing 区域
- 下一轮 target layer 23 第一次读取 KV 时出现 448 个 NaN
- attention 随后全部 NaN，并从 layer 24 开始传播

所以可以分成两个确认级别：

- 已确认的直接损坏点：draft KV 写入和 target KV 读取发生物理别名。
- 尚待真实压测确认的修复：把不兼容布局拆开后，128K 历史请求场景是否完全恢复。

Prefix cache 不是制造错误的根因。它会复用较大的 block ID，并让请求历史更快覆盖更多物理地址，因此更容易撞到上述别名关系。这解释了为什么：
