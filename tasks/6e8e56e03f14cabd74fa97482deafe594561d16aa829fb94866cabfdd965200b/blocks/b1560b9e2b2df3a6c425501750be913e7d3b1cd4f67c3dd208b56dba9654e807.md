## 2. 为什么“提前把 padding 算进去”还不够

这里有两种不同的 padding：

1. 分配和计账上的 padding。
2. 每个逻辑 block 在真实物理布局中都按 padded stride 前进。

当前只做到了第一种。

`page_size_padded=488448` 会让 planner 认为：

```text
allocation_size = num_blocks * 488448
```

但在 Ascend ModelRunner 的 hybrid attention 分支里，它随后根据 draft 的真实 K/V 大小切出一段连续区域，再通过 `.view()` 形成紧凑 cache。相关逻辑位于 [model_runner_v1.py](<<redacted:local-path:b8dd889167fe>/vllm-ascend-v0.26.0rc-dspark-mla-linear-ci/vllm_ascend/worker/model_runner_v1.py:4215>)。

也就是说，draft 的实际寻址仍接近：

```text
base + block_id * 98304
```

而不是：

```text
base + block_id * 488448
```

额外分配的空间存在，但 consumer 没有按 padded page 跨过去。

同一个文件里，cache-only 路径实际上已经展示了正确做法：它使用 `torch.as_strided`，显式把 block 维 stride 设置为 `page_size_padded`，见 [model_runner_v1.py](<<redacted:local-path:b8dd889167fe>/vllm-ascend-v0.26.0rc-dspark-mla-linear-ci/vllm_ascend/worker/model_runner_v1.py:4176>)。但普通 attention/hybrid 路径没有执行同样的 stride contract。

所以你的直觉可以更精确地表述为：

> 如果 padding 从规划、分配、reshape 到 kernel 寻址全链路都生效，那么 padding 可以从根本上解决；只修改 planner 中的 page size 不行。

而全链路实现会涉及 ModelRunner 和 attention kernel，超出了 PR 13277 的边界。

## 3. 为什么 DSV4 没出现

DSV4 并不是没有同类风险，而是已经打过一个专门补丁。

[vLLM-Ascend PR #9367](https://github.com/vllm-project/vllm-ascend/pull/9367) 的描述非常直接：DSV4 MTP layer 与其他层共享 KV tensor 时，slot mapping 会影响主模型精度，因此把 MTP KV cache 单独分离。该 PR 已于 2026-05-20 合入。

当前代码仍然保留这个逻辑：

- 通过名称里的 `"mtp"` 找到 MTP 层。
- 不再把它放进普通 bucket。
- 每个 MTP layer 单独创建一个 `KVCacheTensor`。

见 [patch_kv_cache_utils.py](<<redacted:local-path:b8dd889167fe>/vllm-ascend-v0.26.0rc-dspark-mla-linear-ci/vllm_ascend/patch/platform/patch_kv_cache_utils.py:394>)。

所以 DSV4 没复现的真正原因是：

```text
DSV4 MTP 已经被物理隔离
而不是 DSV4 GQA/DSpark 的布局天然安全
```

同时，这个 DSV4 实现本身也是历史性的 model-specific workaround。它能证明“拆 backing”是有效的止血方式，但不代表我们也应该再增加一个 `"k3_dspark"` 特判。

更有意思的是，vLLM 主仓后来给 DSV4 做 packed cache 后，又真实发生过一次相同类别的问题：

- [PR #44577](https://github.com/vllm-project/vllm/pull/44577) 把多个 KV component 打包到每 block 连续 backing。
- [Issue #47783](https://github.com/vllm-project/vllm/issues/47783) 中 FlashInfer consumer 忽略了 runtime block stride，GSM8K 从约 95% 掉到约 0%。
- [PR #47493](https://github.com/vllm-project/vllm/pull/47493) 修正 consumer 侧寻址后，GSM8K 恢复到约 95%。

这和我们现在的问题几乎是同一个原则：

> planner 声明了 packed/padded layout，不代表 kernel 就自动按那个 layout 寻址。

## 4. vLLM 上游社区怎么考虑这个问题

上游的方向非常清楚：把“逻辑 cache 是什么”和“物理 cache 怎么排布”分开描述。

核心对象是：

- `KVCacheGroupSpec`：scheduler 的逻辑 cache group 和 block table。
- `KVCacheTensor`：worker 的物理 backing，包含 `size/shared_by/offset/block_stride`。
- `KVCacheSpec`：描述单层 cache 的形状、page size、padding、量化和布局能力。

[vLLM KV-cache layout RFC #42082](https://github.com/vllm-project/vllm/issues/42082) 希望最终形成统一的逻辑形状，由 spec/backend 声明物理布局；多个 layer 共享 backing 时，每个 layer、每个 block 的实际内容必须满足明确的连续性与 stride 约束。

针对混合 page size，[PR #45181](https://github.com/vllm-project/vllm/pull/45181) 已经引入并使用了 `indexes_kv_by_block_stride` 这一类能力描述。含义不是“这个 backend 支持 prefix cache”，而是：

> kernel 是否按 tensor 的 runtime block stride 索引 KV，而不是假设 page 永远紧密连续。

如果两个 group 的 indexing contract 不同，它们就不能只因为 `page_size_bytes` 相同而共享 backing。[PR #46992](https://github.com/vllm-project/vllm/pull/46992) 曾提出按 layout key 将不兼容 group 分池；该 PR 最终关闭、没有合入，但它的抽象正适合我们当前的短期方案。

Ascend 社区也已经意识到当前 ModelRunner 与上游分歧太大。[vLLM-Ascend RFC #13321](https://github.com/vllm-project/vllm-ascend/issues/13321) 提出的长期方向就是：

- layout 信息进入 `KVCacheSpec` 和 backend interface。
- allocation/reshape 使用通用的 `offset/block_stride`。
- attention kernel 全面审计并适配 strided view。
- 最后删除 Ascend ModelRunner 里的大量特判。

不过 RFC 也特别指出，Ascend 的 NZ/FRACTAL_NZ 物理格式不一定能仅靠 PyTorch stride 完整表达，因此这是一个跨 runner、backend、operator、transfer 的大工程。

当前开放的 [PR #13505](https://github.com/vllm-project/vllm-ascend/pull/13505) 已经在 compressed-cache 路径上尝试让 Ascend 正确消费 `offset/block_stride`。它证明社区方向一致，但它只覆盖 compressed path，而且会修改 ModelRunner，不能直接作为 PR 13277 的答案。

## 5. 当前工作区方案哪里不够好

当前未提交修改通过以下信息识别 draft：

- `model_type == "k3_dspark"`
- target 的 `num_hidden_layers`
- draft 的层号范围
- `extract_layer_index(layer_name)`

见 [patch_kv_cache_utils.py](<<redacted:local-path:b8dd889167fe>/vllm-ascend-v0.26.0rc-dspark-mla-linear-ci/vllm_ascend/patch/platform/patch_kv_cache_utils.py:30>)。

它做对了三件事：

- 将 draft KV 从 target/Mamba backing 中拆出。
- 给 draft 分配实际大小的连续 tensor。
- 用同一个布局计划重新计算 `num_blocks`、memory 和 concurrency。

但识别方式不对，因为它把一个物理布局兼容性问题表达成了“K3 模型特例”。

按当前 r16 topology 模拟：

- 原布局：5 个 common pool，约 488,448 B/block，5689 blocks。
- 拆分后：5 个 common pool + 5 个 draft pool，draft 约 98,304 B/block，4735 blocks。

也就是用大约 16.8% 的 KV block 容量换取物理隔离。这个代价是真实的，但至少会被 admission/concurrency 正确计入，不再以隐性踩内存的方式换取虚假容量。

## 6. 我建议的 PR 13277 最小正确方案

不改 ModelRunner，重构当前 patch 为通用的 Ascend layout-family planner。

核心规则是：

```text
只有物理寻址 contract 兼容的 KV group，才允许进入同一个 KVCacheTensor.shared_by
```

建议 layout key 至少包含：

```text
- consumer 的 block 寻址模式
- 实际未 padding 的 page bytes
- GQA / MLA / compressed / recurrent 等物理 layout kind
- K/V 或 NoPE/RoPE component geometry
- dtype、KV quant、scale/storage format
```

非 attention 的 layout-neutral group 继续依附于现有主 hybrid family；额外出现、且物理 key 不兼容的 attention family 则独立分配。这样：

- target MLA + Mamba 保持当前已经验证过的布局。
- K3 的 GQA draft 因真实 page geometry 不同，自动进入单独 family。
- 不看模型名。
- 不看 `"mtp"`。
- 不看层号。
- 不使用 `is_eagle_group` 之类 scheduler 语义充当物理布局标记。
- 不改 ModelRunner。
- 不要求当前 kernel 支持 packed block stride。

所有容量计算必须只消费这一份 layout plan：

```text
layout plan
  ├─ KVCacheTensor allocation
  ├─ bytes_per_block
  ├─ num_blocks
  ├─ max_memory_usage
  └─ max_concurrency/admission
```

不能由四处代码分别猜测，否则以后还会出现“allocation 已拆分，但 admission 仍按旧容量计算”的问题。

## 7. 验证边界

重构后至少需要这些验证：

- K3 topology：target/Mamba 与 draft 不再出现在同一个 `shared_by`。
- 不同 layout key 的任意两个 block 地址区间不可能重叠。
- 相同 layout 的普通 attention 仍可共享，不无条件退化成 per-layer allocation。
- DSV4 现有 MTP 隔离行为保持不变。
- Qwen3.5 full-attention + Mamba 路径保持不变，特别是 [ModelRunner 中明确提到的 hybrid MTP 场景](<<redacted:local-path:b8dd889167fe>/vllm-ascend-v0.26.0rc-dspark-mla-linear-ci/vllm_ascend/worker/model_runner_v1.py:4150>)。
- pure attention / UniformType 不改变。
- `num_blocks`、memory override、max concurrency 使用同一个计划。
- 最后再做 prefix-cache-on 的 128K/1K c1/c2：
  - 先只输出 1 token，验证没有 `!`/NaN。
  - 再测完整接受率和平均接受长度。
  - 必须带请求历史重复，而不是只测 fresh service。

因此我建议下一步直接把当前两个 dirty 文件中的 K3-specific 判断替换成通用 layout-family planner，保留“独立连续 backing、`offset=0/block_stride=0`”这一最小策略。等 Ascend RFC 的 stride-aware 路径完整落地后，再把这些 family 重新 packed 到统一 backing。本轮我只做了审查，没有继续修改或启动服务。
