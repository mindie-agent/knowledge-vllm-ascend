[#12283](https://github.com/vllm-project/vllm-ascend/pull/12283) 专门回退了 #12027 的 `model_runner` dispatch 改动；[#12255](https://github.com/vllm-project/vllm-ascend/pull/12255) 随后明确通过 GDN metadata builder 处理 stateful one-token prefill。因此当前 `a4b00791e` 实际上重新引入了已被回退的改动，必须从 #13277 删除。

当前 `non_blocking=False` 也只能算诊断性同步探针。按 torch-npu 的实现，它不只是等待这三张 metadata 表完成：blocking 路径会先同步当前 stream，再执行拷贝。因此它可能等待此前所有 state 写入，直接破坏原有 overlap，掩盖任何前序依赖问题。[torch-npu CopyKernel.cpp](https://gitee.[REDACTED_SECRET].cpp)

所以目前能够证明的只有：

> 在 Mamba state-copy 边界插入一个强同步后，重复 128K 的状态损坏和 NaN 消失。

还不能证明“就是三张 metadata 表尚未拷完”。这个同步点可能同时掩盖四类竞态：

- 上一轮 KDA/Mamba state 写入尚未完成，raw-pointer memcpy 已开始读取。
- `src_ptrs/dst_ptrs/sizes` 的 H2D 尚未完成，Triton kernel 已读取。
- raw-pointer memcpy 尚未完成，下一轮 KDA 已读取目标 state。
- pinned CPU metadata 被下一轮复用或覆盖。

而且 vLLM 0.26 已有 [`synchronize_input_prep`](<<redacted:local-path:b8dd889167fe>/vllm-core-v0.26.0/vllm/v1/worker/gpu_model_runner.py:3810>) 保护复用的 CPU tensor，所以“单纯 CPU buffer 被覆盖”也尚未成立；更值得怀疑的是该 event 是否真正覆盖了 torch-npu task queue 与 Triton launch 的边界。

正向修复应该满足：

- 不修改 `model_runner`。
- 保持 H2D `non_blocking=True`。
- 不做 host/device 全局同步。
- 用明确的 buffer ownership 或 NPU event 建立 producer → H2D → memcpy kernel → consumer 的依赖。
- 分别用“pinned snapshot”“显式 stream event”“关闭 task queue”做 A/B，区分 buffer 生命周期与跨队列排序。
- 用 device-side hash/ring buffer 对比 CPU 期望的三张表，避免 dump 本身引入同步。

因此当前 PR 中：

- `a4b00791e`：错误地重新引入 model-runner 改动，应删除。
- `da3079b7a`、`0cfe7742c`：只能保留在 DFX 分支作为定位证据，不应作为生产修复合入。
- 当前压测结果只能证明这是一个 synchronization-sensitive 的 Mamba state-copy 时序问题；最终修复仍需保持异步并补齐精确依赖。

这轮我没有修改远端 PR。
