- 它更像一个被 4096-token 边界长期掩盖的容量 bug。

证据在 GMM1/GMM2 和 CombineV2 的不一致：

```cpp
// GMM1/GMM2：currentM 乘 2 后，容量累计除以 2，仍保持 token-row 单位
preCurrentmSum += currentM / 2;

// CombineV2：既作为 packed-row offset，又直接用于容量累计
preSrcExpertSum += currentExpertM;
```

乘 2 不是随便的“INT4 packing”：W4A8 把 INT8 activation 拆成两组 INT4 计算行，epilogue 也用 `actualBlockShape.m() / 2` 还原逻辑 token 行。因此 Combine 确实同时需要：

- packed-row accumulator：用于 GMM/epilogue 地址；
- token-row accumulator：用于和 `maxOutputSize` 比较。

当前实现只用一个变量，默认 `maxOutputSize=65536` 时，Combine 的有效容量会从 65536 token rows 提前缩成约 32768 token rows。

为什么 DeepSeek/GLM 可能长期没验出来，关键是这个数字：

- 常见 MoE `top_k=8`；
- FlashComm1 或 shared-expert-DP 下，MoE prepare 可能不再按 TP 切 token；
- `4096 × 8 = 32768`，刚好卡在错误容量边界；
- 所以大量官方配置使用 `max_num_batched_tokens=2048/4096` 时不会明显触发；
- `4480 × 8 = 35840`，正好进入“真实容量未满、packed accumulator 已越过 65536”的窗口，和 issue 报告的 4375/4480 分界是吻合的。

### assistant:final_answer
不能直接说“≤4096 就一定安全”。4096 是 `top_k=8`、`mega_moe_max_tokens=65536` 时推导出的平均临界点，不是严格安全线。

真正条件是每个 rank 都满足：

```text
2 × local_expert_token_rows <= mega_moe_max_tokens
```

因此还受这些因素影响：

- `top_k`：若 `top_k=10`，平均临界点约为 3276；
- expert 路由不均衡：某个 rank 可能在 4096 以下就超过平均值；
- FlashComm1/shared-expert-DP 是否跳过 TP token 切分；
- padding 是否正确被 mask；
- 是否修改过 `mega_moe_max_tokens`。

对 [#14869](https://github.com/vllm-project/vllm-ascend/issues/14869) 的环境，报告者实际验证的是 `max_num_batched_tokens=2048` 可以规避；4096 只是理论边界，不能当作已验证安全值。

所以临时措施优先级是：

1. 精度优先：`VLLM_ASCEND_ENABLE_FUSED_MC2=0`，这是可靠规避。
2. 必须保留 FUSED_MC2：先限制到 2048，并检查每 rank 的 `expert_token_nums`。
3. 4096 只能作为 top-k=8、路由足够均匀时的经验上限，不能写成通用修复方案。
