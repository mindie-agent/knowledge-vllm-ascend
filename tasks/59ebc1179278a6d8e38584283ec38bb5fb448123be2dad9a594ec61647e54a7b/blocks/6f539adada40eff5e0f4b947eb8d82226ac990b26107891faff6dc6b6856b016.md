### 5. 上下文隔离与昂贵资源的生命周期要分开

多个领域会话可以有独立上下文和知识索引，同时复用兼容的检索引擎、远端环境、编译产物和实验资源。

如果每开一个会话就重建索引、加载模型、准备环境，会明显增加等待和资源消耗。反过来，共用实现也不能重新变成全域扫描。

**会话、索引、MCP 连接、远端作业应分别管理生命周期。** 具体进程怎么安排后面决定。

### 6. SDK 路线是否改变用户的账户和使用方式

某端如果只能通过另一套凭据、额外计费入口或不同执行环境接入，这会影响核心体验，也可能迫使后面更换方案。

因此，各端选型时需要同时看清**用户原有账户、授权和工作环境能否沿用**，不能只判断 SDK 接口是否齐全。

## 1. 历史证据是否可信，与当前任务是否适用，需要分开

目前同时规定了“环境不匹配就降低置信度”“只呈现 supersedes 链尾”“pitfall 默认不过期”。这三条组合起来会产生问题。[知识设计](https://github.com/vllm-ascend-workspace/vllm-ascend-workspace/issues/195#issuecomment-5687868447)

举例：某个问题在旧版 CANN 确实存在，新版已经修复。

- 旧经验仍然可信，只是对新版不适用。
- 使用旧版的用户仍需要旧结论，不能一律只返回最新条目。
- 那次踩坑的历史可以永久保留，但“这条路不要走”的建议需要适用范围。

**建议把来源可信度、版本／环境适用性、使用价值分别表达。** 检索根据当前条件选择有效结论，不能因为某个用户环境不同，就修改所有用户共用的置信度。这会影响存储、归并和检索，是需要现在明确的架构语义。

## 2. 经验归并与独立复现之间，还缺少证据约束

评论中的 `merge` 会补充证据、扩大适用范围、增加复现次数。但同一次实验可能被原会话、跨域会话、总结 Hook 各记录一次，也可能被后续 Agent 引用后再次收录。

**如果把这些当成三次复现，就会出现“同一结论被反复转述，最后变成高置信度知识”的循环。**

需要保留原始实验／证据的身份和来源关系，让“重复收录”“引用已有结论”“新增独立验证”能区分。归并本身不能自动扩大适用范围或提高置信度。[对应写入规则](https://github.com/vllm-ascend-workspace/vllm-ascend-workspace/issues/195#issuecomment-5687868447)

顺带说，**dirty 树不宜直接设置信度上限**：保留了基线、完整补丁和运行配置，仍然可以复现；干净 checkout 也不代表远端实际运行的就是这份代码。应判断证据是否充分。

## 3. 领域隔离明确了，但跨用户的知识积累路径还不够明确

现在写清了“本次任务 → 本领域知识库”，也提到了发布，但还没有完整连接：

**本地经验 → 项目／团队可复用经验 → 可公开发布的领域资产 → 其他用户获得更新。**

“属于哪个领域”和“可以给谁使用”是两个独立问题。同为 vLLM 领域，私有模型调试经验与公共框架知识的发布范围也不同。

这里需要确定内容由谁维护、何时发布、如何同步修正，以及反馈作用于哪个范围。可以沿用 Markdown／Git 的内容发布机制；各领域继续独立建库。否则容易做成每个用户各自积累，团队层面的复用路径仍然断着。

## 4. 共享组件的数据模型还带着 vLLM 专用假设

coordinator 已明确要领域无关，但知识条目的必填适用条件仍统一包含 vLLM、vLLM-Ascend 等字段。对纯 Ascend C 或 Motor 经验，这些条件可能根本不存在。[字段定义](https://github.com/vllm-ascend-workspace/vllm-ascend-workspace/issues/195#issuecomment-5687868447)

**建议共享组件只定义通用的来源、证据、适用条件和生命周期；具体需要哪些条件，由领域包／recipe 声明。**

这些条件还应尽量取自**实际执行时的代码与环境记录**。如果等结束 Hook 再探测当前目录，期间代码、容器或环境已经改变，就可能给经验绑定错误版本。这也是受管执行组件与知识组件最重要的连接点之一。
