你在 Cursor 的 vLLM 会话里定位问题，发现需要开发 Triton 算子：

1. Agent 创建一个 **Cursor 原生的 Triton 会话**。
2. 新会话有自己的 Skill、知识库和工具。

### 什么情况下需要自己写 GUI？

假设通过 SDK 可以创建 Triton Agent，也能取得它的实时输出、给它发送消息，但这个 Agent **不会出现在 Cursor 原生会话列表中**。

这时，如果仍想让你直接参与，就得提供另一个入口，例如一个网页：

```text
Triton 任务窗口
─────────────────────
任务历史
Agent 当前输出
工具调用与执行结果
代码变化
─────────────────────
你的输入：[这里需要考虑非连续张量……]
```

我们就需要维护消息展示、流式输出、输入、恢复、交互请求等一系列行为。这已经是在开发一部分聊天客户端。**目前 Cursor 文档明确说明 SDK 云任务可以进入原生界面，本地 SDK 的同等接入路径仍未确认。** [官方文档](https://prod.cursor.com/docs/sdk/python)

**有。最容易导致大返工的是会话接入方式选错；最容易损害效率的是拆域后，协作和人的切换成本不断增加。** 我建议提前守住下面六条边界。

### 1. 用户指导必须命中真正工作的那个会话

如果实际工作发生在后台 SDK 会话，界面只是展示其日志，后面再补输入框，也未必能接续同一上下文。

**领域配置、过程展示、直接纠偏、通信和恢复，需要在所选接入路径上同时成立。** GUI 仍然 case by case；这一条约束的是实际交互效果。选错运行入口，后续可能需要整体更换。

### 2. 拆分领域，需要同时控制会话协作成本

继续拆领域可以，但每次跨域都重新启动、重复读代码、重讲背景，可能抵消减少 Skill 描述带来的收益。

建议明确：

- 按实际任务创建会话，同一任务中的相关领域会话可以继续复用。
- 领域数量不直接决定同时运行的 Agent 数量。
- 用户能持续指导各会话，会话之间的转述、关联和成果交接由系统完成。

**人需要的是随时介入的能力，而不是额外承担多 Agent 的协调工作。**

### 3. 用户纠偏要能改变相关工作的后续行动

例如你在 vLLM 会话里修改了输入条件，Triton 会话仍按旧条件优化，最后交回一个已经不适用的结果。

需要区分：

- 本领域的细节纠正：留在当前会话。
- 影响共同目标、接口或实验条件的变化：送达相关会话，并在后续行动中生效。

**仅有“能发消息”还不够。** 结果是否仍适用、由谁集成，也需要有明确归属。这直接决定持续 review 是否有效。

### 4. 领域划分必须方便调整，不能写死在六端实现里

今天 profiling 属于 vLLM 域，明天可能独立出来。如果一次拆域需要修改六套业务逻辑、迁移大量失效引用，后续调整就会很痛苦。
