### assistant:final_answer
方向对，但落点不对：目标确实是返回 `finish_reason="unexpected_state"`，但不能在 parser 里把 `APIError` 改掉。

实际链路是：

```text
KimiK3 parser
  └─ 抛 KimiK3XTMLParseError
       └─ vLLM serving 当成通用异常，生成 SSE error
            └─ OpenAI SDK 转成 APIError
```

Parser 的返回值只有 reasoning、content、tool calls，没有 `finish_reason`，所以正确方案应是：

- Parser 继续严格拒绝空 tool name、非法 arguments。
- Serving 捕获“模型输出格式错误”。
- 流式返回一个正常终止 chunk：`finish_reason="unexpected_state"`，然后 `[DONE]`。
- 非流式返回 HTTP 200，choice 的 `finish_reason="unexpected_state"`。
- 两种路径均不得返回可执行 tool call。

另外还有几个实现层面需要一起处理：

1. 当前异常分类太粗

同一个 `KimiK3XTMLParseError` 同时表示：

- 模型生成格式错误；
- 请求配置错误，例如非法 `tool_choice`；
- parser 内部流式状态不一致；
- 工具调用被截断。

不能全部转换成 `unexpected_state`。建议至少区分：

- 模型协议错误 → `unexpected_state`
- 请求参数错误 → HTTP 400
- parser 内部 invariant 错误 → HTTP 500
- `max_tokens` 截断 → 保留 `length`，不返回工具调用

2. 流式异常可能在最终 chunk 前发生

[parse_delta](<<redacted:local-path:b8dd889167fe>/vllm-ascend-kimi-k3/vllm_ascend/patch/platform/patch_kimi_k3_parsers.py:506>)会在看到完整但非法的 tools block 时立即抛错。Serving 需要记录该 choice 已经进入 invalid 状态，并确保：

- `unexpected_state` 只发送一次；
- 后续 token 不再解析或输出；
- `n > 1` 时只终止出错的 choice，不影响其他 choice；
- 正确清理或取消剩余生成。

3. 当前工具调用缓冲策略是正确的

[这里](<<redacted:local-path:b8dd889167fe>/vllm-ascend-kimi-k3/vllm_ascend/patch/platform/patch_kimi_k3_parsers.py:529>)直到最终 chunk 才释放 tool calls，避免先输出一个工具调用、之后才发现协议非法。这个行为应保留，不要为了避免异常而做宽松解析。

4. 缺少 serving 级回归测试

现有测试只验证 parser 会[明确抛异常](<<redacted:local-path:b8dd889167fe>/vllm-ascend-kimi-k3/tests/ut/patch/platform/test_patch_kimi_k3_parsers.py:543>)。还需要覆盖：

- 流式空 tool name → `unexpected_state`，无 SSE error；
- 流式非法 typed arguments；
- 非流式一致性；
- 不泄漏 tool calls；
- `length` 与真正协议错误的区分；
- 多 choice 隔离。

所以结论是：**严格 parser 本身没有发现需要放宽的地方；主要缺口是 parser 错误分类和 serving 层的终止语义。** 单纯在 parser 内吞掉异常是不够的，最后只会被误报成正常 `stop`。

是的，按 vLLM 社区惯例看，我们现在确实做重了。社区通常不会让 parser 决定 `finish_reason`，更不会为某个模型把解析异常扩展成一套 serving 状态机。

vLLM 一般有两种处理方式：

1. 传统做法：fail-soft

Parser 捕获模型输出解析异常，记录日志，然后返回：

- `tools_called=False`
- `tool_calls=[]`
- 流式返回 `None`
- 保持引擎原来的 `stop` 或 `length`

Hermes parser 现在仍是这种方式：[非流式失败回退为普通内容](https://github.com/vllm-project/vllm/blob/main/vllm/tool_parsers/hermes_tool_parser.py)，流式解析失败也只记录日志并返回 `None`。你们对齐版本里的 [Kimi K2 parser](<redacted:local-path:5401a5dfe9db>:77) 也是这个风格。

原因是 vLLM 的 [Parser 接口](https://github.com/vllm-project/vllm/blob/main/vllm/parser/abstract_parser.py)只返回 reasoning、content、tool calls，没有 `finish_reason` 通道；异常一旦逃出，serving 就会按通用服务错误生成 SSE error，而不是模型状态。[当前 serving 实现也是如此](https://github.com/vllm-project/vllm/blob/main/vllm/entrypoints/openai/chat_completion/serving.py)。

2. 新方向：从生成阶段避免非法格式

vLLM 当前更倾向于：

- 通用声明式 Parser；
- structural tags；
- XGrammar/guided decoding；
- parser 只提取结果，不负责判罚。

当前主线 Kimi K2 tool parser 已缩成一个很薄的适配器，并声明 `structural_tag_model="kimi"`：[Kimi K2 tool parser](https://github.com/vllm-project/vllm/blob/main/vllm/tool_parsers/kimi_k2_tool_parser.py)。vLLM 文档也说明，required/named tool choice 会使用 schema-constrained decoding，auto 模式可通过 `strict: true` 启用约束。[Tool Calling 文档](https://docs.vllm.ai/en/latest/features/tool_calling/)。Moonshot 的 Vendor Verifier 同样建议供应商增加 guided encoding。[K2 Vendor Verifier](https://github.[REDACTED_SECRET])。

因此我建议 K3 先采用社区风格的最小修法：

- 保留严格 XTML 校验，绝不输出非法 tool call。
- 顶层 parser 捕获“模型输出格式错误”，标记本次解析 invalid。
- 流式后续返回 `None`，非流式返回空 tool calls；只保留已经确认安全的 content/reasoning，不直接回传原始 XTML。
- 保持原始 `stop`/`length`，不要让异常逃到 serving。
- 请求参数错误继续走 400，parser 内部 invariant 仍然报服务错误。

这样 KVV 会把该样本正常计错，也不会因为 `APIError` 自动重试；无需引入 `unexpected_state` 和复杂的 serving patch。

只有在“必须逐字段兼容 Moonshot 官方 API”被明确列为验收条件时，才值得在 parser 外面加一个很薄的 Kimi compatibility adapter，把 invalid 标记转换成 `unexpected_state`。长期再单独做 K3 structural tags/guided decoding，这更符合社区演进方向。
