每次执行：
1. 获取上述四个远程分支的最新 SHA，并记录 ci_new 和 new 的远端旧 SHA用于 force-with-lease。
2. 首次运行若没有状态：仅当当前 ci 是 ci_new 的祖先时，将当前 ci SHA 初始化为上次同步 SHA；否则停止并报告，不能猜测旧 CI 基线。
3. 如果当前 ci SHA 与上次同步 SHA 不同：验证上次 CI SHA 是 ci_new 的祖先，然后对 ci_new 执行 git rebase --rebase-merges --onto <当前ci> <上次ci>；发生冲突立即 abort 并失败，不自动解决；成功后使用精确的 --force-with-lease 更新远程 ci_new。更新成功后原子写入最新 CI SHA。
4. 验证 releases/v0.23.0 是当前 ci 的祖先、当前 ci 是同步后 ci_new 的祖先。
5. 重新生成 new：从 releases/v0.23.0 建临时分支，将 ci_new 的最终树 squash 到工作区，再反向应用“releases/v0.23.0 到 releases/v0.23.0_ci”的完整二进制 diff，从而只减去私仓 CI 修改。若反向应用冲突则失败，不推送错误结果。开发 diff 非空时使用 Conventional Commit 消息并带 Signed-off-by 创建一个汇总提交；为空时让目标直接指向公开基线。
6. 校验 new 相对 releases/v0.23.0 的提交数只能是 0（无开发修改）或 1（有开发修改）；有开发修改时必须为 1。再做树级语义校验：从候选 new 树出发，将 releases/v0.23.0 到 releases/v0.23.0_ci 的 CI 补丁正向应用到临时索引，git write-tree 的结果必须与同步后 ci_new 的 tree SHA 完全相同。不要用原始 git diff 文本或 blob index 行做严格相等校验，因为 CI 与开发修改同一文件的不同区域时 blob SHA 会合理不同。
7. 只有远程 new 的目标 SHA 或树/父关系需要变化时，才使用精确的 --force-with-lease 推送 releases/v0.23.0_new。
8. 任意 lease 失败说明期间出现新推送：不要覆盖，重新 fetch 并在本次最多重试一次；仍失败则报告。
9. 无变化时简短结束。绝不修改或推送 releases/v0.23.0 与 releases/v0.23.0_ci。
