实际规模是：

- 两套旧算子删除了约 6658 行。
- V2 真正修改了 4 个文件，净变化约 `+160/-96`。
- 所以 PR 看起来改动很大，主体其实是删除旧实现，不是重写 V2。

V2 的修改分成四类：

1. A2/A3 的 NZ 权重兼容

旧 V2 把 NZ storage shape 写死成 W4A8 格式，但实际需要同时支持：

- W8A8：INT8，N block 为 32。
- W4A8：INT4 打包在 INT32 中，N block 为 64。
- A2 可能暴露一维扁平 storage shape。
- A3 通常暴露四维/五维 blocked shape。

因此增加了按 dtype 计算 NZ shape，并允许 A2 的等价扁平表示；否则统一后 A2 的真实 W8A8/W4A8 权重会在绑定阶段失败。[aclnn_grouped_matmul_swiglu_quant_v2.cpp](<redacted:local-path:158cc90e2ab0>:25)

2. 单 Tensor/TensorList 的 shape 统一

旧 TensorList 算子删除后，V2 必须同时处理 `[E, N]` 和每专家 `[N]` 的 scale，所以获取 N 的逻辑从固定维度改成最后一维。[grouped_matmul_swiglu_quant_v2.cpp](<redacted:local-path:e52573f2ec44>:40)

3. `group_list` 契约统一

Fused MoE 实际传入的是每个专家的 token 数量，即 `group_list_type=1`；原 V2 更依赖累计值，即 `group_list_type=0`。如果不转换，空专家和 ACLGraph replay 会解释错分组边界。

因此在进入 ACLNN 前把 count 转成 cumsum，并固定底层 attribute 为 0。[grouped_matmul_swiglu_quant_v2_torch_adpt.h](<redacted:local-path:caac27905fc7>:58)

4. A3 图模式的数值一致性

原 V2 的 activation scale 广播、SwiGLU 计算和 INT8 量化舍入顺序与被删除的兼容算子不同。在真实大 token prefill 上会产生 1 个 INT8 单位的误差，最终出现 graph/eager token 不一致。

所以 kernel 改成与原兼容路径一致的逐行 scale、`SwiGLU` 指令、标量倒数和 `CAST_RINT` 舍入。[grouped_matmul_swiglu_quant_spilit_fusion.h](<redacted:local-path:29f12f8bd81d>:406)

需要明确的是，下面这部分现在确实没有必要：

- adapter 中根据 `quant_dtype` 切到 A5 ND/MX 接口的分支；
- MX 输出 shape/dtype 扩展；
- A5 构建列表中加入自定义 V2。

这些是当时按“A2/A3/A5 全部统一到自定义 V2”做的扩展。但后来 A5 已恢复走 `torch_npu.npu_grouped_matmul_swiglu_quant_v2`，[device_op.py](<redacted:local-path:d99e959eaa8e>:1220)，所以自定义 V2 中的 A5 分支已经不是当前生产调用链所必需的。

因此我的判断是：A2/A3 的 NZ shape、group-list 和量化一致性修改需要保留；A5/ND/MX 那部分属于扩展过头，应该收掉。最终 A2/A3 全矩阵通过说明保留部分是有效的，但不代表整个 V2 diff 都是最小改动。

对，你记得是对的。我前面说“V2 更依赖累计值”不准确：V2 内核原生支持两种模式。

- tiling 明确接受 `groupListType == 0 || 1`：[grouped_matmul_swiglu_quant_v2_base_tiling.cpp](<redacted:local-path:5f7175797d5f>:176)
- kernel 也会根据类型选择“累计值做差”或“直接使用 count”：[grouped_matmul_swiglu_quant_spilit_fusion.h](<redacted:local-path:29f12f8bd81d>:69)

现在 adapter 中的 `count -> cumsum` 是多余的，而且会掩盖真实契约：

- Python `BaseDeviceAdaptor` 转换一次并强制传 `type=0`：[device_op.py](<redacted:local-path:d99e959eaa8e>:246)
- C++ torch adapter 又做了一次相同转换：[grouped_matmul_swiglu_quant_v2_torch_adpt.h](<redacted:local-path:caac27905fc7>:58)
- 部分 `moe_mlp` 调用点本身也已经转换，存在三层重复语义处理。

如果一定要统一成 cumsum，那么你的建议更合理：应该在具体调用点、进入算子前转换，而不是在底层 adapter 中偷偷改变输入语义。

但我认为更合适的最终方案是：

1. Token dispatcher 保持它自然产生的 count 数据和 `group_list_type=1`。
2. `moe_mlp` 将 `group_list` 与 `group_list_type` 原样传递。
3. Python/C++ adapter 只做参数和布局适配，不做 cumsum，也不强制改成 0。
4. V2 内核按原生 `group_list_type` 处理。
5. 只有遇到明确不支持 type 1 的其他算子，才在那个调用点转换成 cumsum。

这样可以少一次 NPU `cumsum`、少一个中间 tensor，也不会出现 count → cumsum → count 的往返。`group_list_type=1` 本身是固定算子属性，ACLGraph replay 时不会随请求改变，因此之前“为了稳定 graph attribute 而统一成 0”的理由也不充分。

还有一个测试盲点：当前虽然有 `group_list_type=1` 用例，但它在进入 ACLNN 前已被 adapter 转成 type 0，所以实际上没有覆盖 V2 kernel 的原生 type 1 分支。后续应在去掉两层转换后，重新跑 count/cumsum、空专家、single/multi tensor 和 graph replay，才算真正验证 type 1。
