1. **远端进程控制统一归 remote-dev。** 启动、日志、观察、停止只维护一套实现；coordinator 负责环境、资源及执行归属；skill 负责模型参数、健康检查和实验指标。当前两个包各有进程管理路径，职责重叠。
2. **任务工作区与执行资源分开管理。** 代码、editable 环境和构建目录在任务期间保持稳定；NPU、业务端口随每次执行释放。当前候选会在执行结束后归还整个 runtime，可能让其他任务复用仍需编辑的目录。
3. **coordinator 必须独立常驻。** 客户端只是入口，排队、状态核对、回收由它持续推进。当前已有推进方法，但生产入口缺少后台驱动，仍依赖工具调用。

按这个架构看，主要 gap 是：

| 部分 | 还需要完成 |
|---|---|
| remote-dev | 去掉 VAWS 专属接入假设；统一进程机制；补齐跨平台与具名客户端验证 |
| coordinator | 常驻运行、按配方准备环境、联合选择环境与设备、多机整体分配、稳定任务隔离 |
| knowledge | 在运行事实之外支持官方资料、原理和指南，区分来源与验证程度 |
| scaffold / skills | 接好业务流程，把请求标识、解释器选择、排队恢复等细节藏在入口内部 |
| vaws-top | 保持原职责，本轮没有发现需要改变的边界 |
