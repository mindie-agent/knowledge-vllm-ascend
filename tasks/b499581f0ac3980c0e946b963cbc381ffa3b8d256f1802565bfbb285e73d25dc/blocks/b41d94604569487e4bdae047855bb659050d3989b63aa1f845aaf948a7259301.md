结论：tokenizer/chat-template 侧不应阻断这次 DSpark PR 刷新。

- SpecForge 风格 GSM8K 5-shot raw completions 已经做到 32/32 正确，接收率 `2671/4697 = 56.866%`，与旧服务累计 `56.96%` 几乎一致；prefix cold/warm/reset 也一致。这说明 DSpark 精度正常，中文长 chat 的 `10.64%` 更像语言、长自由生成及 XTML thinking 分支造成的条件分布变化。
- target/draft 不存在 tokenizer 错配：draft 权重目录不带 tokenizer，vLLM 会继承 target tokenizer 和 `tokenizer_mode`；两边 `vocab_size=163840`，BOS/EOS/PAD 均一致。对应逻辑见 [speculative.py](<redacted:local-path:581e9d1a905d>:837)。
- 当前 `--tokenizer-mode kimi_k3`、无自定义 Jinja 是正确路径。K3 直接调用原生 Python tokenizer 生成 XTML，见 [patch_kimi_k3_renderer.py](<redacted:local-path:88c394f0f77c>:344)。
- parser 只拆解已经生成的 token，不参与 draft verification，不能解释接收率下降；renderer/template 会改变输入 token 分布，但 target 与 draft 收到的是同一串 IDs。

SGLang 对比方向是对的，但其 issue 只验证了“能跑”：使用 target tokenizer、raw 英文 `"The capital of france is "`、`temperature=0`、`max_new_tokens=100`，没有公布接收率。因此不能直接把它当作中文 chat 的数值基线。[SGLang #32519](https://github.com/sgl-project/sglang/issues/32519)
