更合适的参考是 DeepSeek V4，而不是 GLM 的纯 Jinja 方式。vLLM 的 `DeepseekV4Renderer` 直接调用 Python tokenizer 的 `apply_chat_template()`，完全绕过 HF Jinja 解析。[DeepseekV4Renderer](https://github.com/vllm-project/vllm/blob/v0.23.0/vllm/renderers/deepseek_v4.py#L13-L81)

   - 在服务初始化阶段自动将其设为默认模板；
   - 确保 render 路径和 parser 的 `chat_template_kwargs` 都能看到同一个 sentinel。

   这样不需要新增 tokenizer，也能直接去掉 `--chat-template`。

2. 长期 upstream 方案：

   - 实现 `KimiK3Renderer`，参考 `DeepseekV4Renderer`；
   - 直接复用模型仓现有 `TikTokenTokenizer.apply_chat_template()`；

   - 不要求用户额外指定 `--tokenizer-mode kimi_k3`。

最终启动参数应只需要：

```bash

--enable-auto-tool-choice \
--reasoning-parser kimi_k3 \
--tool-call-parser kimi_k3
```

单纯给 `tokenizer_config.json` 增加 `chat_template` 只能解决“找不到模板”，还不能完整解决 `thinking_effort`、`tool_choice=required/named/none` 和 `response_format` 的参数映射。因此，当前 PR 最合理的是先做 K3 默认模板自动注入；不要在 vLLM-Ascend 复制整套 tokenizer。
