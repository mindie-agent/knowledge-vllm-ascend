### P0-1：增量解码给 K3 控制 token 插空格，直接破坏所有精确 marker

[源码证明]

- vLLM `ChatCompletionRequest` 默认：
  - `skip_special_tokens=True`
  - `spaces_between_special_tokens=True`

- 当前 K3 只在 [KimiK3ReasoningParser.adjust_request](<redacted:local-path:0c94b789f1de>:278) 和 [KimiK3ToolParser.adjust_request](<redacted:local-path:0c94b789f1de>:546) 关闭 `skip_special_tokens`，未关闭插空格。
- 因而官方 `<|close|>response<|sep|>` 被解码为 `<|close|> response <|sep|>`，所有字符串精确匹配失败。

[现场证明]

- MMMU 五条都未匹配 `THINK_END`，完整回答进入 `reasoning`，`content` 为空。
- BFCL case 5 已输出完整、正确工具协议，但带空格，`tool_calls=null`；这是确定性 parser failure。
- BFCL 前四条主要是模型选择直接作答，不能据此断言“丢失了真实调用”；但 wrapper cleanup 同样失败。
- 普通无 tools 请求每条 ERROR，与 tool_choice mutation 是另一条后续问题，不是 content 全进 reasoning 的直接原因。

修复：

- 在所有 K3 parser adjustment 的公共路径、且在 `to_sampling_params()` 前，幂等设置：

  ```python
  request.skip_special_tokens = False
  request.spaces_between_special_tokens = False
  ```

- 最好由上述 K3 cleanup capability 保证即使 `tool_choice=="none"` 也执行。

验收：

- 使用真实 K3 tokenizer 和 vLLM `detokenize_incrementally`，逐 token 断言所有 marker 无空格还原。
- MMMU replay：五条无 serving ERROR，answer 位于 content，reasoning 只含思考。
- BFCL case 5：恰好一个 `solve_quadratic_equation` tool call，参数为 `2,6,5`，原始 XTML 不出现在 content。

### P0-2：当前 renderer 的 tokenize=False 路径破坏官方 trust boundary

[源码证明]

- vLLM render 默认对 K3 slow HF tokenizer 传 `tokenize=False`：远端 `serve/render/serving.py:538-556`。
- 当前 renderer 使用 `content_format="string"` 并原样调用 tokenizer：
  - [sync 139-151](<redacted:local-path:8b151ac45eb4>:139)
  - [async 165-177](<redacted:local-path:8b151ac45eb4>:165)
- 官方 `tokenization_kimi.py:357-408` 在 `tokenize=False` 时把 segment 直接拼成字符串，丢失 `allow_special`。
- BaseRenderer 随后整串 `tokenizer.encode(...)`；K3 encode 默认允许 special。
- 官方协议明确要求结构 token `allow_special=True`，用户、工具文本及属性值 `False`：`encoding_k3.py:1-7,24-66,102-120`。

[只读 tokenizer 实验]

用户文本中的字面 `<|close|>message<|sep|>`：

- 官方 segmented tokenize=True：仅协议结构 marker 成为 special IDs。
- 当前拼接后重编码：用户字面 marker 也成为 special IDs，token IDs 与官方结果不同。

同时，若只简单强制 `tokenize=True`，当前 string multimodal placeholder 会被作为普通文本编码，media control token 数量变成 0；因此不能只改一个布尔值。

影响：

- 普通文本恰好不含特殊字面串时通常看不出来。
- 对 marker injection、历史 tool 内容及 multimodal prompt 是确定性协议错误，属于输入边界和安全问题。

正式修复：

- `content_format="openai"`；
- 结构化 image parts；
- 可信 `image_prompts`；
- 强制 `tokenize=True`；
- 返回 token IDs，禁止 BaseRenderer 整串重编码。

## P1

### P1-1：none→auto 当前实现造成无 tools 请求 ERROR；none→None 仍是 hidden fallback

当前 [adjust_request:288-295](<redacted:local-path:0c94b789f1de>:288) 把默认 `"none"` 改成 `"auto"`。

后果链：

- parser 被调用；
- 无 `request.tools`；
- serving auto 分支要求 `request.tools`，不成立；
- 落到远端 `serving.py:1235-1242` 的 “cannot determine” ERROR；
- 随后降级成 HTTP 200 普通 completion。

这不是预期 no-tools 行为。

候选 `none→None` 在当前组合配置下确实能工作：

- `Parser._extract_tool_calls` 把 None 当 auto：`abstract_parser.py:563-565`；
- serving 的 `not request.tool_choice` 分支把 None 当普通 completion：`serving.py:1172-1175`；
- 私有 original-none 标志令 allowed tools 为空。

但 None 同时是 vLLM 的 auto sentinel；带 tools 时还会激活 auto streaming/control flow。因此这是依赖两个相反 truthiness 语义的巧合，不应合入。用前述 parser capability 修复，保持 tool_choice 不变。

### P1-2：required/named 可静默返回伪成功

- K3 声明 `supports_required_and_named=False`，因此 required/named 走自定义 parser fallback。
- parser 对未知工具、非法参数和 JSON 异常直接 `continue`：
  - [454-496](<redacted:local-path:0c94b789f1de>:454)
- serving 在 named/required 分支即使零调用也构造：
  - `content=""`
  - `tool_calls=[]`
  - required 还可能强制 `finish_reason="tool_calls"`
  - 远端 `serving.py:1101-1170,1246-1250`
- 全局 [patch_tool_choice_none_content.py:34](<redacted:local-path:3d890e8cf52c>:34) 又会从序列化结果删除空 tool_calls，进一步掩盖异常。
- streaming 只有真实 tool delta 才给 `finish_reason=tool_calls`，与 non-stream 不一致。

修复：required/named 在结束时严格检查至少一个合法调用、named 名称匹配、参数是合法 JSON；失败返回显式 parse error。不要硬编码丢弃有效 response content。

### P1-3：parser 过度宽松且会吞协议错误

责任范围：

- [_parse_json_arguments 377-399](<redacted:local-path:0c94b789f1de>:377) 把非法 JSON 原样放进 OpenAI `function.arguments`；现有 UT 甚至把它固化为期望行为。
- `_parse_attrs` regex 未全串锚定，额外垃圾、重复属性不报错。
- typed arguments 会忽略 stray body、重复 key、mixed JSON/typed blocks。
- 缺失 `TOOLS_END` 的完整 call 仍可能被接受。
- [_response_content 499-528](<redacted:local-path:0c94b789f1de>:499) 使用任意位置 `rsplit/find`，不是严格 envelope。
- 多 tools block、错误顺序和 index 未验证。

修复：完整消费语法；call 只能是全闭合且唯一表示；参数必须生成有效 JSON object；拒绝 duplicate key/index、混合编码和尾随垃圾。

### P1-4：`response_format` 被静默降级

[adjust_request:297-308](<redacted:local-path:0c94b789f1de>:297) 保存原值后把 `request.response_format=None`，保存值在其他地方没有消费。

影响：

- `json_object/json_schema` 只有 prompt 指令，没有 vLLM grammar 保证。
- 官方 encoder 不支持 `structural_tag`，但当前同样会传入后再静默清除。

短期：K3 明确 4xx 拒绝尚未支持的 response_format。长期：实现知道 think/response XTML phase 的 grammar，切换到 response body 后才约束 JSON。

### P1-5：streaming API 不完全等价

- 通用 stream 分支 `serving.py:719-728` 在 `parser.parse_delta()` 后没有应用 `include_reasoning=False`；只有 Harmony 路径处理，因此 K3 stream 会泄露 reasoning。
- K3 `_response_content(streaming=True)` 会保留可能是 marker 前缀的末尾，但 ToolParser API 没有 finished 参数用于最终 flush；生成恰好终止于 `<|cl...` 时尾部丢失。
- reasoning→response 与 response→tools 同 delta、所有 marker token 边界尚未用真实 tokenizer 测试。

修复：serving 在统一位置清除 reasoning；把 finished 传入共享 XTML state machine，EOF 时按明确 malformed policy flush/error。

## 最小测试与验收门槛

必须用真实 K3 tokenizer，至少覆盖：

1. Renderer：

   - 用户/system/tool/历史 assistant 文本分别包含所有 K3/media special 字面串；
   - sync/async token IDs 与官方 `apply_chat_template(tokenize=True, image_prompts=...)` 完全相同；
   - 0/1/2 图像、图文交错；
   - 用户字面 marker 不产生 special ID，结构/media marker 必须产生 special ID。

2. Parser lifecycle：

   - `stream ∈ {false,true}`、`n ∈ {1,2}`；
   - thinking none/high、`include_reasoning ∈ {false,true}`；
   - tools omitted、tools+none、auto、required、named；
   - 0/1/2 calls、typed args/JSON block；
   - 每个 marker 在每个 token/chunk 边界切分。

3. Malformed：

   - unknown tool、错 named tool、缺闭合、非法/重复 attrs、重复 key/index；
   - bad number/bool/null/object/array、NaN/Inf；
   - invalid JSON、mixed JSON+typed、stray body、多 tools block；
   - auto 与 required/named 的错误语义分别断言。

4. API 断言：

   - 没有 “cannot determine” ERROR；
   - API content/reasoning/tool_calls 中没有原始 `<|...|>`；
   - stream/non-stream 重建结果一致；
   - tool IDs 跨 chunk 稳定、不同 choice 状态隔离；
   - required/named 零调用不允许 HTTP 200 空成功；
   - `include_reasoning=false` 两种模式都不返回 reasoning。

5. 修复后只在隔离服务做最小现场 replay：

   - MMMU 原五条：无 ERROR、无 unparsed、content 非空。
   - BFCL case 5：必须抽出正确 tool call。
   - BFCL 前四条仍可能因模型决策不调用工具；这部分不能与 parser correctness 混为一谈。

影响边界：普通 chat 的 ERROR 不会污染随后 BFCL 的 parser 状态——parser 每请求、stream 每 choice 独立实例化；但同一个 `spaces_between_special_tokens=True` 缺陷同时破坏普通 chat reasoning split 和 BFCL 真实 tool extraction。

核心阻断项：

1. `spaces_between_special_tokens=True` 会把 K3 marker 插空格，直接导致 reasoning/content 分栏失败和 BFCL 工具协议无法抽取。必须同时设置：

   ```python
   request.skip_special_tokens = False
   request.spaces_between_special_tokens = False
   ```

2. 当前 [Kimi K3 renderer](<redacted:local-path:8b151ac45eb4>:107) 实际走 `tokenize=False`，官方 `EncodeSegment.allow_special` 在拼接后二次编码时丢失。用户文本里的 XTML 字面串甚至可能被编码成真实控制 token。

   正式修复不能只强制 `tokenize=True`，否则会破坏现有多模态占位符。需要整体改为：

   - `content_format="openai"`
   - 保留结构化 image parts
   - 按图像顺序传入可信 `image_prompts`
   - 强制官方 tokenizer `tokenize=True`
   - sync/async 返回相同 token IDs
   - 不允许请求参数覆盖回 `tokenize=False`

3. [当前 none→auto 逻辑](<redacted:local-path:0c94b789f1de>:278) 必须删除。它会造成 prompt 按 none 渲染、serving 按 auto 处理，最终无 tools 请求必然进入：

   `cannot determine if tools should be extracted`

   `none→None` 虽能临时消除 ERROR，但 vLLM 0.23 又把 `None` 当作 auto sentinel，仍属于隐藏 fallback，不是正式方案。

正式控制流应为：

- `request.tool_choice` 全程保持原值。
- 明确分离“清理 K3 XTML envelope”和“允许输出 tool calls”。
- `tool_choice=none` 时仍允许 K3 parser 清理 response wrapper，但框架强制 `tools_called=False`。
- v0.23 可实现版本限定的 K3 unified Parser/DelegatingParser selection；不要改写整条 serving/SSE generator。
- reasoning、content、tools 使用同一个严格 XTML 状态机，stream/non-stream 共享语法和结束 flush。

历史经验也支持这个方向：

- DeepSeek V4、GLM5 都保留原始 `tool_choice`，不会做 none→auto。
- 两者最终都从临时 serving monkey-patch 收敛到统一 ParserEngine：[DeepSeek V4 PR](https://github.com/vllm-project/vllm/pull/45877)、[GLM PR](https://github.com/vllm-project/vllm/pull/45915)。
- GLM 的 `supports_required_and_named=False` 适合 K3 原生 XTML；但它们只设置 `skip_special_tokens=False`，不能解决 K3 的复合 marker 插空格问题。

还需一并修复：

- required/named 无合法调用时，当前可能返回 HTTP 200、空 content、空 tool_calls，required 甚至伪造 `finish_reason=tool_calls`。
- unknown tool、非法参数、非法 JSON 当前会被 `continue` 静默吞掉。
- `response_format` 当前被静默置空，等于偷偷降级；正式支持前应明确拒绝。
- streaming 的 `include_reasoning=false`、marker 尾部 flush、畸形 call 状态均不完整。
- `chat_template_kwargs` 不应覆盖 tools/tool_choice/thinking/response_format 等保留字段。

验收至少需要：

- 使用真实 K3 tokenizer 和真实 incremental detokenizer，不能继续只用 FakeTokenizer。
- 覆盖 `tools omitted/none/auto/required/named × thinking on/off × stream/nonstream × n=1/2`。
- 覆盖多工具、零参数、全部参数类型、任意 marker chunk 边界、unknown/malformed、0/1/2 图像及 marker injection。
- stream 重建必须与 non-stream 一致；无 XTML 泄漏、无 `cannot determine` ERROR。
- GPQA 两条 smoke：content/output 非空、missing=0。
- MMMU 五条：答案进入 content，reasoning 只包含思考。
- BFCL case 5：必须抽出 `solve_quadratic_equation(a=2,b=6,c=5)`；前四条属于模型选择直接回答，不能误判为 parser 确定性失败。
