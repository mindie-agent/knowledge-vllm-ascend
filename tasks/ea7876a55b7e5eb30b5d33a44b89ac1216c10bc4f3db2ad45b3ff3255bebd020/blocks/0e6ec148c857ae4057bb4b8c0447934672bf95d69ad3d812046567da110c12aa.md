## 下一步应该怎么做

   - reset prefix cache 仅作为观察边界，不把它当原因。

2. 给每个 step 记录：

## 系统性解决方向

### 1. 统一 KV 物理规划

当前实现仍通过 Kimi K3、DSpark 和层号判断是否隔离，见 [patch_kv_cache_utils.py](<<redacted:local-path:b8dd889167fe>/vllm-ascend-v0.26.0rc-dspark-mla-linear-ci/vllm_ascend/patch/platform/patch_kv_cache_utils.py:30>)。这就是临时补丁形态。

应引入统一的 `KVPhysicalPlan`：

- 每个 cache group 声明 backend、dtype/quant、component geometry、page bytes、block stride、packing format。
- 只有 layout signature 完全兼容的 group 才能共享 pool。
- allocation、reshape/view、capacity、zeroer、copy、admission 全部消费同一份 immutable plan。
- 启动时枚举边界 block，断言任意不相关逻辑块的地址区间不重叠。
- 最终删除 `_uses_k3_dspark` 和基于 layer range 的特殊判断。

### 2. 显式状态所有权

每个物理 block/state row 应有 owner 和 generation：

- scheduler 分配 lease。
- producer event 完成后才能 publish。
- reader 必须校验 generation。
- finished/discarded speculative step 必须使所有持久 row 失效。
- dummy/padding row 不能继续持有上一请求的合法 index。

这能从机制上阻止“旧 step 在新请求已经复用 block 后继续写”。

### 3. 用 GPU event DAG 管理异步关系

不要再用 CPU `event.synchronize()` 修正确性。当前热路径存在阻塞点 [model_runner_v1.py](<<redacted:local-path:b8dd889167fe>/vllm-ascend-v0.26.0rc-dspark-mla-linear-ci/vllm_ascend/worker/model_runner_v1.py:1048>)，state update 又被放到 side stream [model_runner_v1.py](<<redacted:local-path:b8dd889167fe>/vllm-ascend-v0.26.0rc-dspark-mla-linear-ci/vllm_ascend/worker/model_runner_v1.py:2309>)。

正确结构应是：

- H2D staging 使用双缓冲或 ring buffer。
- producer stream `record_event`。
- consumer/下一 step `wait_event`。
- 只等待将被复用的 slot 或 state，不阻塞 CPU，也不全局同步。
- accuracy 修复不得新增 hot-path CPU synchronize，并设置 TTFT/TPOT 回归门槛。

不过 r22 已经说明：目前还不能直接把“side-stream 缺 fence”当作根因。先抓到确切 writer，再在对应 ownership 边界加事件。

### 4. 建立真正的合入门槛

PR 不应只凭一次 c2 回放合入。至少要求：

- cold/fresh 与 history replay 都通过。
- c1、c2 固定 token SHA。
- 首 token 和完整 1K。
- target logits、所有关键 KV/state 均 finite。
- 多轮短 decode → 长 writer → victim。
- no stale generation / no physical overlap。
- acceptance、TTFT、TPOT 同时检查。
- 不新增 CPU 同步。

建议把工作拆成两个基础 PR：通用 KV layout planner，以及定位后得到的 state ownership/async lifecycle 修复；然后让 [PR #13277](https://github.com/vllm-project/vllm-ascend/pull/13277) rebase 到这两个基础能力上。当前 `419c315` 可以保留为“已修复一处真实冲突但精度仍未完全收口”，不宜继续宣称问题已解决或直接合入。
