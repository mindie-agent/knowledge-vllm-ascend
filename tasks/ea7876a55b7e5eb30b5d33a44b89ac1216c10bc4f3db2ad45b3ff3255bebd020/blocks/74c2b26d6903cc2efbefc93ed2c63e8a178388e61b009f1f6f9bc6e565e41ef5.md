## 1. 为什么改 KV 前只有精度问题，改后出现卡死

原始 scheduler 语义一直是 384-token block。成熟布局为：

```text
[conv 46,080]
[MLA K / Mamba SSM 393,216]
[MLA V 49,152]
总计 488,448 B
```

draft GQA 的一个 384-token block 则是：

```text
GQA K 49,152 B
GQA V 49,152 B
总计 98,304 B
```

旧 reshape 把 GQA K/V 从 488,448 B 公共页尾部切出来，实际形成：

```text
GQA K: [390,144, 439,296)
GQA V: [439,296, 488,448)
```

因此：

- GQA K 与 MLA K/Mamba SSM 尾部重叠；
- GQA V 与 MLA V 完全重叠；
- GQA、MLA、Mamba 属于不同 KV group，通常使用不同 block id；
- 不同 stride 的 view 会让不同 id 仍然映射到交叉物理地址。

这会污染 KV 数据，表现为 `!`、second-hit 错误等精度问题，但 scheduler 仍按 384 调度，所以通常不会卡死。

后来错误的 padding 实现把 GQA `FullAttentionSpec.block_size` 从 384 提升到了 3072。这个修改穿透到了：

```text
spec.block_size
  -> resolve_kv_cache_block_sizes
  -> scheduler_block_size = 3072
  -> block table / admission / request wave
```

R16/R18 中，一个短请求的 20 个 KV group 变成：

- 6 个 GQA group：各分配 1 个大 block；
- 14 个 target/Mamba group：各分配 8 个 384 block；
- 合计 118 个 block/请求，而正常应接近 20 个。

c64 很快达到 56.6% KV 使用率，并让不同 DP 进入不同 target-forward/collective 波次。R18 已确认：

- 所有 64 个 worker 都完成了 attention 前的同步；
- 不是 H2D backlog；
- DP0/1 能走到 layer1 MLP；
- DP2/3 卡在 layer0 attention；
- DSpark 当前根本没有初始化 zeroer，所以不能归因于 zero kernel。

因此当前最符合所有证据的因果链是：

```text
旧问题：物理 lane 重叠
       -> KV 污染
       -> 精度错误

错误修复：把物理连续性编码成 block_size=3072
         -> scheduler/admission 语义变化
         -> DP collective 波次不一致
         -> c64 卡死
```

最终确认条件是新布局下 c64 消失。

## 2. 当前 block id 到底怎么共享

不是所有 spec 共用同一个 block id：

- 同一个 `KVCacheGroupSpec` 内的层共享 block table 和 block id；
- MLA、Mamba、draft GQA 属于不同 group，各自有 manager/block table；
- 所有 manager 共用一个全局 `BlockPool`，因此活跃 id 全局互斥，但不同 group 通常拿不同 id；
- `KVCacheTensor.shared_by` 只表示底层 allocation 共享，不表示 group 共用同一个 id。

所以布局不能依赖“MLA/GQA 恰好拿到相同 id”。不同 lane 必须在物理上互不交叉。

## 3. 当前实现方案

当前方案完全撤销 3072 promotion，所有 spec 保持 384：

```text
scheduler block size = 384
hash block size      = 原逻辑
coordinator          = 原逻辑
BlockPool            = 原逻辑
block table          = 原逻辑
```

只扩展公共物理页：

```text
[conv]
[MLA K / Mamba SSM]
[MLA V]
[GQA K]
[GQA V]
```

真实 K3 数值为：

```text
成熟 MLA/Mamba 区域  488,448 B
追加 GQA K            49,152 B
追加 GQA V            49,152 B
新公共页              586,752 B
```

这里的 K/V 都是全局 structure-of-arrays：

```text
[所有 block 的 GQA K][所有 block 的 GQA V]
```

因此：

- GQA K 首轴连续；
- GQA V 首轴连续；
- 没有 K/V 交错；
- 不使用首轴非连续 `as_strided`；
- 不需要独立 GQA pool；
- 不留 fallback；
- 不修改 scheduler 或 coordinator。

结构识别也没有写模型名：只有同时出现 Mamba、MLA 和更小的 padded dense attention 时才启用；Qwen3.5 原生 GQA+Mamba、纯 MLA DSpark 等路径保持不变。
