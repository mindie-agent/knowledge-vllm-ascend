## 评估结论

建议从当前四平面方案迁移到 SGLang 式的：

> 共享逻辑 slot/block allocator，但 target KV 与 draft KV 使用独立物理池。

它能从架构上解决两个问题中的主要部分，但不能简单照搬 SGLang 全部实现。

| 问题 | 能否根治 | 说明 |
|---|---|---|
| 四平面 target/draft 物理别名和 Prefix Cache 所有权混乱 | 能 | draft 不再写入 target MLA/Mamba 的共享 backing |
| 20-group metadata 膨胀 | 能 | 确定会从 20 组降为 4 组 |
| dummy 写坏 target KDA/Mamba state | 不能单靠独立池 | 必须保留现在的 dummy `seqlen=0` 合约 |
| metadata builder 本身仍偏重 | 只能显著缓解 | 4 组下仍有 3 次 GDN builder，需要继续合并公共计算 |
| P/D Prefix Cache | 需要额外实现 | draft companion KV 必须随 target block 一起传输或重建 |

### 为什么是 20 → 4

当前测试拓扑是：

- 24 层 MLA
- 69 层 Mamba
- 5 层 GQA draft

上游 hybrid 分组取最小层数 5 作为 group size，因此形成：

- `ceil(24/5) = 5` 个 MLA group
- `ceil(69/5) = 14` 个 Mamba group
- `ceil(5/5) = 1` 个 GQA group
- 合计 **20 个 group**

证据在 [test_prefix_cache_cp_patches.py](</private/tmp/pr13277-clean-dummy-eager.XhJxQR/tests/ut/patch/platform/test_prefix_cache_cp_patches.py:167>)。

把 GQA draft 完全移出 target `kv_cache_config` 后，只剩 24 MLA + 69 Mamba。按上游算法：

- group size 变成 24
- MLA：1 组
- Mamba：3 组
- 合计 **4 组**

分组规则见 [kv_cache_utils.py](<<redacted:local-path:b8dd889167fe>/vllm-core-v0.26.0/vllm/v1/core/kv_cache_utils.py:1209>)。

现有 MLA DSpark profiling 已经验证了这个形态：每次 forward 正好 **1 MLA builder + 3 GDN builder**。5 次 forward 共 20 次 group builder，其中 15 次是 GDN。

该 trace 中：

- `_build_attention_metadata`：平均约 7.45 ms/forward
- 三次 GDN builder：合计约 5.97 ms/forward

所以独立 draft pool 会消除“20 组”这个异常放大，但若还希望 metadata 降到很低，需要进一步让三个 GDN group 共享 seq-lens、query-start、accepted-count 等公共计算，只分别生成各自的 block/state indices。Profiling 在 [trace_view.json](<redacted:local-path:a4314fb2a89f>)。

## Prefix Cache 方案

推荐实现成一个 scheduler 不可见的 `DSparkDraftKVPool`：

1. GQA draft layer 不再注册进 target `kv_cache_config`。
2. 选择 target 的 full-MLA block/slot mapping 作为 canonical logical slot。
3. target hidden projection显式写入独立 draft K/V pool 的同一 logical slot。
4. draft attention 只访问该 pool，禁止再复用 MLA RoPE plane 或追加 V plane。
5. draft pool 不拥有独立 allocator；target block 的 allocate/free/evict/reuse 同时决定 companion draft slot 的生命周期。
6. slot reuse 增加 generation 标记，避免 Prefix Cache eviction 后读取旧 draft KV。

这与 SGLang 的核心做法一致：draft worker共享 target `req_to_token_pool`，但拥有独立 `token_to_kv_pool`，target hidden 再显式注入 draft pool，见 [model_runner_kv_cache_mixin.py]([REDACTED_SECRET].[REDACTED_SECRET].py:621) 和 [dspark_kv_inject.py]([REDACTED_SECRET].[REDACTED_SECRET].py:31)。

两个必要边界：

- 当前已提交的 dummy `seqlen=0` 修复必须保留。独立 draft pool 不会阻止错误 dummy 继续写 target KDA/Mamba recurrent state。
- P/D 场景必须把 draft companion pool 纳入传输。如果只传 target KV，Prefix Cache 命中后 draft prefix 缺失，轻则采信率下降，重则读取复用槽残留。

另外不建议复制 SGLang 的 NPU seq-lens 路径；它的 graph update 仍有 `seq_lens.cpu()`，会重新引入我们正在消除的 D2H 全局同步。

总体建议是切换方案，并分成两层完成：

1. 先做独立 draft pool，使 20 组确定降到 4 组，同时彻底解除 target/draft 物理所有权耦合。
2. 再把三个 GDN metadata builder 的公共部分合并，解决剩余约 6 ms host 开销。

当前只完成评估与资源释放，没有修改或提交代码。
