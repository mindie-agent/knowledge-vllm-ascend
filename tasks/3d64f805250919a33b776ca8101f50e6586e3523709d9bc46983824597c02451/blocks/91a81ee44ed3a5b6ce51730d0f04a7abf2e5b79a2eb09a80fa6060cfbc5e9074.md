### assistant:final_answer
`_apply_attention_residual` 本质上是一个“按 token、跨 residual 候选做可学习 softmax 加权”的复合算子。它不是普通的 `x + residual`，而是从多个历史 block residual 和当前 `prefix_sum` 中动态选择并融合。

实现位于 [kimi_k3_text.py](<redacted:local-path:ab3a0db0003c>:348)。

### 输入输出规格

设：

- `T`：当前批次展开后的 token 数
- `H`：hidden size
- `R`：已保存的 residual block 数
- `K = R + 1`：总候选数

| 参数 | Shape | 当前模型 dtype | 含义 |
|---|---:|---|---|
| `prefix_sum` | `[T, H]` | BF16 | 当前 residual block 内累计的状态 |
| `block_residual` | `[T, R, H]` | BF16 | 历史 residual block 起点 |
| `projection.weight` | `[1, H]` | 通常 BF16 | 将归一化候选映射成标量分数，无 bias |
| `norm.weight` | `[H]` | 通常 BF16 | RMSNorm 的逐通道缩放参数 |
| `norm.variance_epsilon` | scalar | Python float | RMSNorm 数值稳定项 |
| 输出 | `[T, H]` | 与拼接输入相同，当前为 BF16 | 所有候选 residual 的加权和 |

当前 Kimi-K3 配置是：

- `H = 7168`
- `attn_res_block_size = 12`
- `rms_norm_eps = 1e-5`
- `num_hidden_layers = 93`
- 模型 dtype 为 `bfloat16`

### 正向计算过程

首先拼接候选 residual：

\[
V = \operatorname{concat}
\left(
\text{block\_residual},
\text{prefix\_sum}[:,None,:]
\right)
\]

形状变化：

```text
block_residual : [T, R, H]
prefix_sum     : [T, H]
unsqueeze      : [T, 1, H]
values V       : [T, R+1, H]
```

随后整个计算提升到 FP32：

\[
V_{32} = \operatorname{float}(V)
\]

对每个 token、每个候选单独计算 RMS：

\[
\operatorname{rms}_{t,k}
=
\sqrt{
\frac{1}{H}\sum_h V_{t,k,h}^{2}+\epsilon
}
\]

\[
\hat V_{t,k,h}
=
\frac{V_{t,k,h}}{\operatorname{rms}_{t,k}}
\]

注意这里没有显式执行完整的 `norm(V)`，而是把 RMSNorm 的 `weight` 与 projection weight 预先融合：

\[
w_h =
\text{norm.weight}_h
\cdot
\text{projection.weight}_{0,h}
\]

每个候选得到一个标量分数：

\[
s_{t,k}=\sum_h \hat V_{t,k,h}w_h
\]

然后沿候选维 `K` 做 softmax：

\[
p_{t,k}
=
\operatorname{softmax}_k(s_{t,k})
\]

最终对原始、未归一化的 residual 候选进行加权：

\[
Y_{t,h}
=
\sum_k p_{t,k}V_{t,k,h}
\]

最后把 FP32 结果转换回输入 dtype：

```text
probabilities : [T, 1, K], FP32
values_fp32   : [T, K, H], FP32
matmul        : [T, 1, H], FP32
squeeze       : [T, H], FP32
output        : [T, H], BF16
```

### 关键语义

1. **softmax 是沿 residual 候选维执行的**

   不跨 token，也不跨 hidden channel。每个 token 独立决定应该从哪些 residual block 取信息。

2. **归一化只用于计算权重**

   最终加权的是原始 `values_fp32`，不是归一化后的 `normalized`。因此输出仍然保留 residual 的原始幅值。

3. **输出是凸组合**

   softmax 权重非负且和为 1，因此每个 token 的输出是其 `K` 个 residual 候选的凸组合，而不是无约束线性叠加。

4. **`projection` 不执行 forward**

   算子直接访问：

   ```python
   projection.weight.squeeze(0)
   ```

   所以实际要求它必须暴露 `[1, H]` 的 `weight`，且不能依赖 bias、量化 forward 或其他 projection 逻辑。

5. **FP32 是明确的数值规格**

   RMS、打分、softmax、加权求和全部在 FP32 中执行，只在输出时降回 BF16。这对 `H=7168` 的长归约以及 softmax 稳定性很重要。

### Shape 和设备约束

当前函数没有显式检查，但实现隐含要求：

- `prefix_sum.ndim == 2`
- `block_residual.ndim == 3`
- `prefix_sum.shape == [T, H]`
- `block_residual.shape[0] == T`
- `block_residual.shape[2] == H`
- `norm.weight.shape == [H]`
- `projection.weight.shape == [1, H]`
- 两个数据 tensor 必须能够直接 `torch.cat`，因此 dtype 和 device 必须一致
- 参数和数据也必须位于兼容设备上
- 语义上只应接受浮点类型；整数虽然部分操作可能运行，但输出转换回整数会破坏算法含义

`R=0` 在数学和实现上都是合法的：

```text
block_residual = [T, 0, H]
values         = [T, 1, H]
softmax        = 1
output         ≈ prefix_sum
```

不过 decoder 在 self-attention 前会跳过这种无意义的单候选计算；MLP 前和模型最终输出处仍会调用，见 [decoder 调用点](<redacted:local-path:ab3a0db0003c>:435)。

### Kimi-K3 实际候选规模

每隔 12 层保存一个新的 `block_residual`。93 层对应 block 起点：

```text
0, 12, 24, 36, 48, 60, 72, 84
```

所以完整模型末尾：

```text
R = 8
K = R + 1 = 9
values shape = [T, 9, 7168]
output shape = [T, 7168]
```

因此它不是 attention 序列维上的算子，复杂度也与上下文长度的平方无关；其主要计算量约为：

\[
O(TKH)
\]

其中当前最大 `K` 只有 9。单测也用 `[3,4] + [3,2,4] → [3,4]` 验证了同一套参考数学，见 [test_kimi_k3.py](<redacted:local-path:84a3792fadf3>:360)。

### user
这个算子是每12层执行一次吗


### assistant:final_answer
不是。**每 12 层执行一次的是向 `block_residual` 中新增一个残差候选**，而 `_apply_attention_residual` 基本上每层都会执行。

每个 decoder layer 中：

1. Attention 前：

   - 当 `block_residual` 非空时执行一次。
   - 只有第 0 层因为初始 `R=0` 而跳过。

2. Attention 后、MLP 前：

   - 每层都执行一次。

3. 全部 93 层结束后：

   - 额外执行一次输出 residual 融合。

因此 93 层模型总调用次数是：

\[
92 + 93 + 1 = 186
\]

而每隔 12 层执行的是下面的更新：

```python
if self.layer_idx % self.attn_res_block_size == 0:
    block_residual = torch.cat(
        (block_residual, prefix_sum.unsqueeze(1)),
        dim=1,
    )
```

对应层为：

```text
0, 12, 24, 36, 48, 60, 72, 84
```

可以概括为：

```text
每层：执行 residual 加权融合
每 12 层：增加一个新的 residual 候选
```

相关逻辑见 [kimi_k3_text.py](<redacted:local-path:ab3a0db0003c>:441)。

### 输入输出规格

设 `T` 为当前 forward 中展平后的 token 数，`R` 为当前已经保存的 residual block 数：

| 输入 | 真实 Shape | dtype | 说明 |
|---|---:|---|---|
| `prefix_sum` | `[T, 7168]` | BF16 | 当前 residual block 内的累计状态 |
| `block_residual` | `[T, R, 7168]` | BF16 | 已保存的历史 residual block |
| `projection_weight` | `[1, 7168]` | BF16 | residual 打分投影权重 |
| `norm_weight` | `[7168]` | BF16 | RMSNorm 权重 |
| `variance_epsilon` | scalar | FP32/host float | 固定为 `1e-5` |
| 输出 `out` | `[T, 7168]` | BF16 | residual 候选的动态加权结果 |

其中中间候选张量：

```text
values = concat(block_residual, prefix_sum[:, None, :])
values.shape = [T, R + 1, 7168]
```

`R+1` 是 softmax 的长度。

### `T` 的真实含义

vLLM 在这里使用的是展平 token 布局，不是 `[batch, seq, hidden]`：

```text
prefix_sum: [num_tokens, 7168]
```

所以：

- Decode 时通常 `T ≈ 当前活跃请求数`
- Prefill 时 `T = 当前批次所有实际处理 token 数之和`
- Chunked prefill 时是当前 chunk 的 token 总数

因此 `T` 是动态维度，不能固定为 batch size 或 sequence length。

### 每层对应的真实 `R`

Attention 前和 MLP 前的 `R` 有时不同，因为在第 `0、12、24...` 层会新增一个 block residual。

| 层范围 | Attention 前 `R` | MLP 前 `R` |
|---|---:|---:|
| 0 | 不调用 | 1 |
| 1–11 | 1 | 1 |
| 12 | 1 | 2 |
| 13–23 | 2 | 2 |
| 24 | 2 | 3 |
| 25–35 | 3 | 3 |
| 36 | 3 | 4 |
| 37–47 | 4 | 4 |
| 48 | 4 | 5 |
| 49–59 | 5 | 5 |
| 60 | 5 | 6 |
| 61–71 | 6 | 6 |
| 72 | 6 | 7 |
| 73–83 | 7 | 7 |
| 84 | 7 | 8 |
| 85–92 | 8 | 8 |
| 最终输出融合 | 8 | — |

所以完整模型的实际范围是：

```text
R ∈ [1, 8]
softmax长度 K = R + 1 ∈ [2, 9]
```

模型初始化时会短暂存在：

```text
block_residual.shape = [T, 0, 7168]
```

但第 0 层 Attention 前会跳过该算子；第 0 层 MLP 前已经变成 `[T,1,7168]`。因此如果算子只覆盖实际调用，通常不必支持 `R=0`；为了接口完备，支持也没有问题，此时输出就是 `prefix_sum`。

### 推荐的自定义算子接口

```cpp
Tensor apply_attention_residual(
    Tensor prefix_sum,          // [T, H], BF16
    Tensor block_residual,      // [T, R, H], BF16
    Tensor projection_weight,   // [1, H], BF16
    Tensor norm_weight,         // [H], BF16
    float variance_epsilon      // 1e-5
) -> Tensor;                    // [T, H], BF16
```

这里建议把 `variance_epsilon` 设计成算子属性/host scalar，而不是设备 Tensor，因为它是模型固定超参数，不需要每次从 device 读取。

如果框架要求所有参数都是 Tensor，则可以用：

```text
variance_epsilon: FP32 scalar tensor，shape=[]
```

### 算子内部计算 Shape

```text
prefix_sum.unsqueeze(1)          [T, 1, 7168]
block_residual                   [T, R, 7168]
values                           [T, R+1, 7168] BF16

values_fp32                      [T, R+1, 7168] FP32
variance                         [T, R+1, 1]    FP32
normalized                       [T, R+1, 7168] FP32

norm_weight * projection_weight [7168]         FP32
scores                           [T, R+1]       FP32
probabilities                    [T, R+1]       FP32

output_fp32                      [T, 7168]       FP32
output                           [T, 7168]       BF16
```

`projection_weight` 可以在算子入口视为 `[1,7168]`，内部 squeeze 成 `[7168]`。如果是自己定义全新的底层接口，也可以直接规定它为 `[7168]`，减少一次无实际成本的维度处理；但若要无缝接入现有 checkpoint/模型代码，保留 `[1,7168]` 更方便。
