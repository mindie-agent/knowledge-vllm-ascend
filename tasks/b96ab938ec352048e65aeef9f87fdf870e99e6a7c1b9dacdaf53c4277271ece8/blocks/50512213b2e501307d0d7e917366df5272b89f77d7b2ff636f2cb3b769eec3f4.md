### 2. DeepSeek V4 exact-token mismatch — 路径变化 confirmed，因果 attribution strong suspect

精确路径：

1. `vllm_ascend/utils.py:896-900`  
   `shared_expert_dp_enabled()` 从：
   ```python
   explicit_dp or enable_sp() or enable_sp_by_pass()
   ```
   改为：
   ```python
   explicit_dp or enable_sp_by_pass()
   ```

2. `vllm_ascend/ops/linear_op.py:511-518`  
   unchanged consumer 根据该值决定 shared expert 权重是否 `disable_tp`。因此 FlashComm1-only 配置从“shared expert replicated”变成普通 TP shard。

3. `vllm_ascend/ops/fused_moe/fused_moe.py:864-871`  
   新状态下 MC2/AllToAll/FusedMC2 shared output 会执行 TP all-reduce；旧状态跳过。

4. `fused_moe.py:569-580`  
   `_fused_output_is_reduced` 又告诉 upstream 不要做第二次 reduce，整个 shared-expert 分片与归约位置、顺序发生改变。

5. `tests/e2e/pull_request/four_card/test_deepseek_v4.py:43-65`  
   DSV4 测试设置 `VLLM_ASCEND_ENABLE_FLASHCOMM1=1`、TP4+EP，但未设置 `enable_shared_expert_dp`，准确命中新路径。

Kimi 必需性：Kimi K3 确实需要 FlashComm1 下 shared expert 保持 TP-sharded；把这个语义全局施加给既有模型并非必要。

判断：权重分片、局部 matmul 和归约顺序确定发生变化；量化模型因此出现 exact-token 差异很可信。但代数上两种实现可能等价，所以未做 runtime/bisect 前应标记为 strong suspect，而不是宣称已证明唯一根因。

最小收窄：增加模型/算子 capability，例如 `flashcomm_uses_tp_sharded_shared_experts`，只对 Kimi K3 启用；`linear_op` 与 shared-output reduce 共用该 capability。非 Kimi 保留旧行为。

## 其他 confirmed 全局作用域问题

1. `vllm_ascend/ops/fused_moe/moe_comm_method.py:436-448`  
   条件 `quant_type == NONE or SituActivationConfig` 把所有非量化 MoE 都送进 generic dispatch→MLP→combine。影响所有 FusedMC2 非量化 routed/shared experts。Kimi 只需要 SiTU 分支。最小方案是仅保留 `SituActivationConfig`；其他 `QuantType.NONE` 应在 comm-method 选择前回到其旧实现，不能继续落入 MegaMoe。

2. `vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/kv_transfer.py:195-220,1589-1620`  
   `LayerBatchBuilder.build_shared()` 去掉 request identity 去重，final layer 又去掉 `load_keys` 去重；而 `pool_worker.py::_prepare_load_gvas` 每个 request 只 add lease 一次。一个 request 有多个 block ranges 时会重复 `batch_remove_lease`。这是 confirmed lease/refcount 不对称，影响所有 KV Pool layerwise load，完全非 Kimi 必需。应恢复两处去重，或显式携带 acquisition count/token。

3. `vllm_ascend/ops/linear_op.py:455-480`  
   FlashComm1 下以全局 substring `"g_proj"` 选择 Step3p5 `SequenceColumnParallelOp`；Kimi `models/kimi_k3.py:665-670` 的 MLA output gate 同名，因而也被误匹配，而 `mla_v1.py:2062-2068` 已自行 gather gate input 并要求 local head shard。固定 head 存在 confirmed Kimi correctness bug。应按模型/精确 prefix 注册 Step3p5 规则，而不是全局字符串匹配。

4. `vllm_ascend/ops/rotary_embedding.py:52-117`  
   普通 MLA 与 Kimi no-RoPE identity 路径复用 `_cos_mla/_sin_mla`。普通 `get_cos_and_sin_mla()` 会覆写缓存，identity getter 不恢复 ones/zeros。单一全-Kimi worker 通常安全；同进程 target/draft、多 engine 或异构 layer 交错时存在 confirmed alias，实际 corruption 为 suspect。应使用独立 immutable identity buffers。

5. `vllm_ascend/utils.py:660-787`  
   `_ASCEND_CUSTOMOP_IS_REIGISTERED` 是进程级一次性开关，但 Kimi op 仅在第一次调用看见 `model_type=="kimi_k3"` 时加入。先加载非 Kimi、后加载 Kimi 时无法注册。影响同进程多 engine/test ordering。Kimi op 应无条件安全注册，或按 op name 独立幂等。

6. `vllm_ascend/ascend_forward_context.py:286-300`  
   A2 上 `num_experts > 512` 无模型区分地强制 AllGather。影响所有大专家数 A2 MoE；Kimi 可能需要规避算子上限，但全模型应用并非必要。应绑定具体 operator capability/硬件限制，或 Kimi 模型能力，而非裸 expert count。

7. `vllm_ascend/ops/fused_moe/fused_moe.py:807`  
   quantized shared expert 路径从仅 W4A8MXFP 扩到 W8A8MXFP。影响所有 W8A8MXFP shared MoE，非 Kimi K3 必需；应拆成独立修复并配 dedicated coverage。

## KV spec 静态结论

`vllm_ascend/core/kv_cache_interface.py:35-79` 将 Ascend MLA override 改为 `real_page_size_bytes`，让 inherited `page_size_bytes` 计入 quant scale/padding。对 K3 hybrid Mamba/attention 对齐是必要的，静态上方向正确。

但 `AscendMLAAttentionSpec.merge()` 从第一个 spec 复制 `kv_quant_mode`、`page_size_padded`、`indexes_kv_by_block_stride`、`alignment`、`compress_ratio`、`model_version`，却未验证组内这些字段相等。这是 confirmed invariant gap；是否有现存模型触发是 suspect，最小修复是把所有被复制的布局字段加入 equality validation。

对 DeepSeek V4，无法静态确认 KV spec 是 token mismatch 根因：DSV4 的 `model_version/compress_ratio` 保留更像修复，且 MTP hidden-state cache 在 model runner 中有独立处理。当前更直接的静态链是 shared-expert 分片/归约改变。

## 广域配置与 monkey patch 风险

- `gdn_attn_builder.py:151-153`：任何 dict 型 `linear_attn_config` 都按 K3 schema 读取并做 `num_heads // TP`；其他 linear-attention 模型可能 schema 不同或得到 0。应 Kimi/config-class gate。
- `mooncake_connector.py:1103-1106`：任何非空 `linear_attn_config` 都假设 K3 的三段等宽 conv state；会影响其他 hybrid 模型。应由 cache-spec 明确描述 layout。
- `mooncake_connector.py:3229`：`has_mamba_group && num_kv_heads==1 && num_group_pulls==1` 改变所有 hybrid single-KV-head 模型的 replica selection；不是 Kimi 专属，应独立验证。
- `envs.py:83` + `attention/mla_v1.py`：FIA split 默认关闭，但向所有 MLA 实现加入大段 A5 路径。Kimi 适配不要求它；建议拆 PR，至少按硬件和模型 capability 双重限制。
- `patch/platform/__init__.py:21-23` 无条件导入 Kimi parser/renderer patch；`patch_kimi_k3_parsers.py:631-689`、renderer `:402-448` 全局替换 vLLM serving 类方法。非 Kimi 当前有 fallthrough，未确认现时错误，但这是 process-wide signature-drift risk。应优先用正式 registry；否则 wrapper 使用透明参数并加入非 Kimi identity/signature 测试。
- `transformers_utils/configs/kimi_k3.py:181-187` 直接覆盖 vLLM 私有 `_CONFIG_REGISTRY["kimi_k3"]` 并以 `exist_ok=True` 注册 Transformers config。Kimi 功能需要注册，但不应静默覆盖未来 upstream 同名实现；应检查已有类型兼容性。

整体保留建议：保留 Kimi config/model/KDA/SiTU/no-RoPE/hybrid-page-padding的局部实现；将 shared-expert FlashComm1 语义、SiTU comm fallback、linear prefix 规则都改为显式 Kimi capability；恢复 standalone shared-expert-DP contract；KV Pool lease 去重应直接恢复；FIA、W8A8MXFP、A2 >512 与广域 Mooncake 规则应拆分或单独覆盖。
