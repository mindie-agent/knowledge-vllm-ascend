### assistant:final_answer
对，上一条“proposer 再额外传 target config”的方案不够自然，我收回。现有模型不是这么处理的。

仓库里的主流做法是：

| 场景 | 处理位置 | 做法 |
|---|---|---|
| 普通 QuaRot target | ModelSlim/量化层 | 从 descriptor 加载旋转信息，模型前向无需额外处理 |
| QuaRot + Eagle3 | draft model adapter | draft 构造时直接取得 target `VllmConfig`，在 `load_weights()` 中反旋转 `fc`，缺 embedding 时加载 target embedding 后转换 |
| QuaRot + Qwen3/DSpark | draft model adapter | 同样在 draft model 中读取 target rotation，处理 `fc` 等输入边界 |
| K3 DSpark 共享层 | 当前 PR 自定义 hook | draft loader 暂存 rotation，proposer 分享 embedding/lm_head 时回调模型处理 |

最明确的先例是 [llama_eagle3.py](<redacted:local-path:cd0d6aef4f7c>:92)：

- `__init__()` 直接从已有的 `vllm_config` 取得 target rotation。
- `load_weights()` 负责 `fc` 和缺失 embedding 的基变换。
- 不需要 proposer 再传一次 target config。
- 这也是主线 PR #10896 删除早期 monkey patch、改成注册 Ascend model class 后的正式实现。

原因是 vLLM 的 draft model 构造契约本来就同时提供了：

- `vllm_config.model_config`：target 模型信息；
- `vllm_config.quant_config`：target 量化信息；
- `vllm_config.speculative_config.draft_model_config`：draft 模型信息；
- `get_draft_quant_config(vllm_config)`：draft 自己的量化配置。

上游 `Qwen3DSparkForCausalLM` 也依赖这个契约：它从 target config 获取 target layer 数量，同时从 speculative config 获取 draft config。因此再传一次 target config 是重复的，也会掩盖当前真正的问题。

K3 比普通 Eagle3 多出来的难点是：它的 draft checkpoint 没有自己的 embedding/lm_head，而这两个模块只有 target 加载完之后才容易安全取得。这里有两个选择：

1. 像 Eagle3 一样在 draft `load_weights()` 中重新从 target checkpoint 读取并转换 embedding/lm_head。

   优点是 proposer 完全不感知 QuaRot；缺点是重复读大权重，而且可能绕过 target 加载后的 TP 分片、权重转换和模块状态。

2. proposer 仍按上游职责决定是否共享，但把实际基变换交给 draft model。

   这更适合 K3，因为 proposer 手上已经有加载完成的 target module。不过应该做成明确的模型能力接口，而不是现在这种依赖字符串 `label` 和临时 `_shared_layer_rotation` 状态的松散 hook。

因此我建议保留“proposer 提供待共享的 target layer、modeling 负责转换”的边界，但进行两点调整：

- 不再传 target config；draft model 使用构造时已有的 `vllm_config`。
- 不依赖 loader 到 proposer 之间的临时 `_shared_layer_rotation`。使用明确的共享层准备接口，按 embedding/lm_head 类型处理；QuaRot 模型必须返回 draft-owned aligned layer，普通模型继续走上游直接共享。

`process_weights_after_loading()` 也不太适合这里：它执行时能看到 draft，但拿不到已加载的 target embedding/lm_head；为了使用它反而要引入全局状态或反向引用，更 hack。

所以当前第一步不应该添加新接口兜底，而应该确认为什么既有契约失效：

- 实际实例是不是 `AscendQwen3DSparkForCausalLM`；
- 构造时 `rotation_path` 是否正确；
- `load_weights()` 后为什么 `_shared_layer_rotation` 为空。

如果实例化成了上游类，就修模型注册；如果是 Ascend 类但 `rotation_path=None`，就修 config/descriptor 映射。不能再用 proposer 传 config 把这个错误遮住。
