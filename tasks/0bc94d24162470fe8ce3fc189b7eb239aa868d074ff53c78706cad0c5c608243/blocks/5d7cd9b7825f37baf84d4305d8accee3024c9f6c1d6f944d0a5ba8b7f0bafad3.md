### GQA

混合 attention group 中包含：

```text
target MLA backend/spec  → 1 builder
draft GQA backend/spec   → 1 builder
```

再加三个 Mamba group：

```text
2 attention builders + 3 Mamba builders = 5 builds
```

所以当前已有 GQA UT 也是“4 groups、5 builders”。

### MLA

虽然 target/draft 都是 MLA 类型，但 exact spec 不相同：

```text
target: non_causal_multi_token_decode=False
draft:  non_causal_multi_token_decode=True
```

`AttentionGroupKey` 包含完整 spec，所以仍会拆成：

```text
target MLA builder → 1
draft MLA builder  → 1
Mamba builders     → 3

合计 5
```

当前 [`test_kimi_k3_mla_dspark_uses_four_groups_and_four_builders()`](<redacted:local-path:c1c3d32cf38e>:302) 用的是：

```python
len({type(spec) for spec in ...})
```

它只比较 Python 类型，没有按照生产代码比较 exact spec/backend，因此错误地算成了 4。

也就是说，这个 PR 正确的描述应该是：

| 场景 | 原始 KV groups | 当前 KV groups | 原始主循环 builds | 当前主循环 builds |
|---|---:|---:|---:|---:|
| GQA DSpark | 20 | 4 | 20 | 5 |
| MLA DSpark | 4 | 4 | 约 4 | 5，保留 target/draft 语义 |

## 7. 物理 KV 内存上的代价

当前方案主要优化的是 metadata build 次数，不是 KV 容量。

当前四组大小是：

```text
[29, 23, 23, 23]
```

由于所有 group 从统一 block pool 分配，物理 block stride 必须容纳最大 group，也就是 29 个 page：

```text
每个 group block 的物理容量 = 29 pages
每个请求同一序列区间需要 4 个 group block
总容量 = 4 × 29 = 116 layer-pages
```

实际 layer 只有：

```text
29 + 23 + 23 + 23 = 98 pages
```

因此有：

```text
116 - 98 = 18 pages 空置
padding 比例 = 18 / 116 ≈ 15.5%
```

原始 GQA 的 20 组每组最多 5 层：

```text
20 × 5 = 100 pages
实际 98 pages
仅浪费 2%
```

所以 GQA 当前方案是明确的权衡：

- metadata build：20 → 5，显著减少小 batch/decode 热路径开销。
- scheduler group/block table：20 → 4。
- KV 最大容量：理论上比原始 20-group 方案降低约 `1 - 100/116 ≈ 13.8%`。
- MLA 原本就是 `[29,23,23,23]`，因此容量布局基本没有变化。

当前物理布局 UT 也明确验证了：29 个 raw tensor 中，前 23 个由四组 layer 共享 backing，最后 6 个只属于 attention group。

## 最终应如何描述这个 PR

最准确的一句话是：

> 当前 PR 没有缓存或复用 metadata builder 的输出，而是让 target/draft full-sequence attention 共用 scheduler ownership，再把 69 个 Mamba 层均衡成三个 group；因此 GQA 从 20 个 KV group/20 次 build 降到 4 个 KV group/5 次 build，MLA 保持 4 个 KV group，同时保留 target/draft 的逐层 non-causal 语义。

评审前需要修正两点：

1. 把 MLA “4 builders”的 UT 和描述改为按照生产 `AttentionGroupKey` 计算，预期应为 5。
2. 当前 docstring 所说的“avoiding layer padding”不准确；它减少了 group/build，但物理上仍有 18/116 的 Mamba 空槽，应改成明确说明性能与 KV 容量的权衡。
