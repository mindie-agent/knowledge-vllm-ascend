2. **长活 ACP server 还有官方 hook cwd 问题。** 官方 agent hooks 没传 session cwd（`agentExternalHooksService.ts@6954d2c:346-350`），runner 回退到进程 bootstrap cwd（`externalHooksRunnerService.ts:90`）。若 server 从主仓启动、session/new 传 worktree，工具 root 正确，但现有 VAWS UserPromptSubmit 会把 attachment/source 更新回其收到的旧 cwd（sibling `coordinator/.../hooks/vaws_session.py:147-149`）。所以最薄可靠接法应让 ACP server 也从目标目录启动，或由宿主/VAWS hook 使用已经绑定的 session cwd；不能直接把“单个 ACP server 可创建不同 cwd”当作整体验收成功。

推荐取舍：

- **成本最低且真正改变 native root：** 一次安装薄 launcher；新建时 bounded prepare 返回现成绝对目录，launcher `chdir` 后 `exec` 官方 `kimi`。Skill 留给业务判断。resume 跳过 prepare，沿用原 cwd；若要从主仓一键 resume，需要启动侧只读查找旧 session cwd。原生 `/new` 不会自动新建隔离目录，需从 launcher 开始独立任务。
- **已拥有宿主客户端：** 在 session/new 前调用 prepare，再传 ACP cwd；首条提示词只携带业务任务和明确上下文。日常 Agent 无需维护路径，但宿主仍须处理上述 identity / hook cwd 边界。
- **纯 Skill 原地继续：** 技术上能靠每次 Bash 显式 cwd、文件绝对路径、一次显式绑定 VAWS sources 完成业务任务，但 native root、项目配置/MCP、索引和提示仍留在旧目录。它减少客户端补丁维护，却把日常路径一致性成本交给 Agent，不等价于原生 worktree。
- **保留个人 patch：** `/new`、fork、跨 worktree resume、MCP identity 都保持透明；维护范围已超出一个 prepare hook，涉及生命周期、TUI、fork 历史复制、子 agent 和三种 MCP transport，需要持续跟官方升级适配。
