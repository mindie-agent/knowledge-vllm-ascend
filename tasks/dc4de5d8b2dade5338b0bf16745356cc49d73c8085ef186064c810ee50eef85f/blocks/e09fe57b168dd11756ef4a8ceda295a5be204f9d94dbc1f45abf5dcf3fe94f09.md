### 4. 最小单变量 A/B

保持 checkpoint、服务参数、DP 路由、总 token 数、输出长度完全一致；由于 B 可能挂死，应使用两次 fresh service：

- A：每个 DP 发送 1 个请求，prompt 精确 7 tokens。
  - `cu=[0,7]`
  - 1 个 state
  - 总 token=7
- B：每个 DP 同时发送 7 个请求，每个 prompt 精确 1 token。
  - `cu=[0,1,...,7]`
  - 7 个 state
  - 总 token=7

都设置 `max_tokens=1`，因为 R6 已在第一个 target forward 内挂住。

解释：

- A 过、B 挂：锁定 KDA request-boundary / multi-varlen singleton。
- A、B 都挂：再看总 token 数或 TP gather。
- A、B 都过，但原序列挂：加入生命周期变量——每 DP 先完成一个 singleton，再发送 B，检查 state-slot/block-table reuse。

紧接着仅在 KDA 内增加四个 device events：gather、conv、gate-cumsum、chunk-kda 之后各一个。第一个 pending event 就是 native 修复目标。这比先做 MC2 A/B 更有信息增益。

### 5. 建议生产修复

首选 native 修复是纠正 `chunk_kda_fwd` 或 `kda_gate_cumsum` 对多段长度 1 varlen 的 tiling/stream 契约；但需要上述细粒度 events 才能决定具体 C++ seam。

可先落地的最小安全 Python 修复位于 [kimi_kda.py](<redacted:local-path:4148a02e9466>:405) 的 `_run_prefill`：

- 当 `num_decodes == num_sequences`，即所有 prefill segment 都是 singleton：
  1. 先按现有逻辑 gather 对应 recurrent state。
  2. 使用 `has_initial_state` 显式清零无历史 state 的项。
  3. 对这个紧凑、已初始化的本地 state pool 调 `_run_recurrent`。
  4. 使用本地 `state_indices=arange(num_sequences)`。
  5. 将最终 state 写回原 cache slots。
- causal conv 仍保留当前 prefill 初始化路径。
- 长 prefill、混合长度 prefill 继续走原 `chunk_kda_fwd`。

不能简单把首次 singleton 在 builder 中标为 decode：这会让 recurrent kernel 读取尚未初始化的 state。安全 fallback 的核心契约是“先建立并清零本地 state，再 recurrent，再写回”。

不建议生产上增加 worker/step/dummy fence；它不能修复 KDA 内部 kernel/collective 卡死，只会移动观测同步点或掩盖时序。
