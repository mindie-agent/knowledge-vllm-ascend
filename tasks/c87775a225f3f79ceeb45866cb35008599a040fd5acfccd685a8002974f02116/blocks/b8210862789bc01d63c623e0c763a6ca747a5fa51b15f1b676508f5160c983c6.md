- **领域能力迁移缺少台账。** 迁移前最后一版有 18 个业务 skill 和独立的 `repo-init`；结合更早拆包、退休的入口，共清点出 **25 个历史名称**。当前插件包只有一个激活入口，尚不能证明这些能力已完成迁移。
- **旧依赖无法直接搬过去。** serving、profiling 等脚本依赖旧工作区目录、共享 helper、兄弟 skill 和状态文件；需要迁移整个调用链。
- **触发和采集存在耦合。** 当前入口要求激活后查询知识，采集也依赖查询或使用留下的领域绑定。“手动启用后只做远端业务”的流程需要重新梳理。
- **维护 skill 也有迁移遗漏。** `curate-knowledge` 仍引用旧命令入口，需要逐条核对。
- **反馈机制不等于效果已经成立。** 独立裁判主要读取使用描述和摘要，还需要对照真实产物检查归因、误判和收益。

因此，发布前要补齐下面三层工作：

| 层次 | 必须完成的内容 |
|---|---|
| **完整流程调整** | 明确手动激活、领域绑定、按需选 skill、知识使用、业务执行、采集与反馈的关系；普通任务不会被迫展开整套流程 |
| **旧能力整体迁移** | 每个 skill 明确保留、拆分到工具/recipe、转为知识、替代或退休；同时迁移脚本、引用、依赖和触发条件，检查与业务仓库已有 skill 的共存 |
| **知识闭环效果验证** | 覆盖语料迁移、检索适用性、采集质量、近义去重、授权分发、实际使用、独立评价以及后续任务收益 |

**测试也要分开回答三个问题：**

1. **有没有正确触发？** 包括应该触发、不该触发，以及恢复、暂停、升级后的行为。
2. **原来的业务能力是否保留？** 从新插件入口完成真实任务，交付可检查的结果。
3. **知识是否真正有帮助？** 固定任务和环境，对照有无相关历史经验，比较结果质量、重复调查/实验、人工纠偏、耗时及前后台模型成本。

尤其要覆盖“检索到了但没用”“任务成功但经验没有贡献”“实验失败却排除了错误假设”、错版本、无命中、负向、unknown 和多轮纠正，不能只测试正向案例。所有模型测试继续使用 **5.6-luna / max、真实环境**。

并行安排已调整为：先收敛上述流程约定，再同时推进 **运行时、双平台交付、知识闭环与语料、旧 skill 迁移、真实任务评测**五条线；最后在同一发布候选上汇合验收。
