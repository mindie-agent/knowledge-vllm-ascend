### user
不一定是要用repo Init，有些人他不会去调用这个skill，所有要有一个健全的机制去处理，你可以想个办法。然后设计的原则基于以下几条



1. 一切以提升agent的效率为准，效率以完成用户实际目标的总成本衡量，包括Agent的理解、操作、等待、排错和返工。稳定性只有在降低这些成本时才值得投入，不能为了覆盖小概率异常，让每次普通任务都承担复杂流程，当其他的设计和这条冲突的时候以这条设计为基准。
2. 仅对封闭世界的问题写工具来提升稳定性，如果这个问题本身是存在多种甚至非常复杂的情况优先考虑别的办法而不是为了写工具而写工具，对于开放世界的问题，仅对适用条件、输入输出和失败边界明确的封闭问题进行工具化。对于情况多变、依赖上下文判断的问题，优先考虑其他方式。开放问题中反复出现、边界已经明确的机械操作，可以抽取为稳定工具；不为了写工具而扩大工具职责。
3. 不能增加对agent的理解负担（典型负例就是做一个无数入参的cli然后内部是个状态机报错了也无法定位）
4. 工具需要有一个非常明确的边界和定义，不要写大而全的工具，每个工具核心解决一个问题或者一类问题
5. skill更多的是提供agent所需的信息而不是强行约束agent的行为，如果提供的信息可以通过知识库沉淀条目解决则直接沉淀到知识库中
6. 知识库本身提供的知识仅作为参考，不作为一个权威性的约束，所有的决策基于已有的现象和分析为主
7. 所有工具和skill按需介入，vaws项目既可以让agent快速完成轻量级任务比如review一个pr或者看远端目录下有哪些文件，也可以完成重型任务比如从0新开发一个模型
8. 在满足当前任务语义和兼容条件的前提下，尽量复用已有算子、编译产物、环境及其他有效成果。复用检查应与变化范围相称，避免重复全量验证；常规检查由工具内部完成，无需 Agent 介入，必要的复用依据和失败原因仍可查询。
9. 工具需要有可观察性以及和定位性，工具需要说明实际做了什么、卡在哪里、哪些已经完成，并保留必要的原始证据。遇到超出能力范围的情况，应把事实交还 Agent，让它可以换方法继续。不能让 Agent 为了解开一个黑盒，被迫学习整个工具的内部实现。

推荐第一版采用 **上游正式 Release + 本地带缓存的轮询 + 新会话检查 + fast-forward 更新 + 已有不可变环境**，不引入托管服务。

已重新核查 `b63c782`：现有依赖为 remote-dev 0.7.0、coordinator 0.4.0、knowledge 0.5.0，均固定 Git revision；vaws-top 独立固定 v0.1.2 wheel。当前不可变环境与 MCP/hook receipt 机制适合直接复用。

1. **发布一套兼容组合。** Workspace release tag 对应唯一提交，其 `pyproject.toml`、`uv.lock`、vaws-top wheel 版本共同构成版本组合。组件独立发布后，由维护方更新这些输入、跑 CI，再发布 workspace release。客户端不能逐个组件追 `latest`；uv 本身也不会因上游有新版本就判定 lock 过期。[uv 官方说明](https://docs.astral.sh/uv/concepts/projects/sync/)

2. **发布前验证，发布后可消费。** 建议 tag/manual workflow 验证锁文件、最低环境、三平台消费者测试、vaws-top wheel 静态前端。先建立 draft、齐备资源后 publish；`release: published` 只负责后续通知，不把未验证的 published release 暴露给自动更新器。可启用 GitHub immutable releases，防止后续移动 tag/替换资源。[GitHub 发布管理](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)

3. **第一版“实时”定义为在线期间最多约 5 分钟发现。** 本地 watcher 定期检查上游正式 release，新会话入口做 TTL 检查补漏。缓存 ETag、last-check、release ID、tag SHA；网络失败退避，离线启动照常。GitHub 官方一般推荐 webhook，但普通电脑需要可达接收服务或代理，因此本地 polling 是此项目的实际取舍。正确授权的条件请求返回 304 不消耗主限额。[REST 最佳实践](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)、[Webhook 接收要求](https://docs.github.com/en/webhooks/using-webhooks/handling-webhook-deliveries)

4. **检测和应用分开。** startup 只做短检查或唤起独立更新进程；下载和安装不能阻塞会话 hook。当前 `docs/platform-contract.md` 约定启动不安装依赖，应明确保留这点。watcher 可更新个人 fork 的干净默认分支，但不能修改已打开的业务工作目录。应用只针对已配置 workspace、无 dirty/conflict、目标分支符合约定且可 fast-forward 的情况；否则记录 pending，留下具体原因。

5. **同步精确 release SHA。** `gh repo sync` 默认把源默认分支同步过来，可能超过已发布版本；不要直接拿它实现 release 更新。应先取 release tag，解析到 commit、核对所属官方仓库，再通过普通非强推更新个人 fork、`git merge --ff-only <release-sha>` 更新本地。已领先 release 不回退；分叉时不自动 reset/rebase，产生待合并状态。[gh repo sync](https://cli.github.com/manual/gh_repo_sync)、[Git fast-forward](https://git-scm.com/docs/git-merge)

6. **复用环境，不替换运行实例。** 更新成功后调用现有 `vaws_deps.py sync --locked` 准备新内容键环境，刷新新会话配置。运行中的 MCP/hook 保留旧 receipt；coordinator 根据已存在的 `restart-if-idle` 契约更新，不能中断执行/lease。vaws-top 先 deploy 缓存验证新 wheel，现有实例不自动杀掉；新启动或安全 restart 时切换。知识 corpus 已由 knowledge package 自己订阅 Release，保留该所有权。

7. **需要完整状态，而非单个“更新成功”。** 至少记录 `release_detected`、`fork_synced`、`checkout_applied`、`environment_prepared`、`clients_pending_restart`。没有正式 Release 是 `no_release`；不隐式回退 main。最低必要测试覆盖重复检查、网络失败、dirty/detached/diverged、fork 身份错误、下载失败、运行环境不变、非 ASCII 路径/Windows 锁。

不要把 fork 上 `release` workflow 当成订阅上游：事件发生在各自仓库；fork Actions 默认不启用，schedule 最短 5 分钟且可能延迟/丢弃，公开仓库无活动 60 天还会禁用。真正 push 实时同步可后续加入安装在用户个人 fork 的 GitHub App，但第一版不必承担它。[GitHub 事件与 schedule 约束](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)

我未修改任何文件。历史 memory 仅用于确认“不依赖在线服务”的既有偏好；当前实现判断均重新读了最新仓库。
