建议第一版保留以下五个机制。

1. **身份先绑定到真实用户，再派生 Agent。**  
   用经过认证的 GitHub `/user` 返回的数字 `id` 作为用户主键，`login` 用于展示，个人 fork 保存归属和贡献来源。GitHub 官方明确 `id` 持久，而 login 会变化。只输入名字、修改 `origin`、复制 `github.json` 都不能证明请求者身份。[GitHub Users API](https://docs.github.com/en/rest/users/users#get-the-authenticated-user)

   服务端登记 `principal_id → agent_instance_id → native_task_id`。请求的发送者由认证上下文填入，客户端不能通过 `sender="另一个人"` 改变身份。GitHub 登录后签发 VAWS 自己的凭据；不要把 GitHub PAT 当所有 VAWS 服务通用 bearer。HTTP MCP 要验证针对自身的 audience。[MCP 授权规范](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization)

2. **留言板提供目录、主题和回执。**  
   最小对象即可：用户/Agent 目录、`message_id`、`thread_id`、发送者、接收者或频道、任务引用、正文、服务器时间、过期时间，以及 `delivered/read/ack`。消息重复提交用幂等键去重；读取用递增 cursor 补拉，在线时通过 long-poll/SSE 通知新消息。presence 超时只表示离线，不触发资源回收。

3. **即时提醒与持久事实分开。**  
   “我在线”“有新消息”可以短期保留；“请求协助”“接受交接”“产物地址”“协调决定”必须落库。通知只带消息引用，Agent 再取正文。跨用户消息应带清楚来源，不能像 Gas Town 的本地 nudge 一样直接提升成可信系统指令。读到、ACK、同意执行是不同状态。

4. **任务接手采用原子状态转换。**  
   可以使用 `offered → accepted → completed`，附带 `expired/cancelled`；接受时 CAS 检查当前版本、接收人和有效期，避免两个 Agent 同时接同一请求。请求引用现有 VAWS task/execution，不另造一套硬件任务账本。Beads 的 [federation 文档](https://github.com/gastownhall/beads/blob/91aeeb054856d9de19ae079500efe506f992fafc/docs/multi-agent/federation.md) 特别说明 lease 是单 replica 的，不随数据库同步成为全局有效租约——这一点不能照搬成分布式 NPU 认领。

5. **交流结果进入 coordinator 的既有授权路径。**  
   例如 A 发“这台机器即将空闲”，B 接受；A 释放自己所属 execution，B 通过 coordinator 请求新的 allocation。留言中的机器状态只是带时间戳的提示，最终分配仍检查实时 lease。跨用户复用优先共享已经授权的服务访问或产物，权限明确区分查看、调用、控制、停止；消息 ACK 不隐含容器 shell 或停止权限。

关于“防止乱杀容器”，需要明确一条实际边界：**如果各用户仍拥有宿主机 root 或共享 Docker socket，个人 fork 和留言审计无法强制阻止绕过 VAWS。** Docker 官方说明此类权限可控制整个宿主机。要形成强约束，容器控制凭据应留在服务端，服务端对准确 container ID、execution owner、调用人、操作范围逐次检查；拒绝和管理员例外也写审计。[Docker 官方说明](https://docs.docker.com/engine/security/protect-access/)

第一版可先落到“身份绑定、定向留言、回执、协作请求、审计”五项，复用现有服务与存储入口，不引入新的 NPU 调度器。未安装或运行这些项目；以上是官方源码与文档调研。历史记忆中的跨 task 归属回归仅作检查线索，当前 coordinator 能力仍以主 Agent 的实时审查为准。
