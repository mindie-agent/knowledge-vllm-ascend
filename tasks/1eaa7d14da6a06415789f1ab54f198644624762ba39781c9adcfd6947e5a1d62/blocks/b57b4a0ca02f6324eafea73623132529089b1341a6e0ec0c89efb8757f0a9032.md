| 客户端 | 最小方案 | 能解决什么 | 成本与边界 |
|---|---|---|---|
| Claude | 仅新建时注入短提示，首个动作调用原生 `EnterWorktree` | 原生工具创建并真正切换当前会话 cwd；自动复用现有 WorktreeCreate 准备逻辑 | 每次新建多一次工具调用，不需要新 CLI 或 argv 解析。仍需一次针对性验证：切换后 VAWS 来源、shell 环境和已启动 MCP 是否同步 |
| Codex App | 首次一次选择 Worktree 和 VAWS 环境，之后原生记忆 | 后续新建直接创建、准备工作树，Agent 无额外步骤 | 两项一次性选择比每会话创建另一线程、转交任务成本低；当前缺公开脚本设置接口，不能宣称全自动初始化完成 |
| Codex 的提示词/Skill | 帮助首次配置或明确调用原生创建任务 API | 可创建另一个真正使用 Worktree 的新任务 | 不能把当前 Local 线程直接切换成 Worktree；每次转交增加线程和上下文成本 |

普通 prepare CLI 能创建目录、准备代码与环境，**不能改变已经运行的父客户端 cwd**。仅在提示词里记住路径，再给 shell 传 `workdir`，也不能保证其他文件工具、MCP 和会话绑定一致。

Claude `EnterWorktree` 是值得优先验证的低成本补充；恢复不增加流程，也不无条件注入 `--worktree`。旧路径记忆可帮助 Agent 理解任务，但实际 cwd 仍以客户端恢复结果为准。

可行，且更符合当前的成本原则。

默认采用一次 `prepare`：创建独立 worktree、绑定当前任务的默认 sources，返回绝对路径和简短提示。后续 Shell 显式指定 cwd，文件操作使用绝对路径；resume 沿用已有任务上下文。

真实限制是：

- sources 绑定不会改变原生工具默认目录。
- 已启动的 MCP 不会自动切换解释器。
- UI 仍指向母目录，手动相对路径操作仍可能落在那里。

“UI、进程 cwd、MCP 环境、会话历史必须同时迁移”属于此前额外设定的保证，不是业务编辑隔离的必要条件。保留已成功的 native 路径作为优化即可，不必让个人 Grok/Kimi builds 成为前置条件。

`context_file` 仅在已有原生关联无法自动解析时使用；保持 attachment 的真实 cwd，不伪造客户端已切换。

### assistant:commentary
如果目标是“新任务在独立 worktree 干活”，通用兜底其实可以更简单：首次准备一次目录并绑定源码来源，返回一小段客户端提示；后续 Shell 指定该目录，文件操作使用绝对路径，resume 沿用上下文。

这能减少对个人版 Grok/Kimi 的依赖。代价是 Agent 需要在工具参数里带上路径；原生界面和已启动的 MCP 不会因此搬过去，这部分不能算成已自动切换。
