### user
帮我看看vllm ascend的k3的prefill阶段是mha还是MQA

### assistant:commentary
我会按当前 checkout 的 K3 模型实现和运行时元数据链路来核对，重点区分“注意力头计算形态”和“KV cache 头数/共享方式”，避免只凭模型名判断。

### user
head num看着是96

### assistant:commentary
你看到的 96 很关键：它是 query/展开后的 attention head 数，但不能单靠它判断 MHA/MQA。我正在看 prefill 实际送进 attention kernel 的 `num_key_value_heads`，这个字段才是直接证据。

### assistant:final_answer
结论：**K3 文本模型的 full-attention 层在 prefill 计算时走的是 MHA，不是 MQA。**

你看到的 `96` 是全局 attention head 数。执行过程是：

- MLA 的 KV cache 只存 **1 个压缩 latent KV head**。
- 到 prefill 时，`kv_b_proj` 会把 latent KV 展开成与 Q 相同数量的 K/V heads：[kimi_k3.py](<redacted:local-path:a2daa046688a>:814)、[mla_v1.py](<redacted:local-path:14bef3e55999>:1939)。
- 调用 FIA kernel 时明确传入：
  `num_heads = self.num_heads`
  `num_key_value_heads = self.num_heads`
  因此是 **Q heads = KV heads，即 MHA**：[mla_v1.py](<redacted:local-path:14bef3e55999>:1471)。

比如 TP16：

```text
全局 heads = 96
每 rank heads = 96 / 16 = 6
prefill kernel: Q heads = 6, KV heads = 6  → MHA
```

但要区分：

- **Prefill 计算：MHA 形态**
- **KV cache：1 个压缩 latent KV head**
- **Decode：使用 latent KV，表现为 MLA/MQA-like，kernel 的 KV heads=1**
- K3 还有 KDA 层，所以整个 prefill 实际是 **KDA + MLA full-attention 层的 MHA prefill**，并非所有层都做 MHA：[kimi_k3.py](<redacted:local-path:a2daa046688a>:916)。

所以一句话概括：**96 是展开后的 MHA heads；存 cache 时仍然是 MLA 的单 latent KV head。**



### user
mqa是啥，和mha的区别是啥

### assistant:final_answer
MQA 是 **Multi-Query Attention（多查询注意力）**。它和 MHA 最大的区别是：**多个 Query head 是否各自拥有独立的 K/V head。**

| 类型 | Query heads | KV heads | 关系 |
|---|---:|---:|---|
| MHA | 96 | 96 | 每个 Q head 对应自己的 K/V head |
| GQA | 96 | 例如 8 | 每 12 个 Q heads 共享一组 K/V |
| MQA | 96 | 1 | 全部 96 个 Q heads 共享一组 K/V |

张量形状可以直观看成：

```text
MHA:
Q = [tokens, 96, head_dim]
K = [tokens, 96, head_dim]
V = [tokens, 96, head_dim]

MQA:
Q = [tokens, 96, head_dim]
K = [tokens,  1, head_dim]
V = [tokens,  1, head_dim]
```

虽然 MQA 的 K/V 是共享的，但 96 个 Q 不同，因此每个 head 算出的 attention score 和输出仍然不同。

主要区别：

- **MHA 表达能力更强**：每个 head 有独立的 K/V 表示。
- **MQA 的 KV cache 小很多**：上述例子理论上只有 MHA 的 `1/96`。
- **MQA decode 更快**：逐 token 解码通常受 KV cache 读取带宽限制，MQA 只需读取一份 K/V。
- **MQA 可能损失一些模型质量或容量**，所以很多模型采用中间方案 GQA。
- 对 prefill 来说，MQA 的优势一般没有 decode 那么显著，因为 prefill 更偏计算密集。

结合刚才的 K3：

```text
K3 MLA full-attention 层：

Prefill:
96 Q heads
96 展开的 K/V heads
=> MHA 方式计算

KV cache:
存储 1 份压缩 latent KV
=> 类似 MQA 的存储开销

Decode:
96 Q heads读取 1 份 latent KV cache
=> kernel 接口上类似 MQA
```

所以 K3 更准确的说法是 **MLA**，不是普通 MQA：它利用单份压缩 latent KV 降低 cache 和 decode 带宽，但 prefill 会把 latent KV 投影成多头 K/V，按 MHA 计算。
